# sandbox-ai 0.1.99

## Wildcards below a shared service: allowed after your confirmation of the risk

A host wildcard below a shared service - a hosting, cloud or tunnel service where anyone can rent a name, such as
`*.blob.core.windows.net` (every Azure storage account, yours and anyone else's) - was refused always. From this release
it is **your decision**, warned (user 2026-11-20): the agent could open any server anyone rents below
`blob.core.windows.net`, and send data there, and the confirmation says exactly that.

- **At the start**: `--allow-shared-wildcard '*.blob.core.windows.net'` (`-sw`): the option is the confirmation. Given
  with `--allow-host` instead, the start says the risk on a terminal and asks "allow anyway? [y/N]"; `--yes` (`-ys`)
  answers yes for scripts; elsewhere (no terminal, the app's check) it is refused, naming `--allow-shared-wildcard`.
  The start warns with the risk.
- **During the run**: `sandbox-ai net allow RUN --allow-shared-wildcard '*.D'` (or `--allow-host` with its question or
  `--yes`). The supervisor's control op takes such a wildcard only with that confirmation (a request written by hand
  without it is refused), and holds the run's mode and the administrator's policy as at the start. `net revoke` takes
  it back without a question. `net show --keep` keeps it as `--allow-shared-wildcard`, and only where you confirmed it
  (your command's own record, `shared-wildcards.json`, not the supervisor's word).
- **The app**: the network dialog of a running sandbox asks first (ask_first `shared-wildcard`), naming the risk and
  the shared suffix, then passes the confirmation; the Board's network part has the option (Wildcards below a shared
  service), shows what it reaches as bad, and a Start asks first (again after any change of the board or its host).
  The app never passes `--yes`.
- **The web interface**: `POST /net/NAME` refuses such a wildcard until the page's own question for it
  (`confirm_shared_wildcard`, refusal code `shared-wildcard` with the wildcards and the shared suffix); the
  `net-allow` confirmation alone is not it.
- **Marked as a risk**: the run's record (`run.json` and `config.json` `shared_wildcards`, the plan), `net show`
  (a RISK column, `shared_wildcards` in its JSON) and `sandbox-ai report` (a finding of kind `shared-wildcard`,
  medium).
- **Still refused**: in the modes high and paranoid (said with the mode, also for a run started before this
  release); where the administrator's policy forbids it (new key `forbid_shared_wildcards: true`, or
  `--allow-shared-wildcard` in `forbid`), however it is given; and always a top-level domain (`*.com`), a registry's
  public suffix (the Public Suffix List's ICANN section: `*.co.uk`, `*.kyoto.jp`), and every wildcard while the list
  cannot be read. `--allow-domain` of a shared service stays refused and names the way.

## Secret guard: secrets in outgoing requests are found in the proxy (egress DLP)

A secret a start hands the agent, or one the agent reads from the workspace (a `.env`, a key file), could leave unseen
in any request to an allowed host: an upload, a gist, a paste, an argument of a remote MCP tool. Only a Git push (the
privacy check) and a decoy's token (the canaries) were looked at. From this release the connection proxy searches
**every request it opens** - URL, headers, body (the Knostic research's R10, its cases A2, A3 and A4;
`docs/design/egress-dlp.md`):

- **The values a start hands out**: `--secret-env`, `--env` variables whose name says secret or whose value has a
  token's shape, a Git token that enters the sandbox (`--git-token-*`, `--git-credentials` without `--token-proxy`),
  the secret variables of the run's MCP image servers, a Git login given into a running sandbox (`--in-sandbox`).
  Found as they are and URL-, JSON-, hex- and base64-encoded, inside a gzip or deflate body and across two parts of a
  body: registered as canary tokens are.
- **Token shapes**: the privacy check's blocking shapes (GitHub, GitLab, AWS, Anthropic, OpenAI, Slack, Google,
  Stripe, npm, PyPI and Hugging Face tokens, private keys) - a secret the agent read from a file. Also base64-encoded
  (a file in the JSON of GitHub's contents API, an attachment).

What happens:

- **On its way to a host it was not given for**: **reported** by default (a safeguard record of kind `secret-send`,
  once per finding and host: "the value of API_TOKEN (--secret-env) went to paste.example (POST, in the body,
  base64)"), **asked about**, or **refused** (403, before anything of the request reaches the server). The modes
  `high` and `paranoid` refuse a value the start handed out; `high` asks about a shape, `paranoid` refuses it. A
  ruleset's `"secrets": {"on_send", "on_shape"}` (`report`, `ask`, `block`) tightens it, the strictest wins.
- **To the host it was given for** - a Git token to its server, `OPENAI_API_KEY` to `api.openai.com`, a GitHub token
  in a header to GitHub: nothing.
- **To the run's own model provider**: the secret **entered the model's context**. Recorded once per secret (kind
  `secret-context`), never held.

**Nothing is redacted or changed**: a request passes as the agent sent it, or not at all. **No value is shown
anywhere**: questions, records, refusals and logs name the variable or shape, the encoding and the place; the proxy's
logs mask every form of the values it knows.

- `--allow-send WHAT@HOST` (one start) and `sandbox-ai secret-guard allow | forget | list` (per project, kept outside
  every workspace) say that a finding is none - a test fixture, a token that belongs to a host of yours: `WHAT` a
  shape's id, a value's (`env:NAME`, `git-token:HOST`, `git-login:HOST`, `mcp:SERVER:NAME`) or `*`; `HOST` a name,
  `*.DOMAIN` or `*`. `high` and `paranoid` refuse a `*`. `sandbox-ai secret-guard` lists what is looked for.
- The questions come like every other (the app's Approvals page, the web interface, `sandbox-ai approvals`) with the
  kind of secret, the host and the command that allows it; for the run at most. `--ask allow` does not answer them.
- `sandbox-ai safeguards --kind secret-send,secret-context`, the app's Activity > Safeguards, the web's Safeguards
  page and `sandbox-ai report` (a secret that left: high; one in the model's context: medium) show the findings.
- **No slowdown where nothing is held**: with the default (`report`) a body is searched after it went out, while the
  server works on its answer. Searching costs 3 to 10 ms per mebibyte of body, whatever the number of values (0.1 ms
  for a usual request; it follows the request, so it adds to a round trip only where the server answers faster); where the run asks or blocks, the first mebibyte of a body is read before anything is sent.

Limits, said plainly: only what the proxy opens is seen (not `--no-inspect` hosts, `--allow-tcp`, a run without the
proxy, an MCP image server's own connections); a program that encodes a secret in a way of its own is not caught;
values shorter than 8 characters are not registered (the start says so); the shapes are the privacy check's built-in
ones; which file brought a secret into the model's context is not told (the activity timeline of the same minute
shows what was read).

## Package guard: what npm, pip, cargo and go download is checked in the proxy

Agents install packages, and an install script runs at once. A known malicious package, a release of this morning or a
name the model made up and somebody registered ("slopsquatting") ran its code in the sandbox unchecked: contained, but
with the workspace and every allowed host in reach. From this release the connection proxy tells the package and the
version of every download from **npm**, **PyPI**, **crates.io** and **Go's module proxy** and judges it before
anything is fetched (the Knostic research's R12; `docs/design/package-guard.md`):

- **Known malicious** - the version is in OSV's malicious-package advisories (`MAL-...`): **refused, with the
  advisory**. You may allow that one download in its question; never for the run, never always, never by `--ask
  allow`, never by an allow-list.
- **Younger than 14 days** (the project's own rule for pinned releases): **asked**, with the age.
- **A name the registry does not know (404), or a package whose first release is younger than 30 days**: recorded as
  a possibly hallucinated or slopsquatted name (`sandbox-ai safeguards --kind package`, the reports); its download
  is **asked** about in the modes `high` and `paranoid`.

**No package name leaves the machine for a lookup.** The malicious packages are searched in an **offline copy on this
machine** (`~/.local/share/sandbox-ai/osv-malicious`: one sorted list per ecosystem, which the proxy searches in
place - no load time, no memory of its own, a lookup in microseconds). Release dates are read from the registry's own
answers to the agent's requests as they pass; no request leaves that the agent did not make. (So that npm's answers
say dates, a client's request for the short package document goes on as one for the full document.)

- `sandbox-ai packages sync` fetches the copy from the release source and takes nothing on trust: signed by a release
  key (a namespace of its own), every list checked against its SHA-256 in the signed file and for being sorted, a
  copy older than the one here refused. `sandbox-ai update` (and its daily check) syncs it along. `sandbox-ai
  packages sync --osv` builds it on this machine from OSV's own dumps of whole ecosystems instead - unsigned, and
  `packages`, `doctor` and the start say so. **The signed copy is not published yet** (it needs the release key:
  `sandbox-ai packages build --from DUMPS --out DIR --sign KEY`, then the files as the release `osv-malicious`);
  until then `--osv` is the way to a copy, and without one the guard checks age and names only (a start that opens
  a registry says so, `sandbox-ai doctor` warns).
- `sandbox-ai packages` (status: age, entries, signature), `packages check SPEC` (a lookup here), `packages allow |
  forget | list` (the project's allow-list, kept outside every workspace), `--allow-package SPEC` (one start),
  `--no-package-guard` (off for one start; **refused in `high` and `paranoid`**).
- The questions come like every other: the app's Approvals page, the web interface and `sandbox-ai approvals` show
  the package, its version, its age and the advisory, and the command that allows it for the project.
- The decisions are a ruleset section, `"packages": {"malicious", "min_age", "min_age_days", "new_names"}`: your
  rules, the project's, the policy and the mode can tighten them, none can loosen another; an audit ruleset's section
  is recorded as what it would decide. `package_min_age_days` in `defaults.json` is your own base (0: no age check;
  the strict modes keep 14).
- Every download's record in the connection log carries `package`: ecosystem, name, version, `age_days`, the advisory.

Limits, said plainly: Git dependencies, tarball URLs, vendored packages and registry mirrors the proxy does not know
are not judged; a host whose TLS passes unopened (`--no-inspect`) is not seen; a download whose metadata the proxy did
not see in this run (a cached lockfile install, an older pip asking for PyPI's HTML index, crates.io index entries
without a publication time) is judged by the malicious list alone; Go's 404s are not recorded as unknown names (its
clients probe every prefix of an import path); the copy is as current as its last sync.

## Android debugging: an image, a preset, and smali and Frida as MCP servers

"haben wir Android-Container mit Android-Tools wie adb?" - now yes, and more than adb. Three pieces, one setup:

- **The image variant `android`** (`sandbox-ai images recipe android --from AGENT && sandbox-ai build android`): adb
  and fastboot, aapt, zipalign and apksigner from Debian's release, and - each a release file pinned by its SHA-256
  and fetched only while the image is built - **apktool 3.0.3** with its own aapt2 2.20 and its android-framework.jar
  taken out of its jar, **baksmali and smali 3.0.10**, **jadx 1.5.6** and **Frida 17.25.2**'s Python bindings, with
  `frida-server` and `frida-gadget` for **every Android ABI** (arm, arm64, x86, x86_64) in `/opt/frida/android`,
  about 140 MB, kept exactly as Frida publishes them. The versions are the ones the MCP servers use, so an agent sees
  the same tools either way. `frida-tools` is deliberately not included: its newest release with a wheel is not 14
  days old yet, the older one would have to be built with unpinned build tools, and its injected agents and 12 MB
  web UI are not reviewed - `sandbox/recipes/android/requirements.txt` says so and how to add it yourself.
- **The preset `android-debugging`** (gallery: Security analysis): the APKs read-only at `/mnt/apks` and at the MCP
  servers' `/work`, one writable folder for what is built (`/mnt/out`, the servers' `/out`), the host's adb server
  (`--allow-host-port 5037`), the four MCP servers **jadx, cfr, smali and frida**, a device as an optional value
  (`--device usb:VID:PID`, which the Board's device picker offers) and the frida-server's address as another. Its
  **ruleset asks** before anything is installed on a device, wiped, flashed, unlocked or rooted (adb install,
  uninstall, shell pm/rm/su/settings, push into the system, fastboot flash/erase/flashing, a reboot into the
  bootloader), before a script runs inside an app, and before an APK is built or signed; everything the device, the
  app and the decompilers report is untrusted.
- **Two new MCP servers in sandbox-ai-mcp** (branch `feat/android`, pending until its CI publishes the digests):
  **smali** - eleven tools around baksmali/smali 3.0.10, apktool 3.0.3 and apksigner: the DEX files and classes of an
  app, a class's smali in parts of 400 lines, a search through the smali of every class, disassemble and assemble,
  apktool decode and build (an **unsigned** APK), then zipalign and a signature with a throwaway debug key made for
  that one call and deleted with it; and **frida** - sixteen tools against the device **you** configure
  (`FRIDA_DEVICE=IP:27042`, or a USB device of an adb server at `FRIDA_ADB_SERVER`): devices, processes, apps,
  attach, a script of yours with the messages it posts, modules and exports, and - only with `FRIDA_WRITE=1` -
  spawn, resume, kill and pushing the matching frida-server.

**What an MCP server cannot do:** reach the adb server on the host that runs sandbox-ai. An MCP server's container
has no access to this host's loopback or its forwarded ports (`--allow-host-port 5037` is for the agent's own
sandbox). Give the frida server the device's own address and open exactly it: `sandbox-ai mcp set frida --allow-tcp
192.168.1.33:27042`. The README's hardware table, the help (Android: debugging an app) and the preset's notes say it
in those words.


## axross files: the MCP server axross and the preset axross-mcp-server

"add axross-mcp-server preset and add axross-mcp-server to sandbox-ai mcp server list" - axross's own MCP server
(c0decave/axross-headless-mcp, the user's project) is a catalog server now, and a preset starts an agent with it:

- **The MCP server `axross`** (sandbox-ai-mcp, branch `feat/axross-headless`, pending until its CI publishes the
  digest): axross's file tools - list, stat, read (4 MiB a call), checksum, walk, recursive checksum, grep, versions -
  on the folder mounted at its `/work` and, with `remote_open`, on the **SFTP connections saved in axross**
  (`/axross`: axross's config folder, only its profiles.json read; `/ssh`: known_hosts and the profiles' key files).
  Read-only unless `AXROSS_WRITE=1` (write, mkdir, remove, rename, copy, bulk copy, links, chmod). The folder is
  confined by descriptor (no `..`, no link out), secret files are never read, an unknown host key is refused, never
  trusted on first use, passwords come from the secret `AXROSS_PASSWORDS` (a JSON object of profile names and
  passwords). SFTP only; no scripts, remote commands, agent or HTTP transport. Network none by default; for a
  connection `sandbox-ai mcp set axross --network full --allow-tcp IP:22`. `sandbox-ai mcp catalog`, the app's MCP
  page and the web list it from the catalog; `sandbox/mcp_catalog_tools.json` knows its 23 tools.
- **The preset `axross-mcp-server`** (gallery: Development): the folder as the server's `/work` (`ro`, or `rw` with
  the value write=1 and a server added with `/work:rw`) and read-only for the agent at `/mnt/files`; axross's config
  folder and the ssh folder as optional values (left empty: the ones the server was added with); the host of a
  connection as a value for `sandbox-ai mcp set axross --allow-tcp`. Its **ruleset** lets the reads run and **asks**
  before every write, delete, rename, copy, mode change and link (on the folder and on a connection); anything else
  of the server is refused, everything it returns is untrusted.

How much of axross-headless-mcp was reviewed for the image - what runs measured, the rest of the package deleted
from it, about 11,000 of the 42,294 lines that ship read line by line - is in sandbox-ai-mcp's
`servers/axross/PROVENANCE.md`; signing it is the user's decision.

## A board or a session as one file: export and import

"An export function on the board and the sessions that exports a complete running board or a board's configuration,
self-sufficient." **`sandbox-ai board export`** writes a board or a session (running or not, of this machine or of a
host) as one file - a bundle - and **`sandbox-ai board import`** recreates on another machine (or this one after a
reinstall) everything its start needs that existed only on the first one.

- **What goes along:** the start (agent, options with what the trusted project file adds, agent arguments) and the
  app's board itself (parts, places, labels, bridges, team); every folder as a placeholder `<folder:NAME>` with its
  path as the default, asked for at the import (never its contents); the presets of yours it starts from, the MCP
  servers it names (as `mcp export` writes them, images pinned by digest; a project's own servers become yours), its
  LLM servers (without a key), rulesets (their contents), kits (their files), image variants (their extension, not the
  image), your images' records and the loop guard of your defaults. Secrets, host variables, identities and VPN
  profiles go by name only.
- **`--images`:** the MCP servers' and your images go along too (`podman save`): the bundle works offline. It is then
  a tar archive (standard library): `bundle.json` first, then `images/N.tar`. Without, one JSON document. Format:
  `{"schema": "sandbox-ai-bundle", "version": 1, "start", "board", "folders", "values", "secrets", "env", "by_name",
  "withheld", "parts", "images", ...}`. The agents' own images never go along: each machine builds them from
  sandbox-ai's signed Containerfiles, and a bundle never replaces them.
- **Never a secret's value:** no secret, token, password, login (`--copy-auth`, `--auth-file`, `--git-credentials`,
  `--git-token-file`, `--local-config` and a login file copied in are left out and named as withheld), sealed VPN
  file, cookie or HOME content; a value that looks like a credential (the privacy check's shapes, a variable named
  like a secret) is withheld as `<text:NAME>` and asked for at the import. A test exports a board that uses every
  kind of secret-bearing part with canary values and finds none of them in the file (JSON and archive). The file
  does hold the machine's paths and names: the export dialog says so.
- **An import is passed on, not yours:** what a passed-on preset may not carry is refused (a login or token read from
  a file, the internal options of a start, `--llm-traffic all`, `--vpn-bypass-*`, hidden characters, a folder that is
  no placeholder, a ruleset named by path); MCP servers are checked as `mcp import` checks them (a catalog's from that
  machine's signed catalog); archive members are data (only `bundle.json` and `images/N.tar`, regular files, sizes
  and SHA-256 checked, no path of their own, no link), and an image archive that names other images is never loaded.
  The plan comes first (`--check`: nothing written) - created, reused (the same is there), replaced, and what that
  machine lacks with the command to give it -, then, confirmed (`--yes` where nothing can ask), the parts are written
  (undone again if a later step fails) and the board is kept in `~/.config/sandbox-ai/boards/NAME.json` (`board list`,
  `board show NAME [--check]`, `board delete NAME`); it is never started. A part of the same name defined otherwise is
  refused unless renamed (`--rename KIND:OLD=NEW`) or replaced (`--replace KIND:NAME`); a folder whose default is a
  private location is used only when you give it yourself (`--map`), with a warning.
- **Hosts:** `--host HOST` exports a host's session or board (the bundle is checked as one and written here) and
  imports on a host (its plan made there, confirmed here).
- **App:** *Export…* and *Import…* on the Board (toolbar and context menu): Import shows the plan with a field for
  each folder (the bundle's path as its default) and each withheld value, *Replace the parts of the same name here*,
  then imports after asking and shows the board, not started. *Export…* on the Sandboxes page for a session of this
  machine or a host (a button and the right-click menu), with *Include images*.
- **Web interface:** *Export* in a kept start's row (the bundle downloaded), *Import a board…* above the starts (its
  plan, the folders and values to give, then Import, confirmed: `board-import`).

## Scheduled runs: sandbox-ai schedule

"Start an agent on a timetable or a trigger and get a report afterwards: nightly review, dependency updates, test
triage." **`sandbox-ai schedule`** keeps schedules whose runs are normal starts under the same rules (security mode,
network, approvals, limits, telemetry off), with the agent's one-shot mode and a report of each run.

- **When:** `--every 30m|2h|1d|1w|1h30m` (real time), `--at HH:MM` (daily) or `--at "YYYY-MM-DD HH:MM"` (once),
  `--cron "M H DOM MON DOW"` (lists, ranges, steps, names, `@daily`; day of month or day of week as cron), and/or
  `--on-push REPO` (a branch or tag of a local repository moved). Local wall-clock times across DST: a skipped time
  runs at the jump, a repeated time runs once. Runs missed while asleep: once on wake (`--missed once`, default) or
  skipped (`--missed skip`).
- **What:** `-- AGENT [OPTIONS]` as `sandbox-ai AGENT` takes it, `--workdir DIR`, the task with `--prompt`/
  `--prompt-file` put into the agent's one-shot form (`claude -p`, `codex exec`, `opencode run`, `qwen --prompt`,
  `goose run --text`, `openhands task`, `nanobot agent --message`, `letta -p`, `pi -p`, `hermes --oneshot`,
  `dsh headless`) or given in that form after the start's `--`; an agent without one is refused. `--preset NAME`
  (its first task the default task) or `--board NAME` (a board kept by `board import`) as the start.
- **Questions at night:** the schedule's `--ask off|allow|on`, default **off** (refused, nobody answers), said by
  `add`, `list` and `show`.
- **Never two at once, never forever:** a lock per schedule (a due run while one runs is skipped and noted) and a time
  limit per run (`--limit`, default 60m: `sandbox-ai stop`, then the process group).
- **Afterwards:** the history (`schedule history`, `schedule report NAME [RUN]`): why it ran, status, duration, a
  Markdown summary with the git diff stat of what the agent changed (Git on the host without any program the
  repository's configuration names) and the start's own `sandbox-ai report`. `--commit BRANCH` puts the changes on a
  branch without touching the work tree; `--push REMOTE` pushes it only to the address recorded at `add`, after the
  privacy check, and never with a credential helper, proxy, SSH command or URL rewrite of the repository's own
  configuration. `--keep-starts N` deletes older starts' HOMEs (the reports stay). A desktop notification and, when
  present, `sandbox-ai notify`'s `run-ended`/`run-failed` (a small hook point: the launcher's own end message is not
  sent twice for a scheduled run).
- **The timer:** `schedule enable|disable` installs a systemd user timer (every minute, `Persistent=true`,
  `KillMode=process`) or a LaunchAgent (`StartInterval` 60, `AbandonProcessGroup`) running `sandbox-ai schedule
  tick` - no root, no crontab; `--dry-run` shows the files. `sandbox-ai uninstall` names it in its plan and turns
  it off first (only the files sandbox-ai wrote: a unit of that name without its marker is never touched).
- **App and web:** a Schedules list on the app's Sandboxes page and the web interface's Starts page (this machine or
  a host, through `hosts run`): Add…, Edit…, Run now, Pause/Resume, Remove…, History… with each run's report, the
  timer on/off; in the app every button also on the list's right-click menu. German strings, help in English and
  German.
- **Tests:** SPEC parsing (every/at/cron, DST edges in Berlin and New York, missed runs), the lock, the time limit,
  the unit files (made, never installed in tests), a tick starting a due run, the report and history, Git without the
  repository's programs, the push's checks, and end to end through `./sandbox-ai` with a fake agent and a fake clock
  (`SANDBOX_AI_SCHEDULE_NOW`).

## Workspace checkpoints: undo everything an agent did

"B3": **`sandbox-ai checkpoint restore NAME`** puts a start's workspaces back as they were when its last start
began - every file, folder, symbolic link, permission and the project's own `.git`, so a `git reset --hard`, a
`git clean -fdx` or an `rm -rf /work/*` of the agent is undone like any other change.

- **When they are taken:** automatically when a start begins (every writable workspace; with `--checkpoint-mounts`
  or `checkpoint_mounts` the rw `--mount` folders too), every N minutes while it runs when something changed
  (`--checkpoint-every N`, `checkpoint_every`), and by hand (`sandbox-ai checkpoint RUN [--label TEXT]`, also while
  it runs). `--no-checkpoint` / `checkpoint_start: false` take none at the start.
- **Restore:** `checkpoint restore RUN|ID [--path P]... [--dry-run] [--yes]` shows what changes first (M changed,
  A added, D deleted), asks, then takes a checkpoint of the state now (kind `restore`) and puts the folders - or
  only the paths P - back; restoring that one undoes the restore. `checkpoint list|show|diff|delete`. A start that
  runs while it is restored gets a note (pause it first).
- **Limits:** per project `checkpoint_days` (30), `checkpoint_count` (50, periodic ones dropped first),
  `checkpoint_gb` (10 GiB of content); applied after each new checkpoint and by `sandbox-ai gc` (which names what it
  removed); the newest checkpoint and the start checkpoints of running runs always stay. `gc --usage` has a
  "Workspace checkpoints" part. `checkpoint_exclude` (default `node_modules`, `.venv`, `target`, `__pycache__`,
  `.pytest_cache`, `.mypy_cache`, `.ruff_cache`, `.tox`, `.gradle`, `.next`, `.parcel-cache`, `.turbo`): never
  checkpointed, never touched by a restore.
- **App:** Checkpoints… on the Sandboxes page (button and right-click menu; a start of this machine or a host, also
  one that ended): the list, Changes, Restore… (the preview, then asked: `checkpoint-restore`), Delete (asked:
  `checkpoint-delete`), Take one now with a label - every command in the background. **Web:** Checkpoints… in a
  start's row, the same. **Remote hosts:** `sandbox-ai hosts run HOST checkpoint ...`; the app and the web go
  through it. German strings, help section "Checkpoints" (EN+DE, web help exported).

**The design: a content-addressed store per project, not a git object store.** One store per project (its main
workspace) in `$XDG_STATE_HOME/sandbox-ai/checkpoints/NAME-HASH/`: `objects/AB/CDEF…` holds each file content once
by its SHA-256 (read-only), `manifests/ID.json.gz` every path of a checkpoint (type, mode, mtime, size, digest; a
link's target), `meta/ID.json` its small record; `runs/KEY.json` says which folders a start's checkpoints hold (so
`checkpoint RUN` and `restore RUN` work also for a start that was not kept). Why not git with a `GIT_DIR` outside
the workspace:

- **Correctness:** git never stores a path named `.git` - the project's own repository, the thing a destructive git
  command destroys, could not be in its checkpoint. git keeps only the executable bit (no other modes), no empty
  folders, and its `.gitignore` handling would have to be fought for untracked and ignored files.
- **Speed:** `git add -A` zlib-compresses every new blob (about 50 MB/s) and rewrites a 100k-entry index each time;
  the store copies plain bytes (or clones them) and keeps a stat cache - a file whose size, mtime, ctime and inode
  are unchanged since the last checkpoint is not read at all (ctime cannot be set back by the agent).
- **Disk:** both deduplicate by content; git would save more on text by compression, at the price above. Never hard
  links into a workspace (an agent writing in place would change the checkpoint); within the store, objects are
  written once (a temporary file linked in place: two writers of the same content store it once).
- **Clones:** a large file (from 4 MiB) is cloned where the store's file system can - `FICLONE` reflinks on btrfs
  and XFS, `fclonefileat` on APFS - and hashed from the clone (a consistent copy even while the agent writes), else
  copied with its hash taken on the way; small files are read whole into a reused buffer and written only when new.

**Safety:** checkpoints are taken and restored by the launcher on the host; the store lies in sandbox-ai's own state,
which no sandbox gets mounted (a workspace that holds it - your HOME - skips it), so the agent cannot read, change
or delete one. Every folder is opened relative to its parent with `O_NOFOLLOW` (symbolic links are stored as links,
never followed, also not on the way to a file - an agent swapping a folder for a link to `~/.ssh` while a checkpoint
runs gets nothing of it in); special files (sockets, FIFOs, devices) and mounts inside a workspace are skipped and
named. A restore checks every path of a manifest (relative, no `..`), opens every folder on the way without
following a link (a link where a folder was is replaced by the folder), writes each file beside its place, checks
its content against its digest and renames it onto it: nothing outside the folder is ever written. Not kept: owners,
extended attributes, hard links between files (restored as separate files). A file written while it was read is
kept as read, named, and read again at the next checkpoint.

**Large workspaces and the start:** the start checkpoint runs in a thread from the moment the workspaces are checked
while the start prepares everything else (MCP servers, host lookups, VPN, HOME, kits) and is waited for before the
canaries are planted and the agent runs - so no write of the agent (nor a canary) can slip into it, and a start
waits only for what is left (a progress line says so). Measured on ext4 (this machine's disk, no reflinks) with
1 GB in 100,000 files of 10 kB in 1,000 folders (`cp -a` of it: 2.9 s):

| | time |
|---|---|
| first checkpoint (every file copied once) | 7.0 s |
| next checkpoint, nothing changed | 1.4 s |
| next checkpoint, 1,000 files (1 %) changed | 1.5 s |
| diff against the first, 1 % changed | 1.0 s |
| full restore after `rm -rf` of everything (with its own checkpoint first) | 5.0 s |

The manifests of such a workspace take 4.4 MB each (gzip). The thread pool reads only files from 4 MiB on: for small
files a thread per file costs more in hand-offs than the read (35 s instead of 7 s, measured).

## Spend limits: what the model requests cost, and budgets that stop a run

"B2." The connection proxy now counts **every model request's tokens from its answer** - streamed (SSE) or not,
Anthropic's Messages API, OpenAI's Responses and Chat Completions and the APIs like them, the `--llm` servers -
including input read from and written to the cache and the output's reasoning, and **prices them**. One small line per
request goes to `spend-TIME-RUN.jsonl` in the run's log directory (no conversation, no credential; compressed by `gc`
once the run ended and removed with the other logs after `log_days`).

- **Prices:** `sandbox/prices.json` - the providers' list prices per million tokens (input, output, cache read, cache
  write for 5 minutes and an hour, long-prompt prices) with its date and source; your own in
  `~/.config/sandbox-ai/spend.json` (`sandbox-ai spend prices set MODEL in=.. out=.. cached=..`, `prices remove`). A
  model is found by its name with a date or version after it and under OpenRouter's, Bedrock's and Vertex' names for
  it - never by a guess: a model the table does not name is counted in tokens with the cost **unknown**, said so, and
  priced afterwards when you set a price. Local `--llm` servers cost 0; a Claude Pro/Max or ChatGPT plan login shows
  **subscription** (tokens counted, no price per token).
- **Budgets:** `--budget USD` per start (`-bu`; `"budget"` in your defaults and in the project's `.sandbox-ai.json`),
  and limits per day or month for a project or everything (`sandbox-ai spend limit set --project DIR --day 10`,
  `--all --month 200`). A shared limit counts the runs before the start and, within about half a minute, those running
  beside it (the launcher tells the proxy over the run's control socket).
- **80 % and 100 %:** at 80 % a desktop notification and the new phone event **`budget`** (`sandbox-ai notify`); at
  100 % the proxy refuses the run's **next** request to a provider - before it goes out, never cutting one under way -
  with a `sandbox-ai:` error in the API's own shape (HTTP 402; OpenAI's `insufficient_quota`, which clients do not
  retry); every other request with a body to such a provider (batches, embeddings, a WebSocket) is held back too.
  Local models and subscriptions go on. **`sandbox-ai spend raise RUN USD`** (the human only: the control
  socket refuses a process of the sandbox) lets it go on.
- **Where:** `sandbox-ai spend [--by run|project|agent|provider|model|day|billing] [--since 7d] [--json]`,
  `sandbox-ai spend run RUN` (cost so far, a bar per budget), a section in `sandbox-ai stats usage` and the report's
  *Model spend*; the app's System monitor (a Cost column; the chosen run's cost with a bar per budget; Raise budget…,
  also on the right-click menu) and the web interface's (the same, asked first in place). German strings, help in
  English and German.
- **Not seen:** traffic the proxy does not open (`--no-inspect`, `--no-proxy`); what other endpoints cost
  (batches, embeddings, a WebSocket: held back once a budget is used up, not priced); a provider's own discounts and
  taxes. An OAuth access token of Claude Code's (a Claude plan) counts as a subscription.

## Logins of sessions: into the login store, into a new start, and every session's login at a glance

A session that is logged in (a Claude or Codex login typed in its terminal, one it got from the host) keeps that login
in its HOME. sandbox-ai now shows it, takes it as the central login, or gives it to a new start:

- **`sandbox-ai login --status --sessions [--json] [--host HOST]`:** per running or kept session of an agent the login
  store takes (Claude Code, Codex, OpenCode, Hermes, Qwen Code, Pi): where its login came from (the central login,
  this computer's, a login file, `from session X`, none), the account as its file says (Claude: the email and
  organization of `.claude.json`'s `oauthAccount` and the subscription type; Codex: the `account_id` and the email of
  the `id_token`'s claims, decoded but not verified), subscription or API key, when the access token expires, when it
  was last refreshed, and a fingerprint (the first 8 hex characters of the SHA-256 of its tokens) - never a token. Two
  sessions with the same fingerprint share a login; one that shares the central login says so.
- **`sandbox-ai login AGENT --from-session NAME [--yes] [--replace] [--dry-run] [--expect FINGERPRINT] [--json]
  [--host HOST]`:** that session's login as the central login. The account is shown first, then asked (`--yes` does
  not ask, `--dry-run` only shows); a central login of another account, or one whose account cannot be told (an API
  key), is replaced only with `--replace`; `--expect` imports only the login that was shown. Claude takes the
  `claudeAiOauth` block and the account part of `.claude.json`, each value of its type. With `--host` the session and
  the store are that host's; the question is asked here and the host imports only the fingerprint shown. A session
  that still runs keeps its copy (a note says that its refresh can stop the central copy); a stopped Codex,
  OpenCode, Qwen Code or Pi session takes the central login's newer tokens at its next start.
- **`--auth-from-session NAME` (`-as`), a start option:** the new sandbox gets NAME's login (a resumed start keeps the
  one in its HOME). It warns once that subscription logins rotate their refresh tokens - two sandboxes refreshing one
  login outside the login store can log each other out - and names the safer way (import it as the central login).
  Decided variant: at the end of the run a refresh goes back into NAME's kept HOME only when NAME does not run then
  (checked under its session lock, so a resume cannot start meanwhile), NAME's login is still the one copied in, and
  the refreshed login is of the same account (Codex: the same `account_id`; OpenCode and Pi: the same providers and
  accounts; Qwen Code: the same resource; Claude: Anthropic names the same account for both, asked from the host). A
  running or paused session's HOME is never written, and the central store never gets it. A project file may not set
  the option (a session is this machine's); presets, MCP servers and board bundles refuse or withhold it.
- **The login file is untrusted:** it is read through session_inspect's readers (no link followed anywhere on the way,
  regular files only - a FIFO never blocks), at most 1 MiB (`.claude.json` 64 MiB), checked with the login store's

  tests look for one everywhere).

## Update modes: sandbox-ai update mode off|notify|download|auto

One setting per installation says what it does by itself about new releases:
`sandbox-ai update mode [off|notify|download|auto] [--at HH:MM[-HH:MM]] [--source URL]` (kept as `update_mode`,
`update_window`, `update_source` in `defaults.json`; `defaults set` points to it). Alone it shows the mode, the last
check and its result and the next check (`--json` for programs).

- **notify** (the default): a check once a day; a newer release signed by a trusted key is announced once - a desktop
  notification, the app's status line, one line on the command line (at most once a day, on standard error, never
  with `--json` or in a pipe) and the new notify event `update` (`sandbox-ai notify add ... --events update`).
- **download**: also downloads it and checks it in full in the background - `install.sh --fetch DIR` (new): the bundle,
  `SHA256SUMS` and a signature by a trusted key required (never unsigned, whatever `--allow-unsigned` says), never
  older than the installed version. `sandbox-ai update --apply` (or the app's Install now…) installs it through
  `install.sh --from BUNDLE --verify`, which checks it again; nothing is switched before.
- **auto**: also installs it, in its window (default 03:00-05:00 local time) and only while no sandbox, session, MCP
  server or scheduled run of this installation runs or is due within the hour (paused and kept ones are fine);
  otherwise it waits and says until when. Afterwards a notification with the old and the new version and the
  release notes' link. A scheduled install takes nothing from PyPI (`--no-app-deps`).
- **off**: nothing is checked unless asked.
- **Rollback**: `sandbox-ai update --rollback` (the app's Roll back…) switches `current/` back to the version kept in
  `versions/` (install.sh keeps the last 2); `download` and `auto` leave the version rolled back from alone. Like
  `--apply` it refuses while something runs and names it; `--while-running` goes ahead.
- **The timer**: one beside the schedules' timer, made by the same functions (`schedule.py`, now with a timer
  description): `sandbox-ai-update`, a systemd user timer or a LaunchAgent, every 15 minutes, as the user who set the
  mode; it runs the installation's `current/` (an update never leaves it pointing at a removed version). `update mode
  off` and `sandbox-ai uninstall` remove it (only files sandbox-ai wrote); `sandbox-ai doctor` reports the mode, the
  timer and the last check (System: Updates).
- **Copies that do not update themselves** (pip, pipx, the AppImage, the `.pyz`, the macOS app, a git checkout): notify
  works and names the command (`pipx upgrade sandbox-ai-app`, download the new file, `git pull` and `./install.sh
  --from .`); download and auto are refused with that reason. A **system installation** is root's to update: each user
  gets notify (with `sudo sandbox-ai update` as the way); no root timer is made.
- **Other hosts**: `sandbox-ai hosts update NAME --mode MODE [--at WINDOW]` sets a host's own mode over SSH (its timer
  as the SSH user); `hosts list`, the app's Hosts page (Update mode…, also on the right-click menu) and the web
  interface's Hosts page show each host's mode beside its version.
- **App**: Settings › Updates - the mode and its window (Set… asks first), the last check and its result, Check now,
  Install now… and Roll back… (asked first; what runs is named and asked about once more); afterwards "Restart the
  app" is offered, the app never restarts by itself. At its start the app follows the mode: off checks nothing, a
  newer release the last check found is shown at once, a check runs only when the last is a day old - always in the
  background.
- **Web interface**: the Doctor page shows each host's update mode, the last check and a newer version; a change is a
  confirmed POST (`/api/hosts/H/update-mode`, `update-mode`).
- `update --check` keeps what it found as the last check; `update` and `update --check` use `update_source` when it is
  set. Releases mark no pre-releases (`publish_release.py` publishes every release as stable), so there is no
  `--channel`.

- **A quieter app: Show explanations** (Settings > Appearance, off by default, applied at once): the pages' intro lines ("What your sandboxes ask…"), the hints below forms and tables ("A request waits up to 60 seconds…") and the "how this works" paragraphs of every page, dialog and wizard page show only with it on; warnings, errors, status lines, empty lists and what must be read to act safely (a risky choice, a device's risk, what Finish trusts, text an agent wrote) always show, and the (?) buttons and tooltips still explain. The Approvals page folds why a question is asked, a call's arguments in full and what the run's log knows of it into one **Details** box below the answers - folded at first and as you leave it; it opens by itself for a question that cannot be answered safely from its line (arguments shortened there, a write's diff, a decoy file touched).
## Skills, subagents, commands and plugins for a running sandbox: `kits attach`, `plugins attach`

- **What failed:** a start's kits reached its sandbox as a read-only snapshot copied at the start, so a skill added to
  a kit afterwards (`kits add-skill`, `kits host-import`, the Kits page) never reached a running sandbox ("a session
  running now keeps its copy until it ends"), and a kind the kits had nothing of (Claude's subagents and commands,
  say) had no read-only folder at all that anything could be put into while it ran. Plugins were enabled only at a
  start.
- **Every kind of the agent's layout is mounted now**, an empty read-only folder where the kits have none (Podman and
  Bubblewrap alike: the staged folders of the run on this host, bind-mounted); run.json says where (`kits_live`). Not
  with `--no-default-kit` and no `--kit`: the HOME's own folders stay the agent's then. So an agent no longer writes
  subagents or commands of its own into its HOME's folders (`~/.claude/agents`, `~/.claude/commands`, OpenCode's
  `agents/` and `commands/`, Codex's `~/.codex/prompts`) where the kits had none - as with skills before; the
  project's own (`/work/.claude/agents`, ...) stay writable.
- **`sandbox-ai kits attach START (KIT | --skill DIR | --command FILE | --agent-file FILE) [--keep] [--restart]`**
  copies into them on the host, with the checks of a start (the kit read as a start reads it, nothing below an entry
  followed as a symlink, a link in a folder a sandbox can write refused, the size limits over the whole snapshot, no

  neither change nor remove it. A kit's hooks, memory and plugins are not given while it runs. `--keep`: a kit into

- **`sandbox-ai kits restart-agent START`** (and `--restart`): the agent started again in its tmux window inside the
  running sandbox, through its shell relay, from the script the start wrote (`/sandbox/session/agent-restart.sh`: the
  agent's continue flags); the sandbox, its network, MCP servers and kits stay. Only when asked.
- **What each agent needs** is in every answer (`reload`: by itself, a command to type, a restart of the agent, a
  restart of the sandbox), from each agent's docs or source (2026-11-18): Claude Code watches its skills and

- **App:** the Kits page's **Give to a running sandbox…** (a kit, or a skill or plugin chosen in What it brings, to a
  running start of this machine or a host), the Sandboxes page's **Add skills/plugins…** and **Remove
  skills/plugins…** (also on the right click), each asked first; the agent's restart inside the sandbox is offered

## Supply-chain hygiene: hidden text, pinned MCP tools, audit mode, ready-made rulesets, the workspace review, --hide

From the research on Knostic (docs: research-llm/knostic-research-2026-11.md), its two confirmed gaps closed and the
top recommendations built - all local and deterministic, nothing sent to a vendor, the human decides.

- **The hidden-text checker** (`sandbox/lint.py`): Unicode tag characters spelling out hidden ASCII (decoded and
  shown), zero-width, bidirectional and control characters, variation-selector runs (GlassWorm), instruction phrasing
  aimed at the model, credential paths, `curl | sh`, bare-IP URLs, long base64; emoji sequences are no finding.
  `kits add-skill`, `kits host-import`, `kits attach` and `plugins attach` refuse a copy with findings unless
  `--allow-findings` (the app asks whether to give it anyway, the findings shown; the web has a box) (the research's probe
  P1 - a skill with 39 invisible tag characters imported silently - is refused now); `kits host-list` and
  `host-show` count and show them; `sandbox-ai plugins` names a plugin with findings when it installs or updates it;
  the workspace's agent instruction files (`CLAUDE.md`, `AGENTS.md`, `.cursorrules`,
  `.github/copilot-instructions.md`, `.cursor/rules/`, `.claude/skills/` ...) are checked at every start - a warning
  before the agent reads them and a safeguard record of the new kind `hidden-text`; invisible and bidi characters in
  what a push publishes are a privacy warning (`hidden-unicode`).
- **MCP tool definitions pinned per project** (`sandbox/mcp_pins.py`, `runtime.McpGateway.vet_tools`): the run's
  relay compares every `tools/list` with the pin; a new or changed tool, or a description with hidden-text findings,
  is a question of the new kind `mcp-tools` with the definitions before and after. Allowed always, the list is
  pinned; denied or unanswered, those tools leave the list and their calls are refused. A server's first list is
  pinned after the run. `sandbox-ai mcp tools [NAME] [--forget]`. The research's second gap (descriptions passed
  through unchanged, never pinned) is closed.
- **Audit mode for rulesets**: `"mode": "audit"` records what a ruleset would decide (`"audit"` in `tools.jsonl`,
  `mcp-calls.jsonl` and the connection log) and decides nothing; `sandbox-ai rules audit` sums the hits up.
- **Ready-made rulesets**, opt-in with `--rules builtin:NAME`: `github-persistence` (GitHub writes that outlive a
  revoked token: keys, webhooks, workflow files, Actions secrets, collaborators, installations, branch protection),
  `destructive` (recursive `rm` outside `/tmp`, force pushes, hard resets, `DROP`/`TRUNCATE`, `terraform destroy`,
  `kubectl delete`, prunes, `mkfs`, `dd of=/dev/`), `mcp-no-credentials` (a credential in any MCP argument) and
  `secret-files` (reading `.env*`, keys, cloud credentials); every rule asks. `sandbox-ai rules builtin [NAME
  --audit]`. Rules may name `"*"` under `"args"`: some value at any depth.
- **The workspace review after each run** (`sandbox/workspace_review.py`): Git hooks and configuration, `.vscode`,
  `.idea`, `.devcontainer`, `.envrc`, `.claude`, `.mcp.json`, `.cursor`, `.codex`, `.gemini`, `package.json`,
  `Makefile`, `.pre-commit-config.yaml`, `.husky`, CI workflows and the instruction files are recorded at the start;
  every change is named after the run with its diff and the checker's findings (a warning, the safeguard kind
  `workspace-review`, `sandbox-ai workspace review`); nothing is reverted. Such files in what a push publishes are a
  privacy warning (`host-trusted-file`), so the push asks first.
- **`--hide GLOB`** (repeatable; the project file's options and the Board too): an empty read-only file or folder is
  mounted over each workspace file a glob matches at the start (Podman and Bubblewrap); `--dry-run` lists them; a
  symlink is never hidden and a file Git tracks is named; planned before the canaries, so a canary `.env` is never
  hidden.
- Items 7-8 of the research (secret-leak detection in outgoing requests, a package guard in the proxy) are designed
  in `docs/design/egress-dlp.md` and `docs/design/package-guard.md`.

## Supply-chain hygiene, the gaps closed: Keep or Restore, tool pins in the app, late answers, audit without side effects

What the Knostic follow-up left open, closed - CLI, app and web alike:

- **The workspace review, per file: Keep or Restore.** `sandbox-ai workspace review RUN --keep PATH` records that a
  change is wanted; `--restore PATH --yes` puts the file back as it was at the start (an added one removed, a link made
  again). The state at the start is kept by the launcher in sandbox-ai's own state folder
  (`~/.local/state/sandbox-ai/workspace-review/`), never read from the log folder, which the sandbox's proxy writes (a
  line forged there restores nothing); only text files of at most 256 KiB have one - a binary or larger file is Keep
  only, and says why. A file changed again since the review is not touched, nothing is written through a link on the
  way. `--all` lists every project's runs with their log folders. App: Activity > Workspace review (the diff and the
  findings below, Keep, Restore… asked first, the tab counting what is open); web: the Workspace review page.
- **MCP tool pins in the app and the web.** `sandbox-ai mcp tools` now says whether the list a server gave last differs
  from its pin (the relay notes every list it sees, the host keeps the last one after the run), `--repin` pins that
  list (refused when the hidden-text checker finds something in it), `--all` lists every project's pins. App: Activity
  > MCP tool pins (Definitions, Re-pin…, Forget…, asked first; right-click mirrors the buttons); web: the MCP tool pins
  page.
- **A late answer to an `mcp-tools` question brings the tools back.** The question times out, the changed tools leave
  the list; allowed later (the Approvals page, `sandbox-ai approvals allow ID`), the relay puts them back - at once
  with `notifications/tools/list_changed` to each connection whose server said its list may change
  (`tools.listChanged`), else at the agent's next `tools/list`. A late deny keeps them out.
- **Audit rulesets have no side effects.** An audit ruleset never switches the agent's tool hooks on and never refuses
  OpenHands or nanobot; its tool rules are recorded beside an enforcing ruleset's (the start says when they record
  nothing). The proxy reads a request body only for an enforcing rule: an audit body rule is matched without it,
  recorded with `"body": "not read"`, counted by `sandbox-ai rules audit`.
- **`--hide` holds for a directory added during the run.** The run records its globs; `sandbox-ai workspace add` hides
  what they match there before the sandbox sees the folder (the helper mounts the clone in a mount namespace of its
  own, the blanks over the matches, and attaches a recursive clone of that); `workspace remove` unmounts them first.
  A single file added that a glob matches is added with a warning (you chose it).
- **`sandbox-ai scan PATH...`**: the hidden-text checker on its own, for a skill, plugin or repository before an agent
  reads it - exit 0 without findings, 1 with findings, 2 for a path it cannot read; `--json`.

## Budgets count what they could not see: streamed Chat Completions and models without a price

Review 3x-1 left open (item 16, "requests the meter cannot count"): a request whose answer carried no usage was
never counted, and so never held back by a budget. Decided (the coordinator, the user away), only on a run with a
budget (`--budget`, `spend limit set`); without one nothing changes:

- **Streamed Chat Completions are asked for their usage:** OpenAI's API (and the ones like it) says a streamed
  answer's usage only when the request asks (`stream_options.include_usage`), and the agent chooses the body. The
  proxy now adds `"stream_options": {"include_usage": true}` to each streamed Chat Completions request without it -
  in front of the agent's bytes, nothing else of the body changed (with other stream options of the agent's, or
  `include_usage` false, they are kept and it is set true). The connection log marks such a request
  `spend_include_usage`. The agent then also gets the stream's last event, with the usage and no choices.
- **A model without a price is counted at a fallback price:** the table's highest input and output prices (now USD
  20 in / USD 120 out per million tokens; a price of yours above them raises it) instead of "unknown" - an unknown
  model is no way around a budget. The spend log says it once per model (`"event": "fallback"`, the model and the
  price), the launcher tells it as a budget notification (desktop, phone channels with `budget`), and `spend`,
  `spend run`, the app's System monitor and the web interface's say how many requests, at which price, for which
  model. A price set later (`spend prices set`) prices them at that price.
- Left as it was: batch and background requests (their answer comes later, by GET) are still not priced, only held
  back once a budget is used up; a request body the proxy cannot read (compressed, larger than 32 MiB) goes as it
  came, without the question.

  wrote at once.

  left content no checkpoint holds, which no prune and no `sandbox-ai gc` removed: the next prune sweeps it now.
- `sandbox-ai gc` forgets a start's record of its checkpoint folders a month after its last checkpoint went (one
  was kept per start for good).
- Restoring a path whose folders the agent removed puts those folders back with their modes and times (they came
  back 0700).
- A month's spend limit counts every spend log of the month: a spend log no longer goes with the other logs after
  `log_days` while its month goes on (with `log_days` 7 a month's limit saw a week).
- Scheduled runs: a run killed mid-way (the machine shut down, the session ended) is in the history after the next

- App: the Schedules box and the phone channels of a host whose sandbox-ai predates them say "update it" instead of
  "unknown command 'schedule'".

### Review 3x-1 (security)

Everything since 0.1.98 read as whoever a feature does not trust would use it - an agent that writes its workspace
and the workspace's `.git`, a bundle someone passes on, a remote host, a model server
(docs/reviews/final-review-3x-1.md: 21 findings, 17 fixed, 4 left with why).

- **A scheduled run's Git on the host reads nothing of the agent's making.** `schedule --push` refused a workspace
  whose `.git/config` names a credential helper or a URL rewrite - but not `.git/config.worktree`, which Git reads
  too: a helper written there ran on the host at the next unattended push, a rewrite sent the branch elsewhere. The
  push now runs from a repository of sandbox-ai's own that only borrows the workspace's objects: your Git
  configuration counts, the workspace's never.
- **The summary of what a run changed never reads through a link.** The snapshot before and after a run gave the
  files' paths to `git hash-object`, which follows a link on the way to a path: a folder the agent replaced by a
  link to `~/.ssh` put your key into the workspace's `.git/objects`, where the next run read it. sandbox-ai reads the
  work tree itself now, every folder opened without following a link. A `.git` that leads outside the workspace (a
  linked worktree, a submodule, a link the agent made) gets no summary, commit or push: nothing is written into
  another repository of this machine.
- **`board import --images` loads an image only as the image of a part of the bundle.** Any archive of a bundle
  was loaded under whatever reference its entry said - `localhost/claude-sandbox:latest` too, the image every later
  start of Claude Code runs. Now only an MCP server's image by its pinned reference or your image by its record,
  never under a name of sandbox-ai's own images; `mcp image-load` (mcp copy --copy-image) the same.
- **`checkpoint restore` restores what the agent made a FIFO or locked.** A path that is a FIFO or socket now, or a
  folder its owner may no longer read (`chmod 000`), was "skipped" by the checkpoint a restore takes first - and so
  left as it was, without a word: an agent kept `.git` or `src` out of the undo by making a FIFO of that name. Only
  what the restored checkpoint did not hold stays as it is; a locked folder is restored as its owner's and gets
  the checkpoint's permissions back.
- **A schedule's board and `board show NAME` are the board kept here**, never a file of that name in the current
  folder (a workspace the agent writes): `schedule run-now` typed there started the run with that file's options.
- **Spend: every counted request asks for an answer the proxy can read.** With `Accept-Encoding: br` no request of
  a run was counted and no budget ever used up. A Claude-plan token beside another credential (a key in the query,
  a second Authorization) is billed per token, not "subscription".
- **Bundles:** a sparse archive member is refused (a few KiB became GiB in `/var/tmp` at `--check` already); a
  bundle's start sets no `--mcp-env` that changes what code runs in an MCP server (LD_PRELOAD, NODE_OPTIONS ...), as
  a passed-on preset may not; a folder's default with `:rw` after it is still a private location. The plan of an
  import says where an LLM server of the bundle sends the model requests (its address) and what an MCP server it
  brings runs (its image or command).
- **What a schedule runs on the host is never looked for in its workspace.** The timer keeps the PATH `schedule
  enable` was typed with; with a project's activated virtualenv or `node_modules/.bin` in it, a `git` the agent put
  there ran on the host at the next tick. Relative entries and the workspace's folders are left out of the PATH of
  a scheduled run's host-side programs.
- Smaller: a mode is never put back through a link swapped in during a restore; a file name cannot end the code
  block of a run's summary; a run that deleted a file is committed in a SHA-256 repository too.
- Left open, with why: requests whose answer carries no usage (Chat Completions streamed without
  `stream_options.include_usage`, batches, a model without a price) are not counted against a budget; a file that
  cannot fit ends a checkpoint (an agent's sparse file: said at every start); Letta Code's project hooks are looked
  for at its start only; a host that answers what the agent sends it can write a made-up cost into the spend log
  (a shared limit is used up, no money).

### Security review (sandbox isolation) A

The local channels and credentials of a passive review of a running sandbox (`sandbox-security-review.md`: SAI-08,
-12, -14, -15, -18, -19, -21, -22, -23, -24, -26), each checked against the code first
(docs/reviews/security-review-fixes-A.md: 11 findings, 8 right, 2 partly, 1 mostly not; 6 fixed, 3 fixed in part, 2
left with a design). One fact is behind most of them: the agent and every command it runs are one user in one
sandbox.

- **The terminal relays' sockets cannot be replaced from inside (SAI-14).** `sandbox-ai attach` and `shell`
  connected to `tmux/attach.sock` and `tmux/shell.sock`, in a folder the sandbox writes: a program there could end a
  relay, bind its own socket under the name, and take your keys or your command - and show whatever it liked. The
  supervisor now binds both sockets before the sandbox starts, in `tmux/relay`, read-only inside it, and hands them
  to the relays as open descriptors; the clients take the place from the session's record and never fall back. A
  session started before keeps running where it was.
- **What the sandbox writes passes a filter before your terminal (SAI-08).** attach and shell were byte pipes into
  your terminal's parser. Text, colours and the drawing sequences pass; a question for your clipboard or window
  title, titles, hyperlinks, notifications, the next tab's directory, file transfers, printer and window operations
  and every DCS/APC/PM/SOS string are dropped; the command says when the sandbox asked for your clipboard.
  `SANDBOX_AI_TERMINAL_FILTER=strict` (no question at all, no clipboard text) or `off`; output into a file or pipe is
  unchanged.
- **`runtime.py --untrusted -- COMMAND`: a command without the agent's own (SAI-18, SAI-21).** In the sandbox, a
  test suite or install script run this way is confined by the kernel (Landlock) for good: no access to the agents'
  logins, transcripts and settings nor to the credentials in HOME and to `/sandbox`, HOME read-only, no way into
  other processes' environment and memory, an environment without the run's secrets, and - where the kernel has the
  right - no connection to tmux, the hooks or the MCP relays. Not run when it cannot be confined. Every agent's
  sandbox-ai skill tells it to use it for code it cannot vouch for; that an agent's every command goes through it is
  not enforced yet (the report says what that takes).
- **"Allow once" is the asking connection's (SAI-15).** It opened the address and port for 30 seconds to every
  connection of the sandbox. With the connection proxy only the connections that waited for that question pass on
  its answer; any other asks for itself.
- **A login's callback goes to the socket you were asked about (SAI-26).** The supervisor reached the agent's login
  server by its port: a program listening on the port's other loopback address, or taking the port afterwards, got
  the authorization code. Two processes listening - delivered to neither; another socket than at your "allow" - not
  delivered; the answer and the record name the process.
- **An MCP server's rules hold for everything it does (SAI-23).** Only `tools/call` was judged: a ruleset that
  allowed two tools still let every resource be read. `resources/read`, `prompts/get`, `completion/complete` and
  any other request that acts are judged under their method's name. **If your ruleset's default for `mcp` is `deny`
  or `ask`, allow the resources and prompts you use by name** (`"tool": "resources/read"`).
- **Services the sandbox reaches are bounded (SAI-12):** the proxy serves 512 connections at once, the hook server
  64 messages, the relays 16 terminals and 32 shells; one more is refused before anything is made for it.
- **Hooks (SAI-22):** the hook socket is the agent's user's alone (it was open to every user of the sandbox), a
  peer of another user is refused unread and reported as a safeguard, and a tool question names the process that
  asked.
- Checked and unchanged: the agent's display (`--gui`, `--gui-vnc`) never shares a clipboard; only the browser's
  own display does, while you tick *Share the clipboard* (SAI-24).
- Left open, with the design in the report: the agent's login and state for commands not run with `--untrusted`
  (SAI-18), its tmux for them (SAI-21), a hook or MCP request made by a command instead of the agent (SAI-22,
  SAI-23), a listener the agent itself opens on the sandbox's loopback (SAI-19), a start in the foreground, whose
  terminal is Podman's (SAI-08). Not run here: a real start under Podman and Firejail (none in the sandbox this was
  made in) - `tests/test_agent_sandbox_live.py` with `--agent-live` before a release.
- `sandbox-ai doctor` has a line "Landlock (--untrusted)": what the host's kernel, which every sandbox shares, keeps
  such a command from, and what to do where it has no Landlock.
- Tests: core, CI's four parts, 19377 passed, 339 skipped (3280, 4467, 2366 and 9264); 206 of them new
  (`tests/test_security_review_*.py`), 16 contracts; the app's tests around terminals, approvals, the login callback
  and the doctor 129 passed, 21 skipped (the app itself is unchanged).


### Security review (sandbox isolation) B

Kernel, policy and filesystem: the findings SAI-01 to -07, -09 to -11, -13, -16, -17, -20 and -25 of the passive
review of a running 0.1.99 sandbox, each checked against the code first (`docs/reviews/security-review-fixes-B.md`:

- **sandbox-ai's own system call filters** (SAI-03, -13, -16, -20). Firejail's `--seccomp` is a list of calls its
  release refuses; the container around it had no filter. Measured in a running sandbox: `io_uring_setup` reached
  the kernel, `unshare -U` made a user namespace, and sockets of the families `AF_VSOCK`, `AF_ALG` and RDS could be

  asks the kernel whether they hold and starts nothing otherwise. Firejail also gets `--restrict-namespaces` and

  namespace before, but could map nothing into it), sockets of other families and calls newer than Linux 6.17
  fail with the filter's error. `--nested-containers` keeps namespaces, mounting, packet sockets and every
  netlink protocol. `SANDBOX_AI_SYSCALL_FILTER=off` starts once as before 0.1.121 (a warning says so; refused in
  `high` and `paranoid`). The agents' skill tells them what these errors are.
- **Every host folder `nosuid`** (SAI-06), not only with `--nested-containers`; the guard reads the flags inside
  Firejail and, in `high` and `paranoid`, starts nothing without them.
- **Firejail's folder in the agent's HOME** (SAI-11) is made by the supervisor before Firejail starts (root's,
  0700, no link followed, what a run left under the name removed) and hidden in the sandbox. Firejail is started
  with `--noprofile` as before, so nothing was read there; its version is in the manifest.
- **The disk** (SAI-25): the supervisor watches the disks behind what a run writes and behind its records; a
  safeguard warning below 256 MiB, and in `high` and `paranoid` the run is ended at 512 MiB. A watch, not a quota:

- **AppArmor, SELinux** (SAI-02): the administrator's policy key `lsm` (`{"apparmor": "PROFILE"}` or

  it. Without it sandboxes stay unconfined by them, which doctor and a strict start say.
- **The connection proxy** (SAI-10) drops its bounding set as well, marks itself not dumpable, checks what the
  kernel says of it and installs the sandbox's filter on itself; the supervisor checks it again.
- **The run's manifest** (SAI-01, -07, -09): `isolation.json` in the log directory - kernel settings, capability
  sets and labels of supervisor and proxy, ID maps, Firejail's version and options, each filter with its SHA-256,

- **The HTML report** (SAI-17) carries its own Content-Security-Policy (nothing loaded, no script, no form); its

## Adding an MCP server never ends a running session; a full file system is named, not assumed

User reports 2026-11-20 (a Codex session that ran 28 hours): "sollte mcp server hinzufügen ... crash" - its terminal
said "has ended (exit status 143)" after its logs could not be written (No space left on device) and binwalk's
container could not start (Podman exit status 125); then adding radare2 said "--mount /work=/work:rw: /work is not
there and cannot be created". What could end a session while a server is added: a restart that stopped it first and
then failed (`mcp attach NAME START --restart`, the app's Attach with a restart, `resume START --restart` - which the
app offers after every live attach for Codex and OpenCode), the disk watch of the modes `high` and `paranoid` (it ends
a run below 512 MiB), and a stop by hand. A server's own container that cannot start ends only that connection.

- **A restart is checked before the stop**: the new start's MCP servers, the launcher's own checks of its options (an
  image that is not there, a server's folder, the policy) and room on the file systems it writes (its folder, the run
  directories and Podman's run directory under `XDG_RUNTIME_DIR`, sandbox-ai's state, Podman's image store: 256 MiB
  and 2000 inodes each). One that would fail is refused - "web was not restarted (it runs on as it was): ..." - and the
  session goes on. One that fails after the stop anyway says so: stopped for what, the start's own error (Podman's
  line; "no space left on device" named as a full file system), and `sandbox-ai resume NAME`.
- **An end on purpose says by what**: a stop records what stopped the run (`stopped.json` in the session's folder);
  the terminal attached to it says "has ended (exit status 143: stopped by sandbox-ai mcp attach radare2 web --restart
  (to start it again with the MCP server radare2))", not a bare 143.
- **`mcp add` refuses a pull without room** before it starts: Podman's image store needs about three times the size of
  the server's rootfs archive in the catalog (1 GiB when it names none) and 256 MiB more for the running starts; the
  refusal names the file system, its free bytes and inodes and the size needed, and points to `sandbox-ai gc --check`
  (the app: Storage). A pull that filled the disk took the room the running sessions write their logs into.
- **The file system is named, never assumed**: "the log processes.jsonl cannot be written (No space left on device;
  the disk is full: free space on the host)" was said for any ENOSPC - from a tmpfs, a quota or inodes running out as

  one, inodes used up said so); the connection log's warning too.
- **An MCP server's container that cannot start (125)**: its record says Podman's own error line and, for "no space
  left on device", the likely cause (Podman's image store or run directory full, or out of inodes) with what frees
