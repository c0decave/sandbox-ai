## New in the sandbox, the LLM relay and the images

**The LLM traffic log: what an agent and its model exchange.** For every request to the `--llm` server (OpenCode and
LM Studio, say) the connection proxy now records the request as it went to the server - messages, system part, tools,
tool calls and their results, every parameter - with what the relay changed of it (sampling parameters, `max_tokens`
as a ceiling, the loop guard's note and `tool_choice: none`, each with its old value and why), and the answer put
together from its stream: text, reasoning, tool calls with their arguments, finish reason and tokens, for OpenAI chat
completions, the Responses API and Anthropic Messages, streamed or not, gzip too; with status, time to the first byte
and in all, sizes and the loop guard's events. One record per request in `llm-traffic-TIME-RUN.jsonl` beside the
connection log (0600, written by the supervisor from what the proxy hands over a pipe, so a request never waits for
it; rotated at 64 MiB with four older parts per run, the oldest runs' gone beyond 2 GiB per log directory). No request
header is kept; credentials are redacted as in the connection log, also inside JSON in a tool call's arguments, and the
proxy's own keys by value. `--llm-traffic llm|all|off` (`-lt`; `llm_traffic` in the defaults file, the web's and the
app's defaults too): by default the `--llm` server's requests, with `all` also the agent's cloud provider's model
requests after TLS inspection - the start says so, and a project file cannot ask for it; `--llm-traffic-limit MIB`
(`-ll`, 1 to 64, default 4) bounds one record: a larger one has its long texts cut, then its oldest messages, and says
`"truncated"`. `sandbox-ai llm traffic [RUN|--session NAME]` shows each request as a readable chat of what is new
since the request of its conversation before it (told by digests of the messages as the agent sent them, so the loop
guard's note does not count) and its answer; `--full`, `--request N`, `--follow`, `--tail N`, `--grep TEXT`, `--json`,
`--summary` (one line per request), `--markdown` (a report), `--runs`. `sandbox-ai report --llm-traffic` adds a section
with every request's model, status, time, tokens, finish reason, new messages, tool calls and loop-guard marks - never
the conversation. The app's new page Monitoring › LLM traffic: a run or session, its requests (time, model, tokens,
time taken, status, new messages, loop guard), the request as a chat with tool calls, results, reasoning and the
system part folded, New in this request, the parameters with the relay's changes marked, the raw record, search across
the run, export as Markdown or JSON, follow, Open in a window ([x] and Esc); read in the background, long texts cut on
the screen; English and German, help and its tour. The log holds the conversations themselves: README, help and the
start say so. Tests first: tests/test_llm_traffic.py (the answer from each API's stream, tool calls split over chunks,
usage at the end, answers not streamed, gzip, NDJSON, error pages, huge bodies, redaction, rotation, the relay's
changes, the proxy end to end, the options, the command), the contracts of the new runtime and launcher functions,
tests/test_report.py, the app's tests/test_traffic_page.py.

**sandbox-ai's own Containerfiles for services:** `sandbox-ai images build-image NAME --builtin TEMPLATE` builds a
Containerfile that comes with sandbox-ai (`sandbox/service-images/TEMPLATE`, its folder the build context) exactly as
one of yours: every `FROM` pulled once and pinned by its digest, the result recorded by its image ID and marked
UNCHECKED, `RUN` steps without network. The first, `showcase-web`, is nginx 1.28.0 (`docker.io/library/nginx:1.28.0-alpine`,
released 2025-04-23) set up to run as a service can: user 101, port 8080, its pid and temporary files in `/tmp`, none
of the image's entry point scripts, a page of its own at `/` and `/app/` passed to `127.0.0.1:8000`.

**The image recipe `django`:** Django 5.2.18 LTS and psycopg 3.3.6 (pure Python, on Debian's libpq5) with asgiref
3.13.0, sqlparse 0.6.0 and typing-extensions 4.16.0 in `/opt/django/venv`, from `sandbox/recipes/django/requirements.txt`:
every wheel pinned by its version and SHA-256 and installed with `pip --require-hashes --no-deps --only-binary :all:`
(no source build, nothing else). TypeScript 6.0.3 from `sandbox/recipes/django/package-lock.json` (its SHA-512,

**No PostgreSQL or design MCP server yet.** Neither of sandbox-ai's MCP catalogs (sandbox-ai-mcp, axross-mcp-hub) has
a reviewed one, so `showcase-full-stack` names none and says so; the agent uses psql, Django and curl. Candidates need

The images are built by CI and on your machine (`sandbox-ai build django`, `images build-image`); the tests check the

**`--allow-domain DOMAIN` (`-ad`): a domain and every name below it.** `--allow-domain example.com` is exactly
`--allow-host example.com --allow-host '*.example.com'`, turned into those two in one place right after the options
are read, so the firewall, the DNS stub, the proxy, the plan and `net show` see only them (and show them). It has the
wildcard's checks: a public suffix (`com`, `co.uk`) or a hosting service (`github.io`, a name below one) is refused,
as is a run with `--ask off` or real DNS; the value is lower-cased, in ASCII (`xn--` for another script), and
`*.example.com`, `.example.com` and `example.com.` name `example.com` too. It is taken wherever `--allow-host` is: the
command line, a project file, a preset, `sandbox-ai net allow` and `revoke` during the run (`--keep` writes
`--allow-domain DOMAIN` into the project file), the app (the network part on the Board and its inspector, the Start
page, the wizard, the network dialog of a running sandbox). The security modes high and paranoid refuse it by its
name, and a policy that forbids `--allow-host` forbids it too (`tests/test_allow_domain.py`).

**A browser of the sandbox's own: `--browser [chromium|firefox]` (`-bw`).** A browser in a container of its own beside
the agent, in the sandbox's Podman pod, on the agent's network: the firewall and allow-list, approvals for unknown
hosts, the kill switch, the VPN or Tor, the connection proxy with its TLS inspection (the run's CA trusted in
Chromium's NSS database or through Firefox's policies), the logs and reports. Chromium when no kind is given, or
Firefox ESR. Its image, once: `sandbox-ai build browser` (`sandbox/Containerfile.browser`: Debian's chromium,
firefox-esr, Xvfb, x11vnc and certutil; the Debian base pulled once and pinned by its digest, the image labelled with
it; the runtime `sandbox/browser_runtime.py` mounted read-only at every start). It starts like a service - created,
initialised, proven to be in the pod's user namespace and behind the VPN's kill switch, started only once the
supervisor's firewall and proxy are up - as the pod's root without capabilities, with a read-only root.

- **Who drives it** (`--browser-control`, `-bc`): `human` (the default) - only you; there is no DevTools port and the
  agent reaches nothing of it. `agent` - the agent, through Chrome's DevTools Protocol at `http://127.0.0.1:9222` in
  the pod (`SANDBOX_AI_BROWSER_CDP`; Playwright `connect_over_cdp`, or a Playwright MCP server with
  `--cdp-endpoint`), and the agent starts once that port answers. `both` - you and the agent. Chromium only for the
  agent: Firefox speaks only WebDriver BiDi, which Playwright cannot attach to (refused with that reason).
- **Its profile** (`--browser-profile`, `-bp`): `fresh` (the default: new at every start), `session` (kept with the
  session, in its folder beside the HOME - never in the HOME the agent reads; removed with the session), or an
  absolute folder of yours (outside workspaces, mounts and sockets' folders).
- **Its display:** Xvfb without TCP and without the abstract X socket (the agent shares the pod's network namespace),
  no MIT-SHM, and x11vnc only on the Unix socket `RUN.browser-vnc/vnc.sock` beside the run's directory (`0700`, removed
  with the run) - no TCP port anywhere, nothing of it in the agent's container. run.json and `sandbox-ai list --json`
  name it (`"browser": {"kind", "control", "profile", "vnc", "cdp", "container"}`).
- **In the app:** **Browser** on the Sandboxes & sessions page and in the context menu of a start's tab shows the
  live browser - as a tab beside the session's terminal since the fixes from live use (below), in a window of its own
  on demand: a VNC client of the app's own in Qt (RFB 3.3-3.8, security None, Raw, CopyRect,
  DesktopSize; every size bounded) that talks to the socket directly - no web view, no websocket bridge, nothing of the
  app listening anywhere; a socket that is not yours, or in a folder others can open, is refused. The display scales
  with the tab or window; mouse and keyboard go to the browser (in its tab every key, Esc too; in its own window plain
  Esc closes the window as every extra window's, its [x] too, and Shift+Esc sends Esc to the browser); the clipboard
  only while *Share the clipboard* is ticked. The Board has a
  Browser part (kind, who drives it, profile; its badges say when the agent drives it or a folder keeps its
  profile), the guided setup asks for it, the presets take the options; English and German, the help (and the web
  page's) has a section on it.
- **What it means:** what you type in it, passwords too, passes the run's connection proxy like the agent's traffic -
  logged with credentials redacted and checked by the privacy rules. Behind Tor it is not Tor Browser (the start says
  so): sites can fingerprint it. The security mode `paranoid` refuses `--browser` (as `--gui`), `high` a folder of
  yours as the profile of a browser the agent drives; a policy can forbid it. Bubblewrap is refused (no pod), as is
  `--podman-url`. macOS: the socket lives in podman machine's VM, so the live view is Linux-only for now and only
  `--browser-control agent` is taken there.
- `--browser` takes its kind optionally: `--browser` alone is written `--browser=chromium` wherever options are read
  (project files, modes, sessions, the app), so that the next option is never taken for its kind.

Not run here (no Podman in this environment): the image's build and a start with a real pod; the tests check the plan,
the podman lines, the handshake with the supervisor, the runtime inside the container and the build script with
podman replaced (`tests/test_browser.py`, `tests/test_browser_matrix.py`, the app's `tests/test_browser_view.py`, whose

**Models on the server: load, unload and keep them loaded.** `sandbox-ai llm loaded NAME` lists what an LLM server
has loaded now: each instance with its context, the memory where its API reports it, how it stays loaded (LM Studio:
JIT with an idle TTL, which Auto-Evict may unload when another sandbox's model is loaded, or explicit; Ollama: until
idle for its keep_alive, or until unloaded) and the running sandboxes that use it (`--llm NAME:MODEL`). `llm load NAME
MODEL [--context N] [--ttl S]` loads a model explicitly (LM Studio's `/api/v1/models/load`, Ollama's `/api/generate`
with `keep_alive` and `num_ctx`, llama.cpp's router), its context by default `num_ctx` of the model's parameters;
`llm unload NAME MODEL|INSTANCE` unloads it. An unload, or a load that replaces what is loaded, is refused while a
running sandbox uses the model, unless `--force`. A JIT instance is replaced by unloading it first: a model is never
in memory twice (a second load in LM Studio is a second instance). Through the endpoint's VPN and with its key, as
`llm models`; reading never loads anything.

In the app: **Models on the server…** on the LLM servers page (also for a host of `sandbox-ai hosts`): the table of
loaded models, Load… (a model of the server, its context from its parameters, Ollama also a time; checked before the
form closes), Unload… (asked first, naming the sandboxes that use it), Keep loaded (a JIT model loaded explicitly) and
Refresh, every command in the background. The status lines mark a JIT model.

**A start says when its model is loaded JIT.** LM Studio may unload a model it loaded JIT when another sandbox's model
is loaded (Auto-Evict). A start that finds its model loaded that way now says so in its output ("see Help > Keeping
models loaded"), and when no other running sandbox uses the model it loads it explicitly (the JIT instance unloaded
first). A model a running sandbox uses is left as it is.

## More changes and fixes

**MCP servers behind a VPN start again:** the VPN container of an MCP server named two of its nftables chains
`redirect` and `refuse`; `redirect` is a keyword of nft, so `nft -f` failed and no MCP server behind a VPN came up (it
failed closed: nothing left past the VPN). The chains are `dns_redirect` and `dns_refuse` now, and every rule set a
VPN container loads goes through nft's own parser in the tests.

**Board: Save beside Save as preset…:** *Save* (button, Ctrl+S, File > *Save the board*) keeps the board where it belongs:
in the preset of yours it was made from (at once, its name, description, category and notes kept), else in its
project's file (Apply), else as a new preset of yours. *Save as preset…* still saves under a new name. Presets of yours
are private (`~/.config/sandbox-ai/app/presets.json`) and always under *New from preset… > My presets*.

**File manager: a text with mixed line endings comes back from the hex view.** Such a file opens as text read-only
(the editor could not write it back exactly); after the hex view neither the text nor the Markdown view came back
("These bytes are no text the editor can show unchanged …") and the text view's button was greyed out. Unchanged in the
hex view it is the text it was again; changed there into bytes the editor cannot show unchanged, it stays in the hex
view and says why.

**Every model server in the agent's Model server choice.** The Board's agent part and the launch page listed only the
servers that answered in time: each was asked for its models one after another with a minute each, and a few that were
down (LM Studio not running) took longer than the whole read, so the list held one or two servers or none. Now every
server `sandbox-ai llm list` names is listed at once, then all are asked for their models together, each briefly
(15 seconds; another host's a little more), and the list fills in as they answer. A server whose models are not known
(no default model, none listed since its last check, no answer now) stays in the list, greyed, with why: "No models
known: the server did not answer - start it, or: sandbox-ai llm check NAME"; its bare name is offered only where the
launcher takes it (a default model, or exactly one model known).

**MCP servers' variables: values that are no secret, optional ones, secrets of another name.** A catalog declares each
variable with a description and whether it is required and a secret; sandbox-ai knew only names that were always
required and came from your environment or a secret, so a flag like gowitness' or WhatWeb's `ALLOW_PRIVATE_TARGETS=1`
could not be set and the start failed. `sandbox-ai mcp add|set NAME --env NAME=VALUE` keeps a value that is no secret
in the definition (`"env_values"`; one line, at most 1024 characters, never anything of a secret's shape or name - the
privacy check's token patterns, a `..._TOKEN`, `..._API_KEY` or `PASSWORD` - and never for a variable the catalog
calls a secret); `--env NAME` of a variable the catalog does not require is passed only where there is one
(`"env_optional"`), of a required one as before; `--env NAME@SECRET` takes it from the secret SECRET (`"env_secrets"`).
Older definitions stay valid. A start's own: `--mcp-env NAME:VAR=VALUE|NAME:VAR@SECRET` (`-mv`), in an instance of its
own as with `--mcp-limits`. The app's MCP Properties (the MCP page and the Board's MCP part) show a table of the
server's variables - its catalog's description, required or secret, where the value comes from, a value field for one
that is no secret, a chooser of your secrets for a secret - each value checked by sandbox-ai's own rule as it is typed.

**An MCP server running with another definition no longer ends a start late.** "MCP server playwright is running with
a different definition or other rules; stop it first" came after the workspace and session were made. Now the start
gets an instance of its own (`NAME.HASH` of what it runs), said before anything starts; the running one serves its
starts on. A helper or a team's board runs once: refused before anything starts, with `mcp stop NAME` as the fix.

**Everything a start's MCP servers need is checked first, every problem at once.** Before a pod, workspace, session or
server is made - a dry run too: the server is defined, its `--mcp-limits`, `--mcp-mount` and `--mcp-env`, its
folders, the administrator's policy, its required variables and secrets, its image (there: Podman runs it with
`--pull=never`) or rootfs, its VPN, and an instance running with another definition - "3 problems with the MCP servers
of this start ...", each with its fix, instead of a session "not kept: its first start failed" per problem. The Board
lists each of them on the MCP part it is about, before Start.

**The Board's MCP part: two buttons that say what they do.** "Reset to defaults" and "Defaults for every start…" were as
wide as the inspector and did not say how they differ. Now "Use the server's limits" discards this board's limits (the
server's defaults hold again) and "Save as the server's defaults…" opens the server's Properties with this board's
limits and variables filled in, for OK to make them its defaults for every start; both of their own size, with a
tooltip and a line of help. In the server's Properties the button is "Use the built-in limits".

**A service's image from a drop-down.** The Service (container) part's image field and the guide's question for a
service offer your images (`sandbox-ai images list`: pulled and built, with what they are pinned as), then "Other…"
for a name typed in.

**The guide introduces a kind of part once.** Its first step, what the part is, was shown every time a part was added;
now once per kind of part (kept in the app's state), then the guide starts at the first question, with "Show the
introduction" to see it again.


**`images pull|build-image --json` print the JSON alone.** Podman's own output went to standard output: `podman pull`
prints the pulled image's ID there and `podman build` its steps, before the JSON (CI's services job: "Expecting value:
line 1 column 1"). Podman's output now goes to standard error, with and without `--json`; the live test says a
command's standard output and error when its JSON cannot be read.

**`llm status --watch`: its pause of its own, and a test that cannot hang.** The watch's pause between two readings is
a function of its own (`watch_sleep`). Its test had replaced `time.sleep`, which every thread shares, and ended the
watch at the second call: on CI a thread an earlier test had left running took that call, and the watch read on
without a pause until the 5-minute timeout. The test now replaces the watch's pause alone and ends it at every call
from the second on.

**Every agent waits long enough for an MCP server's call.** Codex waits 60 s for an MCP call unless told otherwise,
and sandbox-ai told it otherwise only for helpers and team boards: a server whose tools run longer (the new `exec`,
commands up to 600 s) was cut off. Now every `--mcp` server gets its wait in every agent's own setting - Codex
`tool_timeout_sec` (and `startup_timeout_sec` 60 s for a server's start, instead of 10 s), Claude Code each server's
`timeout` (and `MCP_TOOL_TIMEOUT`/`MCP_TIMEOUT` for older versions; your `--env` wins), OpenCode, Hermes, Qwen Code,
DSH and Goose theirs: the server's `tool_timeout` (10-3600 s) from its catalog entry or its definition (`mcp set NAME
--tool-timeout SECONDS|default`, a project file's `mcp_servers`), 2000 s for a helper and a team board, else 660 s.
It is the agents' setting, not the server's: a change of it starts no instance of its own.

**`--nested-containers`: the agent's own IPC namespace, for crun's mqueue.** Podman inside the sandbox failed on
GitHub's runner with "crun: mount `mqueue` to `dev/mqueue`: Operation not permitted": the kernel lets only a holder of
CAP_SYS_ADMIN in the user namespace that owns the IPC namespace mount mqueue, and the sandbox's IPC namespace is the
pod's. The guard now gives the agent an IPC namespace of its own user namespace, with a fresh mqueue at `/dev/mqueue`
(stricter as well: no System V IPC shared with the sandbox's own processes; with `--gui` the display offers no MIT-SHM
then). Neither can stop a start; the dry run's `nested_containers` names it. Where crun still may not mount mqueue,
the live test is skipped as a known limitation of that runner (the CI job `nested` takes exactly that skip with a
warning) and the option stays not live-tested.

**The web page adds an MCP server with values and named secrets, and shows its variables.** Its add form took only
names of variables. Now it takes them one per line as `mcp add --env` does - `NAME`, `NAME=VALUE` (a value that is no
secret: one line, at most 1024 characters, nothing of a secret's name or shape) and `NAME@SECRET` - checked as the
command checks them before anything runs. **Add…** on a catalog entry shows the variables its catalog declares, each
with its description, whether it is required and whether it is a secret, and fills in the required ones by name; it
reads them from the new `mcp catalog --json`. A host before 0.1.95 gets the catalog's lines as before and is told to
update for values and named secrets.

**Playwright MCP is in the signed catalog.** INTEGRATIONS still called it "prepared, not built"; it is published in
sandbox-ai-mcp (`sandbox-ai mcp add playwright --network full`, with the limits the catalog recommends), as binwalk,
Brave Search, capa, DuckDuckGo, Engram, gowitness, memory, OpenOSINT, osint-mcp, radare2, SearXNG, Signal, Telegram
(bot and user), web-fetch, WhatsApp, WhatWeb and YouTube are.

**Security: an MCP server under Bubblewrap no longer sees sandbox-ai's environment.** bwrap's own process is PID 1 of
the server's PID namespace and kept the environment it was started with - the launcher's, API keys of your shell
included - which every process of the server could read at `/proc/1/environ` (`--clearenv` empties only what the
server's command gets). bwrap now starts with `PATH` alone; what a server needs still reaches it through `--setenv`.
Found by the independent review of the new `exec` MCP server. Agent sandboxes were not affected (bwrap runs them with
`--as-pid-1`).

**Security: an MCP tool call's question shows all of its arguments.** A question about a tool call showed the
human the first 300 characters of its arguments, and its file held at most 500 characters of each value: a long post or
thread was allowed without being seen whole (found by the independent review of the bluesky MCP server). The question's
line keeps the short form and says when it shortened it; its details carry the complete arguments - pretty-printed JSON
of exactly the value the relay passes on, credentials redacted, up to 64 KiB - a larger call is refused without a
question (see *A tool call too large to show is refused* under the fixes from live use), never cut silently.
`sandbox-ai approvals show ID` prints them in full (new), `approvals list --json` has them
as `details` and `details_whole`, the app's Approvals page and Questions window show them below the list (opened by
themselves where the line shortens them), the web interface in a details element of the row; a desktop notification
that cannot show them whole offers no Allow. A non-printable character in them (a bidi override, a zero-width space)
is shown as its JSON escape. An answer is bound to the call its question showed: a call of the same tool with other
arguments made while one was asked waited for that question and got its answer - an "Allow once" of a harmless call
let it through unseen; now it gets a question of its own (an answer for the run still covers the tool for the run).

**Security: an MCP server can run as PID 1 itself (`"pid1": "server"`).** PID 1 of a server's container was catatonit
(Podman's `--init`), of its Bubblewrap sandbox bwrap's own reaper - and that process holds the MCP connection's stdin
and stdout, which every process of the server can open through `/proc/1/fd`: a command of a server that runs commands
(`exec`) could write MCP messages to the client (found by the independent review of the exec MCP server). A catalog
entry or definition with `"pid1": "server"` (checked like the other fields: any other value is refused; `mcp add`
carries it from the entry; part of a server instance's identity) runs the server itself as PID 1 - Podman without
`--init`, `bwrap --as-pid-1` - and the server reaps its children. Every other server keeps the default.

### Security boundary

- The connection proxy lets only WebSockets switch protocols. An `Upgrade: h2c` (or any other) request header is
  taken off the request (the client goes on in HTTP/1.1), and a server that switches to anything but WebSocket is
  cut off: after such a switch every later request on the connection passed as raw bytes, past the HTTP rules and
  the privacy check of pushes.
- HTTP on ports other than 80 and 443 is checked whatever its form: a method in lower or mixed case (`post /x`), a
  bare LF or CR before the request line, or a request line sent in pieces (cut after the method or its space) was
  relayed as plain TCP or TLS, past the HTTP rules and the push check, while servers such as Go's and nginx read it
  as the request it is.
- An "allow once" for a request an ask rule holds lets through only the request its question showed: a request to
  the same endpoint with another query or body, made while the first one was asked, waited for the same question
  and passed by its answer. It now gets a question of its own (as MCP and tool calls already did).
- With the kill switch at `api` (`sandbox-ai net cut RUN api`) each request's Host header must name one of the
  model API's hosts, as the TLS handshake must: a request naming another site behind the same front end (domain
  fronting) went there; it is refused with a 403.
- After a kill switch request (`sandbox-ai net cut`, the app's Kill switch) the run's control socket still holds
  later requests to the run's security mode: every later `sandbox-ai net allow`, `mcp attach --live` and
  `net allow --api-key` of that run failed with "'str' object has no attribute 'get'" (and a hand-written cut
  without a mode lifted the strict mode's limits on what `net allow` may open).

  bootstrap line, tor's last lines and what helps (bridges, another network, the host's clock, more time). The
  profile keeps the settings (`vpn add --tor --bootstrap-timeout/--bootstrap-attempts/--bootstrap-stall`, and the new
  `sandbox-ai vpn set NAME ...` for a profile you have; `vpn show` and the plan say them), and the launcher waits for
  every attempt at its longest. A session's start - the terminal it was started in and an attach - waits as long as
  its supervisor says new lines and gives up after 120 s without one or after 20 minutes (more when the Tor profile's
  settings allow more), saying which, since when and its last line. The bar shows "VPN: Tor 69% (Loading relay
  descriptors), attempt 1 of 3". MCP servers behind a Tor of their own get the same bootstrap and are waited for the
  same way (their wait was a fixed 120 s), their Tor's lines said in the start's progress ("MCP server fetch: vpn: tor:
  bootstrapped 30% ..."). launcher.log has each stall (a warning), the attempt that made it and every percentage
  (DEBUG). Tests: tests/test_live_regressions_tor.py (end to end through ./sandbox-ai with a fake Podman whose Tor
  container runs the real vpn_runtime.py and a tor that is slow, stalls or progresses), tests/test_vpn_tor.py.
- **A start through Tor no longer ends at tor's first SERVFAIL after its bootstrap.** User: "vpn: tor: bootstrapped
  100% (Done)", then "the VPN did not come up: 127.0.53.1: DNS error code 2". tor says 100% before it has a circuit
  an exit looks names up through; until then its DNSPort answers SERVFAIL (DNS error code 2), as it does for a name
  one exit could not resolve - and the first such answer for one of the agent's names ended the start. Now every
  lookup through Tor (the checks, the agent's names, a name allowed during the run; an MCP server's Tor and `vpn
  check` alike) takes SERVFAIL and no answer as "not yet" and asks again with growing pauses: up to 90 s for tor's
  first circuit, said in the start's progress ("Tor: waiting for its first circuit (DNS through Tor: SERVFAIL, try
  3)"), asking check.torproject.org too to tell a missing circuit from a failing name, then up to 30 s for each name
  (20 s for one allowed during the run), never past the launcher's wait. Only then does the start stop, saying what
  was asked, the answers and what helps. Every lookup still goes to tor's DNSPort alone, and the kill switch is never
  touched. The DNS probe (whoami.akamai.net) stays: through Tor an exit's resolver answers it, which is still
  compared with this host's own address. Tests: tests/test_verify_tor_browser.py (end to end through ./sandbox-ai
  with a Tor container running the real vpn_runtime.py against a DNSPort that answers SERVFAIL at first).

### Images and variants

- **A start builds its own missing image first.** A start whose image of sandbox-ai's own is missing - the agent's,
  its variant, the team's, Cairn's, the browser's - builds it before anything else (`sandbox-ai build ...`, the same
  pinned and checked build, its progress on standard error) instead of only saying so; not in a dry run, not for a
  remote Podman (`--podman-url`), not with `SANDBOX_AI_NO_AUTO_BUILD=1`, and an image that is pulled never is. Podman
  failing to answer `podman image exists` is said as such (with `sandbox-ai doctor`), not as "not built"; a missing
  image names Podman's image store and the user ("(Podman's image store: PATH, user NAME)"), since rootless Podman
  keeps one store per user; and `sandbox-ai build` as root says that its image goes into root's store, which another
  user's starts do not see.
- Image variants belong to their agent: each agent has its own (`~/.config/sandbox-ai/images/variants/AGENT/NAME`,
  the variants of before moved there once), so a recipe's variant - `media`, `dev` - can be made for claude and for
  dsh alike, each its own image `localhost/AGENT-sandbox-NAME`; a dsh start no longer meets claude's variant of the
  same name. Where a name is a variant of several agents, `sandbox-ai images` lists it and its commands take it as
  `NAME@AGENT` (`sandbox-ai build media@dsh`); what a start says (and builds, as before) when the image is missing
  names it so; `sandbox-ai build all` builds each.
- There is no image variant for Tor any more: the recipe `tor` (torsocks, torbrowser-launcher) is gone, and no preset,
  note or help tells you to build or add one - Tor networking needs nothing in the agent's image, the Tor container
  beside it carries everything (the sandbox's own browser, `--browser`, for pages). A variant of yours called `tor`
  stays an ordinary variant. No preset adds `--image-variant`; a test checks every preset.
- The Images page lists every variant, built or not, with its agent, and builds a variant as one (`--variant`): its
  Build of the variant `tor` built the Tor VPN's image. The start's preparation looks for the start's own agent's
  variant and makes it from its recipe for that agent.
- A preset or board made with one agent and switched to another no longer refuses its image variant: a variant of
  another agent only is made for this agent too (same packages and files) and built at the start; `--image-variant
  tor` (the gone recipe) without a variant tor of this agent starts the agent's own image with a note - Tor is the VPN.
- A system installation (`./install.sh` as root, `sudo sandbox-ai update`) is open to every user whatever root's
  umask: with 077 (hardened systems, a root shell's own) every folder of it - the commands, the launcher, the
  Containerfiles a build reads, the app and its environment - was root's alone, and a user's sandbox-ai, build and
  app failed. install.sh makes a system installation with umask 022. `install.sh --from .` as root in a user's
  checkout lists it with the checkout as a safe directory for git (it refused it as "dubious ownership"), and its
  fallback copies regular files only.

### Approvals

- **A tool call too large to show is refused, never asked; a silent question refuses only its own call.** A question
  about the agent's own tool (a `tool` rule that says ask: Bash, Edit, Write ...) or an MCP tool showed at most 64
  KiB of the call's arguments and a "truncated" line, and "Allow once" still let the whole call through - a command
  could hide its `rm -rf` after 64 KiB of harmless text. Now such a call (more than 64 KiB, or a value the rules know
  only by its length) is refused at once with why, never asked; an answer for the run still covers it (that scope is
  unchanged). And a question nobody answered refused every call of that tool under its rule for a while; now only
  that exact call (the keyed digest its question is bound to) - another call is asked on its own.

## Logging

"I press Start and nothing happens, and no information": two rounds for the launcher and two for the desktop app
make what was asked, what was decided and why, which command ran, how long it took and how it ended traceable -
in `~/.local/state/sandbox-ai/launcher.log` and the app's `app.log` and log window, never with a secret. The README's
*Troubleshooting* says where to look and how to send it (*Copy for a bug report*).

- **Logging, round 1 (launcher).**
  - The launcher keeps a log of its own, `~/.local/state/sandbox-ai/launcher.log` (rotated at 2 MiB, three old files
    kept): what each start was asked (its command line, secrets taken out), its checked plan (agent, backend, image
    and variant, mode, workspace, configuration, MCP servers, VPN, session or terminal), every line it says on its
    terminal, the image checks (which image is missing for which agent, Podman's answer, the build started, its
    time and end), the pod created, run and removed, each MCP server reused, started or refused and how long its
    socket took, the VPN brought up, and why the start ended or was refused (its message and where it came from).
  - `SANDBOX_AI_DEBUG=1` adds every outside command (podman, ssh, a build; its command line, time, exit status and
    the end of its error output) and every background check by what it does, and says these lines on standard
    error too, so a session's `supervisor.log` has them.
  - Sessions log their status once per change with why (its supervisor runs, is gone while its pod runs, Podman did
    not answer), a session's supervisor PID and log file, how long its terminal took or why its start ended (the
    end of its supervisor.log), a running session without its terminal once; stop, resume, pause and delete what
    was asked and in which state.
  - Polled things are said once per change, not at every poll: Podman not answering `pod ps`, a host SSH cannot
    reach, a model server that does not answer - each until it answers again. A line said again at once is written
    once, then "(said N more times)".
  - Silent failures found and now logged: `podman image exists` timing out or not running before a start (the start
    went on without a word), an automatic image build that could not run (no reason given), this host's own
    addresses not asked for the VPN's checks on another engine (the checks compared with nothing), the live MCP
    servers not taken out of the agent's configuration, an `--ask allow` deny that could not be written, a question
    file that could not be read (nobody was told), a session listed as damaged, an MCP relay connection that ended
    on an error (now a `connection-ended` record in the MCP log).
  - Also logged: `sandbox-ai build` (asked, time, exit status), image layers built or failed, `mcp add` and the pull,
    `mcp attach`, approvals answered (by whom: the human or `--ask allow`) and questions asked, desktop
    notifications, the web interface's actions and refusals (who, from where; never a body), requests to model
    servers, commands on other hosts.
  - Nothing secret reaches the log: the proxy's redaction, tokens of the usual forms, bearer credentials, secret
    option values, `NAME=VALUE` with a secret name, URL passwords and every value read from the secret store are
    taken out; a failed command is logged without its argument list.
- **Logging, round 1 (desktop app).** "I press Start and nothing happens, and no information": the app re-checked a
  start's needs in the background with no useful line - "Still preparing what the start needs…" again and again,
  debug lines naming only `Prerequisites.check_prerequisites.<locals>.read`. Now what was asked, what was decided and
  why, which command ran, how long it took and how it ended can be followed in app.log and the log window:
  - Every background call says what it does in words (`what=`, else its name without `<locals>`, its docstring and
    the sandbox-ai calls it makes) and its arguments (that of a parameter named value, secret, token, key... masked);
    a human's action (work) at INFO with its end and duration, a read at DEBUG; a read that fails at INFO once per
    change of its error (then DEBUG); a call that gives no answer within its time at WARNING, naming it - it ran on
    silently before.
  - Every sandbox-ai command the app runs (`call`, also over ssh): its command line, how long it took, its exit
    status and the tail of its error output; a failure at INFO once per change (a human's action: every time, at
    WARNING), "exit status 0 again" when it works again; a timeout at WARNING.
  - The Board's Start: the board, agent, host and session asked for; each reason it waits or is refused (placeholders,
    the launcher's check again - its verdict logged once per change -, folders made first, the prerequisites); where
    the start goes (a tab, a terminal window, the running session attached) with the launcher's options; an
    exception with its traceback.
  - The prerequisites: what the start needs on its host, what was found, what could not be read and why, what is
    missing or not built, the answers to "Build it now?" and the MCP folders, each command with its duration, the end
    of the terminal tab "Preparing the start"; a second Start while it is under way says what it waits for and since
    when.
  - What the human was told and asked: every warning and message (at WARNING / INFO), every question with its
    answer (also one that needs no confirmation by the settings), the pages' status lines and notices once per change
    (an error at WARNING, progress "…" at DEBUG), the bar above a terminal and its choices (a sign-in's bar never: it
    shows the login's code), a notification also while notifications are on, settings changed.
  - State changes once per change: each sandbox and session listed, its state changed, no longer listed (this
    machine and each host); a host that does not answer (WARNING) and answers again; terminal commands started,
    ended (exit status, duration), closed and killed; SFTP connections (connecting, connected, refused with ssh's
    reason, no answer, Cancel), host keys scanned; the sandbox browser's display (connected, closed, failed); pages
    that did not load, downloads; approvals answered (decision, scope, host, outcome); session copy/move; a second
    start of the app.
  - Every `except Exception` that went on with a default (about 120 places: the backend's reads of an older
    sandbox-ai, hosts files, policies, catalogs...) logs the exception at DEBUG with the reason it is swallowed.
  - The same entry again is counted, not written: "(the entry before came N more times in S s)"; a level named
    "WARN" (the MCP catalog's failure) is a warning now - it was logged as information.
  - Nothing secret reaches a line: command lines mask the value of `--token`, `--api-key=…`, NAME=VALUE of a
