# sandbox-ai 0.1.96 (hotfix)

## Hotfix round 1

- **A preset that was skipped says why.** A preset of an extra preset directory that is refused there (for example one that names `--workspace`, allowed only in your own presets) was skipped; a start with it, `presets show` and `presets check` said only "no preset NAME; see: sandbox-ai presets list", and the list does not show it either. They now name the file and the reason it was skipped.
- **`sandbox-ai version --help`** shows what `version [--verbose]` does instead of printing the version, and an unknown argument (`version --verbos`) is an error instead of being ignored.
- **The web interface no longer accepts the removed recipe tor.** Its list of image recipes still named tor (gone in 0.1.95: the Tor container carries Tor); a request for it passed the web interface's check and failed in `images recipe`.
- **The app's preset "GPU workstation" can download models.** It promises "PyPI and Hugging Face for models" but opened only huggingface.co; Hugging Face serves the model files from cdn-lfs.hf.co and cas-bridge.xethub.hf.co, which are open now (as in the preset data-ml).
- **"Install the kits' plugins" after the Kits table's context menu.** The table's context menu took the page's "Add to the kit" menu in as a submenu; when the context menu was dropped after use, the entries of that menu went with it, and the next change on the page (Install, Update, any change that disables the page's buttons) failed with "Internal C++ object (QAction) already deleted". A context menu now holds a submenu of its own with the same entries.

## Fixes from live use

- **`--vpn mullvad --mcp fetch` starts again: a start lends its tunnel to its own MCP servers.** The team-VPN change
  below made the start refuse a networked MCP server behind its WireGuard `--vpn` ("would need a tunnel of its own"),
  because that server got a tunnel of its own of the same profile - the same key twice, the same tunnel address, and
  the server sends to whichever tunnel spoke last, so the two tunnels quietly steal each other's traffic. So the
  common `sandbox-ai claude --vpn mullvad --mcp fetch` no longer started. Now there is one key and one tunnel: the
  start's VPN container lends its tunnel, and each such server's VPN container borrows it - no tunnel, no key, no tun
  device of its own, a kill switch through which nothing leaves but over loopback (as behind Tor: every TCP
  connection over IPv4 to its relay, every lookup on port 53 to the relay's resolver, other UDP and IPv6 dropped),
  and a relay that hands each connection through a Unix socket in a private folder (among the VPN's private paths
  that no workspace or mount may show; only these VPN containers mount it, a server's read-only) to the start's VPN
  container, which opens it through the tunnel to public IPv4 addresses only - never the start's own sandbox, its
  loopback or the networks beside the tunnel - with a mark of its own, which the agent's proxy never sees and its
  firewall lets by after its cut chain (see below), held to the
  tunnel by its kill switch. The server keeps its own sandbox, firewall and rules. It comes up once the start's
  tunnel is up, is an instance of that run alone (`NAME.HASH`: never reused by another start or behind another
  tunnel), and is stopped when the start ends; when the start's VPN container goes, the borrower says so and ends,
  and its kill switch stays (fail closed). The same for WireGuard, Mullvad and a persistent Tailscale node with an
  exit node; for a server whose own definition names the start's profile; for `mcp start NAME --for START` and
  `mcp attach NAME START --live` while START runs (for a START that does not run the server comes up with its next
  start). A server whose own definition names another profile keeps a tunnel of its own of that one; Tor, OpenVPN
  and an ephemeral Tailscale profile are unchanged. The lock stays for separate sandboxes (two sessions, team
  members), and `mcp start NAME --vpn PROFILE` with a profile a session holds is now refused before anything starts,
  naming the holder and how to share its tunnel (`--for START`). On macOS the folder is a Podman volume in podman
  machine's VM. Held by the real `./sandbox-ai` with the VPN containers' real runtime (Podman and the kernel stood in
  for: tests/test_hotfix_mcp_lent_vpn.py, which failed first with the refusal), the relay with real sockets, and
  the MCP VPN matrix (tests/test_mcp_vpn.py: every way up, every server kind, every VPN kind).
  A security review before the release (tests/test_hotfix_mcp_lent_vpn_security.py, each failing first; the code, the
  launcher's path checks and the rules as written - Podman and the kernel stood in for here too) found no way for an
  agent or a server to reach the lent tunnel's socket or to leave past the tunnel, and these, fixed: a start whose 512
  lent connections were all in use counted as gone - one server that held them for 15 s ended the VPN containers of
  all the run's other servers; now it is busy, not gone, and one server's relay hands the start at most 256
  connections and lookups at once (no thread per packet beyond that). A connection whose far end never closed kept its
  slot for good after the server's program had closed its side: closed now after 120 s of silence. Neither the
  lender's nor a relay's accept loop ends on an error that passes (no descriptor, no thread). The networks never lent
  are named in the runtime itself (multicast was "global" to Python's ipaddress; a TCP connection there fails in the
  kernel anyway). A borrower's look at its lender checks the profile each time (macOS: the volume of a run's name,
  used again). A DNS answer above 3 kB did not cross the socket (the answer's line had the request's limit); a
  question that came over TCP was asked over UDP again and got the truncated answer once more (now asked again over
  TCP); a lookup whose resolver sent other answers without end never ended. The folder of the lent tunnel is made anew
  and is never a link, and `--vpn-lent-by` is refused in presets as in project files and servers' options. Known
  limit, now in the README: a lent tunnel carries TCP to public IPv4 addresses (any port) and lookups only.
  What that review left open is closed too (tests/test_hotfix_mcp_lent_vpn_cut.py, each failing first; in the kernel:
  tests/test_mcp_lent_vpn_live.py and tests/test_killswitch_live.py in CI's killswitch job):
  - **`sandbox-ai net cut` stops the lent connections.** They carried the checks' mark, which the start's firewall
    accepts before its cut chain: a cut start's MCP servers went on reaching the internet through its tunnel. Now
    they carry a mark of their own, accepted only after the cut chain, and every mode judges them by exactly the
    rules that judge the agent's own packets: `all` and `remote` stop them, `api` keeps only those to the start's
    own model API (a helper with another provider loses its network while that cut holds; judged by address - the
    name check of `api` is the connection proxy's, which a command server and a helper have in their own sandbox),
    `local` leaves them (a lookup stops where the tunnel's resolver has a private address, as the agent's own
    does). A lent TCP connection that was open before ends at once: the cut answers its packets with a reset (the
    agent's are closed by its proxy, which a lent one never passes), and one that says nothing ends at its next
    keepalive probe (15 s).
  - **A lender that cannot start stops only a start that needs it.** It started for every WireGuard, Mullvad and
    persistent Tailscale start, and its failure was the start's. Now only a start with servers that borrow its
    tunnel is refused; any other goes on with a warning, and a server with network attached later (`mcp attach
    --live`, `mcp start --for`) is refused with the reason. (Started with the tunnel, not on demand: a lender begun
    later would need a second privileged entry into the running VPN container from another launcher, with a life
    and failures of its own.)
  - **The run's token.** The lender's socket served whoever had the mount. Now every request carries a token of
    256 random bits made for each run - handed to the lender and to each borrower on standard input with the
    secrets (never the environment, a command line or a log; on the host a file only you read, beside the mounted
    folder, not in it) and compared in constant time: a borrower another run left behind, or any other container,
    is denied and ends.
  - **`sandbox-ai gc` removes what a killed start left** of its lent tunnel (`vpn/.lend/RUN`; macOS: the volume
    too) - never one of a live run: not a folder whose launcher still holds its lock, whose run is registered or
    orphaned, or whose pod still runs a container, and none while Podman does not answer.
  - Also: an image server's VPN container mounted the Mac's folder instead of the run's volume on macOS (its
    lender's socket is in the volume), and a second start of a run's name no longer makes a running start's folder
    anew.

## Browser and Tor, second check

- **The agent no longer reaches the display of a browser that is only yours.** `--browser-control human` promises that the agent reaches nothing of the browser - but x11vnc, started with `-rfbport 0` for "no TCP listener", ended only its IPv4 listener and still listened on `[::]:5900` without a password, in the pod's network namespace the agent shares: the agent could connect to `[::1]:5900`, see your browser's screen and drive its mouse and keyboard, sites you are signed in to included. x11vnc now gets `-rfbportv6 -1 -noipv6` as well, and the start checks that neither Xvfb nor x11vnc has any TCP or UDP socket - else it stops (also for the agent's own `--gui-vnc` display, which had the same listener). Found by running the real Xvfb and x11vnc as the browser's container starts them.
- **The browser's display comes back when its x11vnc or Xvfb ends.** The browser's container started the browser again when it ended, but not its display: after x11vnc or Xvfb ended (a crash, the out-of-memory killer in the container's 2 GB) the container ran on without one, and the app's Browser tab stayed "closed" for the rest of the run. The display is now started again (its stale sockets removed first), the browser with it, within the same limit of restarts.
- **The app's Browser tab connects again by itself.** When the browser's display closed while its start ran (its container starting the display again, above), the tab said "The browser's display was closed (the run ended?)" and stayed so until Reconnect was clicked. It now connects again by itself (every second, for up to two minutes) and says so meanwhile; a server that breaks the protocol is not asked again. Tested with the real x11vnc on the run's socket: the tab shows its picture, and clicks and keys reach the window there.
- **A folder of yours as the browser's profile is used by one run at a time.** Two starts with the same `--browser-profile DIR` both ran, and each browser's runtime removed the other's profile lock at its start (taking it for a lock left by an earlier run): two browsers wrote the same cookies, logins and history databases at once and could corrupt them. A start now holds the profile folder (`.sandbox-ai.lock` in it, as `--state-dir` has) for its whole run; a second start is refused, naming the run that holds it. A profile kept with a session gets the same lock.
- **A folder of yours as the browser's profile is made yours alone.** A profile folder made with a plain `mkdir` (0755) kept its mode, and Firefox writes its databases there as 0644: your logins, cookies and history were readable by every user of the machine. The start now makes the folder 0700 (as it does with one it makes itself) and refuses a folder that belongs to another user.
- **The start of a browser only the agent drives says what it is.** With `--browser-control agent` the start said "(the app's Browser button shows it)", but such a run records no display for you and the app's Browser says "Only the agent drives this browser", as the README says. The start now says the app shows no display of it, and that `--browser-control both` lets you watch it too.
- **Behind Tor, a kept browser profile is said to link the runs.** The start says that the browser behind Tor is not Tor Browser; it did not say that a kept profile (`--browser-profile session` or a folder) brings the cookies, logins, history and cache of its earlier runs - with Tor or without, from your own address - into the Tor run, where a site links the visits to them at once. It says so now, and that `--browser-profile fresh` avoids it.
- **Firefox asks no Mozilla server for Remote Settings by itself.** "Nothing of its own on the network" did not hold for Remote Settings: Firefox ESR fetched blocklists, certificate intermediates, CRLite and other lists (firefox.settings.services.mozilla.com and its attachments' CDN) by itself - an approval question for a host you never opened, and behind Tor a call of every run - and it called mitm-detection.services.mozilla.com after a certificate error and sent Firefox 128's private attribution reports. Its user.js now points Remote Settings nowhere (as Mozilla's own test profiles do) and turns the MITM check, the attribution reports, the captive portal URL and sponsored top sites off; Firefox's translations and its local machine learning, which download their models through Remote Settings, are off with it. An address of the sandbox's loopback (127.0.0.0/8, ::1, localhost) from a sandbox's tab is now never opened here: the bar says why, with *Copy link* and, when the start has a browser of its own that shows you a display, *Open in the sandbox's browser*, which opens its Browser tab and types the address into its address bar (Ctrl+L, the address, Enter).
