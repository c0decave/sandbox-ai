**A shell of your own in a running sandbox: `sandbox-ai shell NAME`.** It opens an interactive shell in the running
start NAME, beside the agent and without taking its terminal; `sandbox-ai shell NAME -- COMMAND ...` runs one command
there and returns its exit status, and `-n`/`--no-tty` runs it without a terminal for scripts and pipes (input to its
end, output and error output apart; also the default when your terminal has none). The shell is under exactly the
agent's rules: a second small relay beside the attach relay, started by the guard inside the sandbox's Firejail
confinement (`tmux/shell.sock`), starts it with the user, `/work`, environment, firewall, connection proxy and CA,
mounts and resource limits of the agent's own tmux window `shell`, with no capability, nothing of the host and no
secret the agent does not have. Nothing is `podman exec`'d into the container (that would carry the supervisor's
capabilities and see the proxy's CA key) and nothing runs privileged; only the terminal's bytes and the exit status
cross, through a framed protocol whose client executes nothing the sandbox sends, follows no symlink in the
sandbox-writable folder and bounds every frame. It works for Podman and Bubblewrap starts in tmux (the ones
`sandbox-ai attach` reaches); on macOS the relay's client runs in podman machine's VM through `podman exec`, as
attach's does; another host's start is reached with `sandbox-ai hosts run HOST -- shell NAME`. A task in the
foreground, an MCP server's sandbox and a paused start are refused with the reason; a start made by an older
sandbox-ai has no shell relay until it is restarted (`sandbox-ai resume NAME --restart`), and is pointed to its tmux
window `shell` through `sandbox-ai attach NAME` meanwhile. Each shell is noted in the start's activity timeline
("shell opened by the human", the command when one was given, credentials in it redacted, and its end with the exit
status), so `sandbox-ai activity`, the report and Monitoring show that the human opened it. Tab completion, `--help`,
README (command tables, a section of its own), QUICKSTART and the agents' sandbox-ai skill name it. The desktop app's
Sandboxes & sessions page has a **Shell** button beside Attach (and in a session tab's menu) that opens it in a terminal
tab of its own, on this machine or a host; the web interface has the same button in a start's row (a host's
sandbox-ai older than 0.1.97 is told to update first).

**Session bridge: one running session reaches another, in a controlled way.** `sandbox-ai bridge add A B --allow
CAP[,CAP...]` lets session A send notes to session B (`message`), ask B's agent a question and wait for its answer
(`ask`, with a timeout), read files below a path of B's workspace (`files:ro:PATH`), write there (`files:rw:PATH`:
every single write is asked to you, with the diff shown), or watch B as an observer (`watch`: B's activity, a summary
of its LLM traffic, the changes in its workspace since the bridge started, and alerts to you). `--both` gives B the
same over A. What an observer may do besides alerting is switched on one by one, per bridge, with
`--observer-actions alert,hint,net-cut,pause` (a hint is a note into B's inbox; net-cut sets B's kill switch so that
only its model API stays reachable; pause freezes B, and only you resume it). `bridge list`, `bridge show ID`,
`bridge revoke ID|--all` and `bridge resume ID` (lifting a suspension) are the rest. Design and threat model:
docs/BRIDGE_DESIGN.md.

- **On the host, never between the pods.** Each bridge has a broker of its own on the host; each side gets an MCP
  server `bridge-PEER` attached to its running sandbox as `sandbox-ai mcp attach --live` attaches one (a detached copy
  of one socket folder handed to the run's supervisor). So every call goes through the run's relay: it is logged in
  the run's `mcp-calls.jsonl`, held by its rules, asked about like other MCP calls, and refused where the run's
  policy or security mode refuses `--mcp`. Claude Code takes the server up at once (its `~/.claude.json`, taken out
  again when the bridge or the run ends); the other agents read their MCP servers only when they start, which
  `bridge add` says.
- **Only you make or widen a bridge.** No tool of a bridge creates, widens or chains one, and `bridge add|revoke|
  resume` refuse to run inside a sandbox. A bridge reaches exactly its two sessions: A-B and B-C never give A-C.
  Content that passed two bridges is not passed on over a third, and content never goes back to the session it came
  from over another bridge (a loop guard).
- **Content of the peer is untrusted.** Every tool that returns the peer's content (inbox, ask, list_files, read_file,
  the watch tools) is marked untrusted in the relay of the reading run, so that run is tainted before its agent reads
  it, and the rules for tainted runs hold from then on.
- **Files never leave the granted path.** Every component is opened from its parent's descriptor without following a
  link; `..`, absolute paths, `.git`, the run's private folders and canary decoy files are never reached (reading a
  canary through a bridge suspends it and alarms you); FIFOs, sockets and devices are never opened. A write goes to a
  new file in the same folder and is renamed over the old one (a hard link is replaced, never written through); a
  file the peer changed after you were asked is not written. A session whose workspace is read-only cannot be given
  `files:rw`.
- **Limits.** Per side: calls a minute (`--limit rate=N`, 60), message, question and answer size (`size`, 16 KiB),
  four open questions, a hundred waiting inbox items, eight connections; per bridge: the ask timeout
  (`ask-timeout`, 300 s) and the volume a day (`daily`, 64 MiB); reads and writes up to 256 KiB a call.
- **What is asked.** `--ask each|first|never` says what is asked about the calls that move content across (default
  `first`: the first call of each tool); writes are asked every time whatever it says, and `--ask allow` of a run never
  answers a bridge's question. The questions are listed and answered by `sandbox-ai approvals` and on the app's
  Approvals page (a write with its diff in full before Allow).
- **Warnings.** Bridging sessions with different network permissions is allowed, and `bridge add` says in which
  direction data can flow from the more restricted session to the less restricted one (with examples of what the
  latter reaches, or that it leaves without the VPN or Tor of the former).
- **Its life.** A bridge lasts until either session ends (it is not restored on resume), until `--until` (30m, 2h,
  HH:MM, an ISO time) or until `bridge revoke`. A kill switch (`sandbox-ai net cut`) or a canary alarm of either
  session suspends it until you lift it (`bridge resume ID`) or revoke it.
- **Records.** Every call in the bridge's own log (`bridge show ID`), events of kind `bridge` in both sessions'
  activity (Monitoring, `sandbox-ai activity --kind bridge`), and observer alerts and actions, writes and suspensions
  as findings of `sandbox-ai report`.
- **Across hosts.** `sandbox-ai bridge add web lab1:docs --allow ...` bridges a session of this machine with the
  session `docs` on `lab1`, one of your hosts (`sandbox-ai hosts add`; only those, never an SSH address). `lab1` runs
  its half of the bridge, `sandbox-ai bridge-stub ID`, started over SSH with the host's own settings (BatchMode, the
  host key checked strictly) on a connection of its own with every forwarding off; nothing listens on either host,
  and the connection carries only framed bridge messages. Each half attaches and keeps its own side: it checks every
  call against the grant it was given at the start (nothing widens it later; a call names no side, so a half cannot
  pass itself off as the other), walks its own files with the same rules, asks its own questions (a read or write of
  lab1's files is asked on lab1, listed by `approvals` there and on the app's approvals page with the other hosts'),
  and keeps its own limits, taint, exposure (hops and loops are counted across hosts) and logs. A path outside the
  grant never leaves this machine; what comes back is framed as the peer's content here, and a result without content
  is worded here, never taken from the other host. An oversize, malformed or flooding message, a dropped connection, a
  revoke on either host and the end of either session end the bridge on both hosts; a suspension on either suspends
  both, and `bridge resume` on either lifts it unless the other's cause still holds. A bridge is never opened again
  under the same ID (no reconnect after a revoke). The other host needs sandbox-ai 0.1.97 or later: an older one is
  refused with its version and `sandbox-ai hosts update HOST`. Design: docs/BRIDGE_DESIGN.md, section 9 (built with
  two halves instead of the first design's relay of raw MCP lines, so that each host judges its own side).
- **Not yet:** two sessions on two *other* hosts are not bridged through this machine (bridge them on one of them).
  (The observer's terminal snapshot and the app's New bridge… with the sessions of your hosts came later in this
  release: see below.)

### Bridge security review

An independent review of the same-host bridge, with both agents taken as hostile. Each item below was shown by a
failing test before it was fixed:

- **The workspace itself as a link (high).** The broker opened the peer's workspace by its host path, following
  links. A workspace inside a folder another sandbox writes (nested projects) could be turned into a link to your
  files, which a `files` grant then read (or, asked, wrote) and the observer's walk listed. The workspace is now
  reached from `/` without following any link, as everything below it already was.
- **A diff cut without a mark (high).** A question's details were cut at 64 KiB without saying so, and approvals
  and the app show exactly that much, so a write of up to 256 KiB could hide its payload after the cut. Details
  over 64 KiB are now refused before anyone is asked.
- **Calls that go on after a suspension (medium).** A call waiting for your answer went on once allowed, also when
  a kill switch or a canary alarm had suspended the bridge meanwhile. A suspension now ends the question, and the
  bridge's state is checked again after your answer.
- **Questions without a bound (medium).** Each call waiting for you made a question and a notification, bounded
  only by the rate, and a call went on after its connection closed. Now at most 4 calls of a side wait for you, at
  most 64 are in flight over all its connections, and an ask takes its place among the open asks before you are
  asked.
- **A write's diff without a time bound (medium).** difflib needed minutes of CPU for some 256 KiB writes. A diff that
  cannot fit is refused at once where that shows in linear time; any other is made by a process of its own, ended
  after 10 s, one at a time.
- **Smaller fixes (low).** Every call counts against the rate, and calls over it are logged once a minute (refused
  calls had grown `bridge.jsonl` without a bound). The peer's content cannot end its own frame (the end line carries
  a marker made for each result). A message cannot add a line to your notification. The bridges folder is 0700.
- **Across hosts too.** Each fix holds on both halves of a bridge across hosts: the other host's half walks its own
  workspace from `/`, bounds its own questions, diffs and calls in flight (its link serves at most 16 calls of the
  other half at once, and they count against that side's 64), ends a waiting question when either half is suspended,
  and counts every call of the other half against the rate. Content that comes back from the other host is framed
  here, with a marker made here.
- **Left open (low).** A write the human allowed reaches the peer's agent through its workspace without tainting
  its run (the supervisor has no control operation that taints). Binary content, or a file over 4 MiB, is asked
  about by sizes and digests only. `pause_peer` names the peer by its start name, which a rename can make another
  session's. The observer's walk does not bound the number of folders (only files and depth).

## Analysis round 1 (security)

- **`sandbox-ai net cut` behind Tor cuts tor's DNSPort too.** Since the resolver in front of tor's DNSPort (0.1.96) tor
  answers lookups on `127.0.53.1:9053`, and the cut's rule for lookups named only port 53: a run behind Tor that may
  look up any name (`--dns`, `--egress-all-allow`) still reached that port directly while its network was cut
  (`all`, `api`, `remote`), and tor, whose own packets pass the cut, carried each such lookup out - names out and
  answers back through the kill switch. Every mode that cuts lookups now rejects Tor's resolver address whole,
  whatever the port and protocol, in the firewall's chain and in the supervisor's view (`runtime.cut_mode_rules`,
  `cut_class`); `local` keeps lookups as before, and the resolver's own questions to tor (the checks' mark) pass.

## Analysis round 3 (chaos, concurrency and hostile input)

Concurrent starts, kills at every step, damaged files and hostile input on the features of the last 48 hours. Each
bug below was shown by a failing test first:

- **Loop guard: an odd event from the model server (medium).** One streamed event of another shape (`"choices": true`,
  a number where `tool_calls` is a list, an object as a block's index) made the loop guard and the LLM traffic record raise
  inside the relay: the connection ended in the middle of the answer, so the agent got half of it and the record
  was lost. Such an event is skipped now (as one that is no JSON is); the answer goes on to the agent as it came.
- **Teams: a start ended before it wrote its record (low).** `team start` killed between making the team's folder and
  writing its record (or a record a full disk never let be written: an empty `team.json`) left a name that `team
  start` refused as an existing team while `team show`, `list` and `delete --yes` said there was no such team. Such a
  folder is listed as damaged and `team delete NAME --yes` removes it; the record is written whole or not at all (0600
  from the start), and a start whose record cannot be written leaves nothing behind.
- **App, Board: the image list closed itself when it was opened (medium).** Opening a Service part's image list reads
  your images again, and their answer rebuilt the whole inspector: the list the user had just opened was deleted under
  the mouse a moment later (the flaky "OpeningCombo already deleted" of an app test was this). The list is filled in
  place and stays open; the inspector is rebuilt only when your images changed, and only once the list is closed.
- **LM Studio: two starts at once loaded their model twice (medium).** Two starts of the same model at the same time
  (two app windows, a double click, two terminals) both found it not loaded and both loaded it: LM Studio's second
  load is a second instance (`MODEL:2`), the model in memory twice. One start at a time per server looks and loads now;
  the next one finds the instance the first one loaded.
- **Cairn: a killed launcher's relay folder stayed (low).** A launcher killed with SIGKILL left `RUN.cairn` beside its
  run's folder (the relay's socket and the log of the workers' calls); `sandbox-ai stop` and gc removed the run's
  folder and the browser's beside it, never this one. It goes with them now. (macOS: the relay's Podman volume
  `sandbox-ai-cairn-RUN` of a killed launcher still stays; `podman volume rm` removes it - left open.)
- **Pi's telemetry guard: PI_OFFLINE switched off past it (low).** The guard refused `PI_OFFLINE` set to `0`, `false`,
  `no` or `off`, but Pi 1.4.0 is offline only for `1`, `true` or `yes` (any case, untrimmed): `PI_OFFLINE=OFF pi`,
  `No`, `on`, `2` or `" 1"` from the agent's shell ran Pi online (package checks and installs at its start, tool
  downloads). Its install report stayed off (`PI_TELEMETRY=0`, the proxy). Any value Pi does not read as on is refused
  now, in the Python and the JavaScript guard alike.
- **--llm-models: the models a start offers held on four paths only (medium).** "The proxy refuses requests for the
  others" held for the chat, completions, responses and messages APIs, and only for a model given as a string: the
  agent reached any other model of the server through its native API (Ollama's `/api/generate`, `/api/chat`,
  `/api/pull`, `/api/delete`; LM Studio's `/api/v1/chat` and `/api/v1/models/load`), on a path beside an endpoint's
  prefix, with `"model": ["other"]`, or with a body the relay does not read (gzip, another content type, over 32
  MiB). With a list of models every request with a body to that server is held to it now (`model`, Ollama's `name`,
  `source` and `destination`); one that names another model, a model that is no name, or a body that cannot be read
  is refused with the APIs' own error (`--llm NAME:MODEL,MODEL` the same). With `--llm-models all` (the default)
  nothing changes.
- **Checked, no change:** the loop guard's volatile-parts pattern on 64 KiB of hostile text (no slow backtracking);
