# sandbox-ai 0.1.83

0.1.79 to 0.1.82 were not released on their own: 0.1.83 carries everything listed for them below (and with 0.1.79
everything of 0.1.78, docs/releases/v0.1.78.md), and on top the memory of the app's test suite (CI killed it) and a
third performance pass over the desktop app, measured with the same probe as 0.1.81 and 0.1.82 (3 hosts - one
answering, where nothing runs, one slow, one unreachable -, a Podman that takes 3 s, 30 kept starts, a 5,000-record
connection log, 20,000 files, a run with one open and 200 answered questions, 7 LLM servers):

- **App: a closed window goes entirely; the test suite no longer runs out of memory.** CI's app job was killed (exit
  137) while its ~1,400 tests ran in one process: every window, page and dialog a test made stayed, with its backend
  and the sandbox-ai modules that backend had loaded (about 15 MB a window). Three causes, fixed where they were: the
  project bar's list of projects was a QObject of Python's own whose signal was connected to a lambda that referred
  back to the bar - a cycle through a connection held in C++, which Python's collector cannot see (it is now the bar's
  child and goes with it); three caches of the app (the Board's options, the launcher's option arities, the names of
  secrets and profiles) were keyed by `id()` and held their backend for good (now weak); and the tests deleted their
  windows with `deleteLater()` and `processEvents()`, which leaves them undone outside an event loop, while Python's
  collector runs only on a timer of the GUI thread (since 0.1.80). The tests' conftest now ends what a test made of
  the app's windows, pages and dialogs after every test (shut down, hidden, deleted, collected). The whole suite:
  peak RSS over 2.1 GB a third of the way through and growing (CI's runner has 7 GB) -> 0.68-0.84 GB, flat across
  the files; a window made and closed four times leaves no backend and
  no top-level widget behind (a test). A window's State, deleted with it, is no longer handed to the next one
  (`state.current()`); the panel title bars' tooltips are escaped like every other (test_review5 failed since 0.1.81).
- **App: a host where nothing runs is not asked for questions.** Questions only come from running sandboxes: a host
  whose starts were read with none running, starting or paused is no longer asked for its questions every 5 s; its
  starts are still read on their schedule (every 10 s while the Sandboxes page shows, every minute otherwise - in the
  tray too, which read no host's starts before), and as soon as one shows a start, its questions are read at once and
  from then on. A host the app has just started something on (any terminal it opens, Resume on the Sandboxes page) is
  asked for 2 minutes whatever its last look said; a host that lists a question, or whose starts could not be read, is
  asked as before. This machine the same way: while its registry lists no running sandbox, the scan every second
  reads no question folder and no policy.
- **App: the questions are not shown again when nothing changed.** The scan of this machine's questions every second
  redrew the page (both tables, the buttons, the counts said to the window) even when nothing had changed; now only
  when something did, or while a question's time runs (its countdown). The page's first scan runs in the background
  like every later one (the window shows meanwhile).
- **App: background reads reuse their threads.** Every read (2-3 a second) started a thread of its own; a thread that
  finished one now waits up to 30 s for the next (at most 8 wait). Never a queue: a call starts at once, on a waiting
  thread or a new one, however many run (a host that hangs holds up no other read), and the call's function starts
  before its caller goes on, as a thread's start did. Everything else stays: reads versus work, cancelling, timeouts
  and late results dropped, results on the GUI thread, the collector on the GUI thread only. The Credentials page
  handed a secret's value to a host's `secrets set` through a closure it emptied right after (a race the thread start
  used to win): the value is now handed over.
- **App: icons drawn once.** The navigation's and menus' icons were painted anew each time one was asked for (about 130
  at the start); each name, colour and size is painted once now.
- **App: a row of buttons that wraps is measured once.** Qt asks a page's wrapping rows (FlowLayout) for their height
  dozens of times when the page is shown (the Terminals page: 50 times, 20 ms in Python); each width is measured once
  now, and again when a button in it is hidden, shown or changes its size.
- **Not changed, measured:** under the application's style sheet a widget costs about six times as much to make as
  without it (the 14 pages made later: 77 ms unstyled, 460 ms styled); the one rule that sets the font size of every
  widget is a quarter of that, but it also overrides the sizes 9 places set themselves, so dropping it would change
  how they look. Making the tabs of a page after its first only when they are shown would save a third to four fifths
  of the Kits, Hosts, Images and Credentials pages - but the page's first read fills those tabs (the counts on their
  titles, the editor's document, the overview of every kind), so it would only move their cost from idle time into
  the click on the page; not done. The Start page's form of options (35-60 ms of its making) is read and written by
  every part of the page at once; not made lazily. Importing the modules of the pages made later only then would save
  about 6 ms; a full collection of Python's garbage takes 20 ms with the window's 88,000 objects (rare); the 80 ms
  between show() and the first paint are Qt's own (layouts, styling, the backing store).
- **Measured, before -> after** (offscreen Qt, Python 3.13, PySide6 6.12, the probe above; startup alternated with
  0.1.82, 7 rounds; idle 60 s with the Sandboxes page shown or the window hidden as in the tray; this machine was
  shared, at times with a load average of 4-8):

  | | 0.1.82 | 0.1.83 |
  |---|---|---|
  | first paint after the first import, median of 7 | 0.67 s (0.62-0.82) | 0.63 s (0.52-0.70) |
  | usable (first second without a stall over 100 ms) | 0.61 s (0.55-0.75) | 0.59 s (0.46-0.69) |
  | window built / the Approvals page in it | 0.20 s / 54 ms (37-78) | 0.20 s (0.15-0.26) / 17 ms (13-30) |
  | idle, Sandboxes page shown: CPU of the app / commands a minute | 1.6-1.8 % / 25 (21 ssh, 4 podman) | 1.6-2.1 % / 13 (9 ssh, 4 podman) |
  | idle, in the tray: CPU / commands a minute | 0.8 % / 15-16 ssh | 0.5-0.7 % / 4 ssh |
  | threads started for the background calls (107 a minute shown, 76 in the tray) | one per call | 0-1 a minute |
  | timer wakeups a minute (shown / tray) | 135 / 130 | 133-135 / 130-132 |
  | longest stall after a page switch, second round (quiet machine / load 4-8) | 62-129 ms / 69-110 ms | 0-53 ms / 106-138 ms |
  | the app's whole test suite, peak RSS | over 2.1 GB a third of the way, growing | 0.68-0.84 GB, flat |
  | a window made, shown and closed: what stays, per window | 10-15 MB, 7,400 Python objects | ~1.5 MB, none |

  In the probe the one answering host runs nothing, so it is no longer asked for questions (12 ssh a minute fewer
  shown, 11 in the tray); the slow and the unreachable hosts are asked as before (their starts cannot be read). The
  timer of the questions' scan (60 wakeups a minute) stays: the probe has an open question here, whose countdown is
  shown every second. The page switches vary with the machine's load by more than they differ.
- **Tests**: tests/test_performance.py - a closed window goes entirely (four windows made and closed leave no backend,
  no top-level widget, no growth of Python's objects), the caches keep no backend alive, calls reuse their threads and
  still run side by side (a waiting one holds up no other; results on the GUI thread), the questions page does nothing
  while nothing changes (no question folder or policy read while nothing runs here), a host where nothing runs is not
  asked for questions (and is asked at once when a start shows up, when the app starts something there, or while it
  lists a question), in the tray only the starts of such hosts are read, a row that wraps is measured once until it
  changes, an icon is drawn once. tests/conftest.py sweeps what each test left (see above).

## From 0.1.82

0.1.82 carries everything listed for 0.1.81 (docs/releases/v0.1.81.md, which carries 0.1.80, 0.1.79 and with it
0.1.78), and on top a second performance pass over the desktop app, measured with the same probe as 0.1.81:

- **App: the window is there in about half the time.** The window made all 18 pages before it showed (about 0.45 s,
  then 0.2 s more to style them all). It now makes the first page, the Board and the open questions (their panels
  are the window's) and the Sandboxes page (the tabs follow it), shows, and makes the other pages afterwards: one at a
  time, only while the mouse and the keyboard rest (0.4 s) and the reads of the pages made so far do not keep Python
  busy; a page asked for earlier (shown, a tour, a link from another page) is made at once. A page made later is the
  same as one made with the window (linked with the other pages, its (?)s, its kept tables, filters and splitters,
  the current project); the self-test still makes every page. First paint after the first import: 1.04-1.14 s ->
  0.59-0.68 s (median of 5: 1.11 -> 0.64 s); the window itself 0.47 -> 0.22 s, styling it 0.19 -> 0.06 s.
- **App: the hosts are read through their shared SSH connection again.** 0.1.81 ran ssh itself for every read of a
  host (instead of `sandbox-ai hosts run`) but without the shared connection that `hosts run` uses (one ssh master
  per host, ControlPersist): every read every 5 s was a new TCP connection, key exchange and login on the host. The
  app now asks sandbox-ai's hosts module for the host's master (started when needed, checked again only when it has
  carried no command for 30 s) and sends each read through it; a master that refuses is told to take no new sessions
  and the read runs on its own connection, as `hosts run` does it. Measured against a local SSH server, per read:
  24 ms of ssh CPU and 138 ms -> 6 ms and 13 ms; no login on the host per read.
- **App: escaping a text for the screen is 17 times faster** when there is nothing to escape (most texts), and a long
  table measures its columns without an index made for every cell: the Approvals page with 200 answered questions
  is made in 35-55 ms (80 ms before), every fitted table gains.
- **App: style sheet.** Applied once at the start (after the first pages are made) and once per theme change (cleared
  first: a sheet over a sheet is about six times slower); 12 widgets carry a sheet of their own (none per row). Under
  the application's sheet a widget is styled again each time it is put into another, so a page made later is put
  into its frame once, already in its place in the window, and the watch of the mouse and keyboard is paused while a
  page is made (its widgets' events through a filter in Python doubled the time).
- **Not changed, measured:** merging a host's reads into one SSH round trip saves about 6 ms of CPU per merged read
  once the shared connection carries them (the reads' `sandbox-ai` starts on the host stay the same), so the reads
  stay apart. In the tray only the open questions are read (5 s per host; a host that does not answer is asked less
  often), as before.
- **Measured, before -> after** (offscreen Qt, Python 3.13, PySide6 6.12; idle 60 s with the Sandboxes page shown or
  the window hidden as in the tray; the probe's hosts cannot use a shared connection, so the commands a minute are the
  same - the cost of each is what changed):

  | | 0.1.81 | 0.1.82 |
  |---|---|---|
  | first paint after the first import (Podman taking 3 s), median of 5 | 1.11 s (0.90-1.47) | 0.64 s (0.59-0.68) |
  | window built / style sheet applied | 0.47 s / 0.19 s | 0.22 s / 0.06 s |
  | usable (first second without a stall over 100 ms) | 1.09-1.36 s | 0.54-0.75 s |
  | pages made later (14), each, in idle time | - | 20-100 ms (rarely 120 ms) |
  | idle, Sandboxes page shown: CPU of the app / commands a minute | 1.6 % / 25 (21 ssh, 4 podman) | 1.6 % / 25 (21 ssh, 4 podman) |
  | idle, in the tray: CPU / commands a minute | 0.7 % / 16 ssh | 0.8 % / 16 ssh |
  | timer wakeups a minute (shown / tray) | 137 / 130 | 135 / 130 |
  | one read of a host: ssh CPU / time (local SSH server) | 24 ms / 138 ms | 6 ms / 13 ms |
| memory over 10 minutes of polling (window shown) | flat (0.1.81: 212 -> 213 MiB in 30 min) | 220 -> 220 MiB |
  | longest page-switch stall, first round / second round | 72-130 ms / 0-189 ms | 127-130 ms / 62-155 ms |

  The page switches vary from run to run on this machine by about as much as they differ; in the first round of a
  lazy window part of the stalls are pages being made while the probe rests between two switches.
- **Tests**: tests/test_performance.py - a host is read through its shared connection (checked once, then trusted
  while it carries the reads; asked again when it is older), a shared connection that refuses is left and the read
  runs on its own, a lazy window makes only its first pages and the others when they are shown or asked for by name,
  a lazy window ends the same as one made at once (the (?)s, the kept tables, the frames, the links between pages), a
  page made later shows the current project, the other pages are made in idle time and never while the mouse or the
  keyboard is used. CI: the fakes of host commands take host_run's ssh command line; the rebirth test of the
  sessions never asks a real Podman.

## From 0.1.81

0.1.81 carries everything listed for 0.1.80 (docs/releases/v0.1.80.md, which carries 0.1.79 and with it 0.1.78), and
on top a performance pass over the desktop app: measured first (a probe with 3 hosts - one answering, one slow, one
unreachable -, a Podman that takes 3 s, 30 kept starts, a 5,000-record connection log, a folder of 20,000 files, a run
with 200 answered questions, 7 LLM servers with 70 models), the worst fixed, measured again.

- **App: a look at another host no longer starts Python twice.** Every read of a host (its open questions every 5 s,
  its starts every 10 s while the Sandboxes page shows, and every other host command) ran `sandbox-ai hosts run` -
  `main.py`, then `hosts.py`, about 0.1 s of CPU each - only for it to start ssh. The app now builds the same ssh
  command line with sandbox-ai's own hosts module and runs ssh directly (an unknown host, an older sandbox-ai or ssh
  missing: the command as before, so its messages stay sandbox-ai's). Idle with 3 hosts: 0 Python starts a minute
  (21 before), the CPU of what the app starts from 4.1 % to 0.2 % of a core.
- **App: one Podman listing for every look, kept 10 s.** The registry of runs and the kept sessions each asked Podman
  (`podman pod ps`) on their own, with a cache of 2 s, at every look (every 3 s while the Sandboxes page shows): about
  10 Podman listings a minute with a stale Podman run and a kept Podman session. They now share one listing, kept 10 s;
  after an action (stop, resume, Refresh) the next look asks afresh. Measured: 4 a minute.
- **App: nothing is rebuilt or repainted when nothing changed.** The Sandboxes tree was taken down and built again
  at every look (every 3 s, and at every answer of a host), the navigation's Approvals entry got a new icon at every
  scan of the questions (every second), so both were laid out and repainted all the time: ~700 repaints and ~620 timer
  wakeups a minute in an idle window. The tree is now updated in place (only the cells that changed; selection, folds
  and scroll stay), the Approvals entry only when the count changes, the host filter and the Hosts table only when a
  host or a row changed (an open host list no longer closes under the mouse every 10 s). Idle window: no repaint.
- **App: fewer wakeups.** The Connections and Terminals pages' timers tick only while the page is shown (their reads
  did so already), and the cycle collector's check on the window's thread (every 250 ms) backs off to every 2 s while
  little is allocated.
- **App: the approvals' scan every second costs a stat.** A run's folder of questions whose listing has not changed
  (older than 2 s, so a coarse clock cannot hide a change) is not listed and matched again: with 200 answered
  questions the scan took ~1 % of a core; and a kept start's record is read by its id instead of reading every start's
  record to find it by name (30 kept starts: 900 file reads per look before, 30 now). The approvals history is a
  model-backed table (a long history fills in one step).
- **App: the Board's properties are a real panel again.** The inspector (a part's properties) can again be dragged
  to another edge of the window (left, right, top, bottom), undocked as a window of its own (drag its title out, double
  click it, or its undock button) and closed; its title bar's arrow folds it to a slim strip at the window's edge (its
  title bar alone when it shares its column with another panel). A click on a part unfolds it, shows it again when it
  was closed and brings a floating one back where it was, never taking the canvas's keyboard; Esc or a click on the
  empty canvas fold it only while it is docked. Where it is, folded or not, its width and a floating one's place are
  kept for the next start. View > Panels > Properties as a separate window is gone (undocking does it); View > Panels
  > Board: properties shows or closes it like the other panels.
- **Measured, before -> after** (offscreen Qt, Python 3.13, PySide6 6.12, this machine; idle 60 s with the Sandboxes
  page shown, or the window hidden as in the tray; "started" is what the app runs: Python for `sandbox-ai`, ssh,
  podman):

  | | before | after |
  |---|---|---|
  | idle, window shown: CPU of the app / of what it starts | 3.8 % / 4.1 % | 1.6-2.0 % / 0.1-0.2 % |
  | idle, window shown: commands started a minute | 31 (21 Python, 10 podman) | 25 (0 Python, 21 ssh, 4 podman) |
  | idle, window shown: repaints / timer wakeups a minute | 700 / 615 | 0 / 135 |
  | idle, in the tray: CPU of the app / of what it starts | 1.2 % / 2.5 % | 0.7 % / 0.0-0.1 % |
  | idle, in the tray: Python starts / timer wakeups a minute | 15 / 388 | 0 (15 ssh) / 132 |
  | window built / first paint after the first import (Podman taking 3 s) | 0.65 s / 1.06 s | 0.54 s / 0.95-1.18 s |
  | longest stall after a page switch (18 pages, twice each) | 140 ms (MCP), 132 ms (Terminals) | 86 ms |

  Unchanged and within bounds: every page's own switch takes 3-40 ms, the Files page lists 20,000 entries without a
  stall, the Board repaints 43 parts in 8 ms and drags at 8-11 ms a step. Memory over 30 minutes of polling (window
  shown): 212 -> 213 MiB (before: 214 -> 225 MiB).
- **Tests**: tests/test_performance.py - a host is read through ssh without a Python start (and an unknown one through
  sandbox-ai's command), one Podman listing serves runs and sessions for a while (and an action asks afresh), a quiet
  folder of answered questions is not listed again (and a new answer is seen), the Sandboxes tree is updated in place,
  an idle window starts no sandbox-ai command, repaints no navigation and keeps its tree, every page shows within 1 s.

## From 0.1.80

0.1.80 carries everything listed for 0.1.79 (docs/releases/v0.1.79.md, which carries 0.1.78), and on top the fixes of
an independent review of the desktop app's threads and background work:

- **App: the window shows at once, whatever Podman does.** The Sandboxes page read what runs on the window's thread
  while the window was built; that read asks Podman about a run whose launcher is gone and about a kept Podman
  session, so with a slow or hung Podman nothing (no window, no tray) appeared for 9–40 s. The first read now runs in
  the background like every later one: the page says "Reading what runs on this account…" until it is back, and the
  tabs of starts that ran already then get no tab of their own (as before). Measured: built in 0.5 s with a Podman
  that takes 3 s (6.9 s before) and in 0.4 s with one that takes 8 s (about 20 s before).
- **App: reads are not work.** Every background call is either work a human started (an install, a build, a start
  or stop, a copy, a write, an answer, a doctor or privacy check) or a read or poll (a list, a status, a refresh).
  Only work shows in the status bar's busy bar ("Running: …") and makes closing the window ask "Still at work: … Quit
  anyway?"; reads and polls never do (the Terminals page counted as busy three quarters of the time and quitting asked
  about a mere listing). Quitting ends the reads still running without a question, with everything they started (no
  more `sandbox-ai hosts run`, ssh or `podman pod ps` left running after the app, adopted by PID 1: 7–8 before, none
  now); the work is stopped after the question, as before.
- **App: "Stop and quit" no longer freezes the window.** Stopping the work (up to a grace period and 10 s) runs in a
  thread; the window says "Stopping the work that runs, then quitting…", takes no more input and closes when done.
  Only work is waited for, not the reads.
- **App: no memory grows while it sits in the tray.** Each background call (2–3 a second while polling) kept its
  thread object, its callbacks and what they referred to for good (~3.7 KiB each, ~0.8 GB a day): a callback
  connected to the call referred to the call itself. Calls let go of everything once they reported (on the window's
  thread): 5,000 calls leave nothing alive (5,000 before). Python's cycle collector runs only on the window's thread
  (in a worker thread it could delete a dialog's or page's Qt objects and crash the app).
- **App: big tables fill in one step.** The Files page (a folder of up to 20,000 entries) and the Connections page
  (up to 5,000 records) show their rows from a model instead of one item per cell: filling 20,000 rows takes 0.06 s
  (about 1 s before, plus the click's own work), selecting them all 0.5 s (39 s). A folder's rows are made in the
  listing's thread; the Connections filter applies after a 200 ms pause in typing and reuses each record's row.
- **App: the preset catalogue is quick.** Each preset of sandbox-ai was checked by building sandbox-ai's whole option
  parser again (the Gallery took 0.6 s to open, the Start page 0.2 s to show): the parser is built once and the result
  kept per option list (the Gallery opens in 0.18 s the first time), and the Start page's preset list is made in the
  background.
- **App: no crash at the end with terminal tabs open.** Quitting could end in "QObject: shared QObject was deleted
  directly" and a segmentation fault: Python's cleanup at the end of the interpreter deleted web views after QtWebEngine
  had gone. The terminals' pages, web views and profiles are now deleted in QtWebEngine's order, and the window and
  every other top-level widget by Qt, while the application still runs. ("The requested buffer size is too big,
  ignoring" is QtSvg's, drawing an SVG icon of the desktop's theme; the app has no SVG of its own: harmless.)
- **App: no local event loops in clicks.** Listing a folder on the Files page and opening a terminal tab (which waits
  for the check whether Chromium's sandbox can start) no longer wait in a nested event loop: the folder shows when
  its listing comes, the tab when the check is back; the same command asked for twice meanwhile opens one tab.
- **App: smaller fixes.** A worker that raises SystemExit (argparse, `sys.exit`) reports an error instead of ending
  silently (its buttons stayed disabled and its page busy for good). A background call that times out tells its page
  at once but keeps its buttons disabled until its thread really ends (a second click could run the same action twice),
  and buttons shared by two calls work again only when both ended, in the state they had. The Activity page asks a host
  one look at a time also while a filter is typed (older looks no longer pile up), and the Board's local dry runs run
  one at a time. Polls pause while the window is in the tray or minimised (the approvals go on: questions must be
  answered), the Sandboxes page reads less often while hidden and the Activity page not at all; a host that does not
  answer is asked less and less often (the approvals at most every 30 s, the Sandboxes page's look at most every
  5 min; Refresh asks at once). The Board's security score button is a disclosure (an arrow), like every other button
  that shows or hides something.
- **Tests**: the page sweep now fakes the backend before the window is built (with a fake `podman` that takes 10 s,
  a run, a question and a kept Podman session), selects a row in every list before clicking, allows 0.5 s per click
  (1 s before), and adds an idle phase (the polls never stop the event loop for 0.25 s and never count as work) and a
  quit phase (no question about work, no process left). New tests: 1,000 background calls leave nothing alive, a
  timeout keeps the button, shared buttons, SystemExit in a worker, Stop and quit in a thread.

## From 0.1.79

0.1.79 carries everything listed for 0.1.78 (docs/releases/v0.1.78.md; 0.1.78 was never published: it only marked
the state installed from the repository while the reviews went on), and on top:

- **Version numbers** go up with every larger change from now on: x.y.z → x.y.(z+1); after x.y.249 comes x.(y+1).0,
  after x.49.249 comes (x+1).0.0 (`scripts/bump_version.py`).
- **LLM servers: what they have loaded and use now.** `sandbox-ai llm status [NAME] [--json] [--watch SECONDS]` reads
  every registered server at the same time (5 s per request; one that is down or hangs holds up no other) and shows
  the loaded models with their size and the memory they take, and what its API reports: Ollama the VRAM and RAM of
  each loaded model (`/api/ps`), vLLM the KV cache and the requests running and waiting (`/metrics`), llama.cpp its
  slots and with `--metrics` the requests (in router mode the memory per device and the devices' total and free),
  LM Studio the loaded instances (`/api/v1/models`, 0.4 and later; its models' sizes too). What an API does not
  report is said ("not_reported"), never guessed; the host's total RAM/VRAM is not reported by these APIs.

  as a line per server on the LLM servers page (read in the background every 20 s while it is shown) and beside a
  start with `--llm` (app: below the Sandboxes table for the selected start; web: LLM status in its row); `sandbox-ai

- **App and web: every model of a server is offered.** The Model choice beside the agent (Start page, Board) and a
  preset's LLM value listed at most 30 models of a server; now all of them, in a popup that scrolls (20 rows) and that
  typing filters (any part of the name, any case); the dialog's default model and the wizard's model too. The web's
  model choice of a new start lists every model with its size and whether it is loaded, and has a filter.
- **App, Board**: the right mouse button drags the view like the middle one (a right click without moving opens a
  menu: add a part there, select all, fit, zoom 100 %, arrange, undo/redo; on a part Set up step by step…, What is

  edge. Selecting a part brings back the inspector's panel when it had been closed (floating or docked).
- **App: the window keeps answering while work runs.** A kit change (Add plugin, a marketplace, a skill, a hook;
  cloning a marketplace takes a while), a host's update or installation show a busy bar naming what runs, a Cancel
  that ends the command with everything it started, and what sandbox-ai writes as it comes; the outcome is said in
  the page (wrapped, plain text), one change runs at a time and a second click starts nothing. The status bar says
  which pages have work running ("Running: Kits & plugins…"). What still ran on the window's thread now runs in the
  background: the registry reads that may ask Podman about ended runs (the project switcher and menus, the Files
  page's folders, the Activity page's sources, the Board's live rows, Start at login); the approvals' scan and the
