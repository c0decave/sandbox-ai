# sandbox-ai 0.1.84

**The first public release of sandbox-ai.** 0.1.77 to 0.1.83 were never published: this release carries all of them
(each in full below). The highlights:

- **Sandboxes:** Claude Code, Codex and OpenCode in rootless Podman or Bubblewrap with Firejail, a default-deny network
  behind a TLS-inspecting connection proxy, approvals for everything else (or `--ask allow` / `--ask off`), secrets
  that never enter the sandbox, a privacy check of every push, canaries, rulesets per HTTP request and MCP tool call.
- **During a run:** workspaces (folders, single files, named), MCP servers and helpers attached without a restart
  (`workspace add`, `mcp attach --live`), `net allow`, limits and devices — also on stopped sessions for their next
  start; every command finds a start by the name `sandbox-ai ps` shows.
- **Sessions:** codenames like `brisk-otter-lantern`, `ps` grouped and coloured, orphaned starts shown, stopped and
  resumed, leftover pods cleaned up (`gc`), the directory you start in becomes `/work`.
- **Hosts:** manage other machines over SSH — install and update (also `--from-here`, with or without sudo), their
  doctor with the installed version, remote starts, presets per host.
- **Kits & plugins:** a marketplace browser over sandbox-ai's, the kits', Claude's and Codex's marketplaces.
- **Local LLMs:** Ollama, LM Studio, llama.cpp, vLLM and any OpenAI-compatible server, with model lists, sizes, what is
  loaded and how much RAM/VRAM it uses (`llm status`), for OpenCode and Codex, with keys kept in the proxy.
- **MCP catalogs:** signed catalogs, the catalog of every server shown, unsigned ones added on request.
- **Desktop app and web UI** with the same features as the command line: Board, Start page, Sandboxes, Approvals,
  Files (two panes), Credentials, Kits, LLM, VPN/Tor, Images, Teams, Hosts, Settings, help on hover and tours, English
  and German; the app responsive (everything slow runs in the background), fast (first paint ~0.6 s, near-idle CPU).
- **Security reviews:** six rounds of independent security, correctness and usability reviews; their findings are
  fixed (proxy Host checks, kit link chains, trust reviews that show every key, login sync only for the same account,
  and more — see the details).

**Command line**

### Presets: every built-in preset tested with every agent and backend

- Presets: a folder, file or device that is a preset's default and does not exist on this computer (e.g. `~/c0de/axross` in a preset of your own) is no longer created as an empty workspace at the start. An optional one is left out with a note naming `--preset-value NAME=PATH`; a required one stops the start with a message that says to create it or give another. The same applies when the app's form passes the default it showed.
- `sandbox-ai presets check` now also reports the MCP servers (`--mcp {value}`) and publishing logins (`--publish {value}`) a preset's options name that are not set up yet, with the command to add each and, for an optional value, how to leave it out (`--preset-value search=`). Before, it said "ready" and the start failed.
- `sandbox-ai presets check` gives the preset's hint (the exact command that creates the profile or server) when a required value such as `tor` or `llm` is missing. It also notes a folder you named that does not exist.
- A project file whose `"workspaces"` names a folder the command line or a preset already gives, in another spelling (`~/src/lib` and `/home/me/src/lib`), now adds it once. Before, the start was refused with "Workspaces must not overlap: X and X".
- Preset notes corrected: archivist-1995 and data-ml now include the `sandbox-ai build` step; onboarding-buddy and pixel-art-factory say that screenshot tools and Pillow come with the media variant; local-api names `sandbox-ai llm add ... --anthropic`.

- The app shows its version at the bottom right of the window (and sandbox-ai's where they differ).
- `install.sh` (and so `sandbox-ai update`) says how to install or update from a checkout when the repository has no published release yet.
- Docs: README and README_DE complete for every command and option (990 checked), the quickstarts, the app README, the learning video's storyboard and the screenshots as the app is now.

### Security fixes (review round 5)

- **A sandbox's Claude login goes back to the host only if it is a refresh of the same account.** The live login
  sync wrote a changed `~/.claude/.credentials.json` of a sandbox back to its source (the host's login or the
  login store) whenever the source still held what the two had shared, without asking whose login it was: a
  `/login` with another account inside a sandbox replaced the host's login, and an agent could plant its own
  account's tokens there, so that Claude on the host then talked to that account. Now the launcher asks
  Anthropic, on the host and the way Claude Code does (`GET https://api.anthropic.com/api/oauth/profile` with
  the access token, TLS verified, no redirect followed, 5 s), which account and organization the sandbox's new
  token belongs to, and compares it with the source's (its own `~/.claude.json` `oauthAccount`, else the same
  question with the source's still valid token, once per run). Only the same account is written back, during the
  run, at its end and at the next start of a killed run; another account, or one that cannot be checked, stays in
  the sandbox and the source keeps its own login (said after the run, never with a token). If Anthropic cannot be
  asked, nothing is written back and it is asked again at the next change, at most once a minute, and once more
  at the end. Not covered: an agent that refreshes the login itself could still pair the new access token of the
  right account with another account's refresh token, which Anthropic cannot check without using it up.
- **No credential goes with a `Host` header naming another server.** The proxy added `--api-key`, `--llm` (key
  and header secrets), publish and Git login credentials by the TLS name it checked alone; a request to
  `mine.hf.space` with `Host: other.hf.space` reached the other tenant with your key (domain fronting). Such a
  request is now refused with a `sandbox-ai: ...` 403 and logged (case, a trailing dot and the default port
  don't count; plain http to an `--llm` server needs its name or pinned address).
- **A request question names where the request goes:** the server the proxy verified (over plain http, the
  address), not the `Host` header the agent wrote; a different `Host` is shown as an unverified claim, and the
  connection log records the real URL with the claim as `host_header`.
- **A writable `--mount`, `--state-dir` or MCP server folder that holds sandbox-ai's launcher** (e.g. `~/c0de`
  holding a checkout, a venv holding the package) is refused, as a workspace already was: the agent could
  rewrite the launcher and the next start would run it on the host. Read-only mounts stay allowed.
- **Test connection sends no key over plain http to a public address:** `wizard models --url` (the app's and the
  web's Test connection) now checks the URL as `llm add` does before a key leaves; `--insecure-http` (in the web:
  the ticked box, asked first) allows it.
- **Web:** replacing a publish login, an identity's login or an MCP server of the same name is asked first
  (`login-replace`, `mcp-replace`); a start's terminal is read for the "not trusted" offer only until the sandbox
  runs, so an agent's output can't raise it; a catalog's text can't forge another row of the MCP table (`mcp
  catalog` prints one line per entry, its texts printable); a request must send its headers within 10 s and its
  body within 30 s, and one address other than this machine's holds at most 16 connections. `mcp add` says when
  an entry gets the full outside network.
- **Starts sandbox-ai builds itself keep their `/work`:** team members, `resume`/`restart` (the folder that was
  `/work` at the first start is recorded), web starts also without a workspace field, and starts on another host
  whose sandbox-ai is 0.1.78 or later pass `--workspaces-as-given`, so a project file in the directory they run
  from (the web service's, the SSH login's HOME, one the agent wrote later) never takes them over.
- **Proxy, smaller holes closed:** an `--llm` key below a path prefix and an allow rule for some paths no longer
  go by a path that servers read differently (`/tenantB/x%2F..%2F..%2FtenantA/...`: a dot segment after
  decoding); SSH to a public Git host is refused also after a junk line before the client's banner (any early
  line counts, and the server's banner too); `git push -o` options (GitLab's merge request title and
  description) go through the privacy check with the commits.
- **`hosts install --system --prefix`** checks every folder from `/` down to `PREFIX/lib/sandbox-ai`: each must

### Fixes: a sandbox whose supervisor died

- **A running sandbox no longer loses its run directory.** When a sandbox's launcher (its supervisor on the host)
  was killed without its cleanup (SIGKILL, the OOM killer, a stopped cgroup), Podman kept its container running,
  but the next `sandbox-ai list` (the app asks every 10 seconds), `workspace add`, `net` or the web took the
  missing PID for the end of the run and deleted its run directory under `$XDG_RUNTIME_DIR/sandbox-ai/runs`, the
  control socket with it: the sandbox showed as stopped and no command reached it any more. A run directory now goes
  only on positive evidence: its launcher's PID is gone (or another process has it) where this process sees the
  launcher's processes (run.json and session.json record the PID namespace; inside a sandbox or a container nothing
  is decided for records without one), and with Podman no container of its pod runs any more (Podman answered).
  Then its browser directory, its leftover pod and its end (history, `exit.json`) go with it.
- **Orphaned starts are shown and can be ended:** a start whose supervisor is gone while its pod runs is
  `orphaned` in `sandbox-ai list` (with its run), a session's terminal can still be attached to, and
  `sandbox-ai stop NAME` stops its pod (`podman pod stop`, the agent ends as at any stop), removes it, records the
  end and removes the leftover run directory; `sandbox-ai resume NAME` then continues it with its HOME and its last
  conversation (`resume` of an orphaned start does both, and says so; before, `stop` said "not running"). A running
  sandbox-ai pod that no start knows any more (`gc` names it) is ended with `sandbox-ai stop POD`. A stopped start
  that keeps no HOME is never removed on its own while its pod may still run.
- **Pods are no longer left behind unnoticed:** every pod carries the label `sandbox-ai.run`; when Podman refuses
  to remove a pod at the end of a run (once more without `--time` for Podman before 4.0), the launcher says so with
  the command that removes it. `sandbox-ai gc` removes sandbox-ai's own pods that nothing runs in any more (the
  `agent-…` pods of killed launchers and reboots: `podman ps -a` showed their infra containers as `Exited (0) 292
  years ago`), never a pod that runs, is being created or is not sandbox-ai's, and names the running pods no start
  knows (with the command that ends them). `gc --dry-run` shows them first.
