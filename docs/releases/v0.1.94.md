**Tor starts work.** Every start with a Tor profile failed: the Tor container's data directory was a tmpfs with
`uid=` and `gid=`, which Podman's `--tmpfs` does not take ("unknown mount option"). The runtime now gives the
directory to debian-tor itself. A live test starts tor in the real container as a start does (a CI job, with a real
Tor check through the Tor network).

**.onion names for MCP servers behind Tor, and no server back outside Tor during a run.** A fetcher behind Tor
refused every .onion URL: tor maps them into 10.192.0.0/10, which the server took for your local network (and the
model went on to the clearnet). Behind a Tor profile, and only there, an MCP server's container and a command
server's or agent's sandbox are now told `SANDBOX_AI_TOR=1` and `SANDBOX_AI_TOR_VIRTUAL_NETWORK=10.192.0.0/10`, so
that a fetcher takes exactly that network. A running server is used again only behind the VPN its own definition
names (one of `"vpn": TOR` started meanwhile with `mcp start NAME --vpn OTHER` was used by a Tor start), and a server
that a running VPN or Tor start reaches is never started again without that VPN (another start, `mcp start` without
`--vpn`: on macOS the running start would have reached it in the same volume). Behind Tor an address the Tor Project
does not confirm as an exit stops the run during it too, and a Tor container that ends during the run is said and
written to vpn.jsonl (its kill switch stays in the pod's namespace: the sandbox has no network, nothing falls back).

**A model server in your network behind Tor:** `--vpn-bypass-tcp ADDRESS:PORT` reaches exactly one IPv4 address and
TCP port of your local network past Tor (the `--llm` server on another machine). The rest of your network stays
closed, UDP and IPv6 too, everything else goes through Tor, and the connection proxy still checks and logs it. The
board offers it from the refusal. The kill switch is tested in the kernel (nftables in a network namespace, every
way out tried).

**Kill switch for running sandboxes:** `sandbox-ai net cut [RUN] remote|local|api|all|off`, `--all-runs` for all of
them. `remote` cuts the internet, `local` the local network and the host's ports, `api` leaves only the model API,
`all` cuts everything (with the run's MCP servers, helpers and team members); `off` gives back exactly what the run
had. It never widens anything; the firewall, the connection proxy and the supervisor hold it (open connections the
cut forbids end too), out of the agent's reach. In the app: a Kill switch menu on the Sandboxes page, and an
**emergency stop** (File menu, Ctrl+Shift+X, a button in the header) that cuts every sandbox here and on your hosts
at once, without a question.

**Developing with containers inside (experimental):** `--nested-containers`, with `SANDBOX_AI_EXPERIMENTAL=nested-containers` in the environment until its live test passes on every platform, lets one sandbox run Podman, Buildah and `unshare -rn`
(the agent is root of a user namespace of its own; the proxy's and tor's IDs are never mapped). The containers share
the sandbox's network: its firewall and connection proxy hold for them too. Refused with Bubblewrap, behind Tor, in
the high and paranoid modes and where the administrator's policy forbids it; the board's score drops by 10.
`--tmp-size SIZE` sets the size of /tmp and /var/tmp. The image recipe `dev` brings Podman and the test tools;
`tests/devtools` has helpers for sandbox-ai's own tests (a window manager check on a virtual screen, a fake
internet, a model server mock, a distro matrix for the installer, a throwaway Gitea).

**Your own images from Docker Hub and other registries, or from your own Containerfile:** `sandbox-ai images pull
REFERENCE [--as NAME]` pulls an image once and records it pinned by its digest; `sandbox-ai images build-image NAME
--file CONTAINERFILE` pulls every `FROM` once, pins it by digest and records the result by its ID; `images list` and
`images remove`. Nobody has reviewed these images: each is marked UNCHECKED wherever it appears, and no start ever
pulls one. Two uses:

- **Services beside the agent:** `--service NAME:image=IMAGE,port=PORT,...` (repeatable; Postgres, Redis, SearXNG, a
  test target) runs a container in the sandbox's pod, reached at `localhost:PORT`. It shares the sandbox's network
  and so its firewall, connection proxy, allow-list, approvals, kill switch and VPN; it starts only once the
  supervisor's firewall and proxy are up and before the agent (which waits for its port), with no capabilities, no
  new privileges, a read-only root, a numeric user none of the firewall's own, the sandbox's resolver, its data in a
  tmpfs (or a volume kept with the start), its own memory, CPU and process limits, variables and secrets from
  `sandbox-ai secrets` (never in the project file); it is removed with the run and its output kept in the log
  directory. `sandbox-ai list`, the dry run and `SANDBOX_AI_SERVICES` (for the agent) name them. Refused with
  Bubblewrap, with `--podman-url`, behind Tor and in the mode `paranoid`.
- **A variant on a base image of yours:** `sandbox-ai images new NAME --from AGENT --base IMAGE` (Debian 12
  bookworm images, e.g. `python:3.12-bookworm`): `sandbox-ai build NAME` prepares the image (programs the sandbox's
  setup runs reinstalled from Debian, Node.js added if missing), builds the agent's layers on it and then the
  variant's extension. The sandbox's own supervisor runs from that image's programs: refused in the modes `high`
  and `paranoid`, and every start says so.

**Approvals you can change while it runs.** A question nobody answers is no longer a refusal for the whole run:
the request is refused, refused at once for 2 minutes (the agent does not wait again), then asked again. The
Approvals page is rebuilt: which sandbox it is about (the active tab's, one chosen, or all) with its mode, VPN/Tor and
kill switch; the questions say *why* they are asked (the network settings, which rule of which ruleset, a canary)
and how long an Allow holds; **Blocked** lists every refusal of the run with its reason and the process that tried,
with Allow for this run, Allow always (an exception rule, shown before it is written), Ask again and Deny for this
run; **Allowed now** shows what the run may reach and revokes it. `sandbox-ai approvals blocked|decided|ask-again`
and `allow|deny` of an answered question do the same from the command line. The network settings do not change what
a ruleset decides - the page and the help say so.

**MCP servers:** the hub's catalog (axross-mcp-hub) is signed now (every server reviewed in full: exiftool, yara,
capa and the others need no `--unsigned` any more; nmap scans without host discovery, `-Pn`, which under sandbox-ai's

**MCP servers behind a VPN, proven:** a server whose VPN is its own, the start's or `mcp start --vpn`'s reaches the
network only through it, on every way it comes up, or it does not run. A catalog server's container is created in
its VPN container's namespace by that container's ID (it was by name: a container that took the name later would
have been joined), only while the VPN container runs with its kill switch, inspected (`container:ID` exactly) before
it starts and checked again after; a command server's or helper's pod must show the server in the VPN's namespace
with the kill switch, else the server is stopped; a running one is checked again before another start uses it; the
end of its VPN container stops it. Its lookups now go to the VPN's resolver through the tunnel (they went to the
resolver Podman gave it, through the tunnel or nowhere). A Tailscale profile without an exit node is refused as an MCP
server's way out (the rest left from your own address). Tested in every run (every way up x server kind x VPN kind),
in the kernel (a real WireGuard tunnel between network namespaces) and with real containers (a Tor profile end to
end).

**Limits per MCP server, and per board:** a server's memory, CPUs and processes are its own and the defaults of every
start that uses it. `sandbox-ai mcp add` takes the limits the catalog entry recommends (a `"limits"` key in
rootfs.json beside the catalog, signed with it - axross does not read it; an old catalog gives the defaults) and has
`--cpus`; a container server now gets a CPU limit too (half the host's CPUs unless set; Bubblewrap: `CPUQuota`).
`sandbox-ai mcp set NAME --memory 2g --cpus 2 --pids 512` changes a server of yours later - its network, folders,
variables and VPN as well, checked as `add` checks them, its image and signature untouched. One start asks for other
limits with `--mcp-limits NAME:memory=4g,cpus=2,pids=1024`: a running server has one set of limits, so such a start
gets an instance of its own (`NAME.HASH`, shared by every start asking for the same limits); `--dry-run` shows the
instance and its limits, `mcp list` the running instances, `mcp stop NAME` stops them all, the kill switch cuts the
one a start reaches. On the board an MCP node has Memory, CPUs and Processes, the server's own shown as the default,
Reset to defaults, and *Defaults for every start…*. The MCP page has **Properties…** for a server (double click,
Alt+Enter, its right-click menu with Start…, Stop, Attach to… and Properties…); a catalog entry opens Add… by double
click or Enter, and its menu has Add… and Details… (its notes, folders, variables, recommended limits). Every limit and
folder is checked while it is typed, by sandbox-ai's own rules: a value that is not valid (`1024` without m or g, 0
CPUs, 5000 processes, a read-only folder that is not there) is marked with its reason and OK takes nothing until it
is corrected. `mcp add ... --mount /data=/work/memory:rw` creates the writable folder that is not there yet (0700, said)
instead of failing; the messages say that TARGET is the folder in the server's container and HOST the one on this
machine.

**The Playwright browser crashed:** every MCP container had a /tmp of 64m, and Chromium keeps its profile, cache,
shared memory and screenshots there. /tmp is now a limit of each server (`tmp`: `mcp add|set --tmp`, `--mcp-limits
NAME:tmp=SIZE`, the board's and Properties' /tmp field; a tmpfs is memory, so never more than the memory limit), and
the sandbox-ai-mcp catalog recommends 2g, 2 CPUs, 512 processes and a /tmp of 768m for Playwright (its smoke test now
loads a large page and takes a screenshot). A server added before keeps its limits: `mcp list` and the MCP page say
it is below the catalog's, and `mcp set NAME --recommended` (Properties… > Use the recommended limits) applies them.
What ends a server's process is recorded now (an out-of-memory kill, its process limit, a full /tmp, an exit nobody
asked for): a safeguards record `mcp-server` with the reason and the fix, shown by `sandbox-ai safeguards`, `mcp list`
and the MCP page, instead of only "crashed".

**Two review rounds before the release** (core and app, each finding with a test):

- The kill switch holds Tor's SocksPort (`--socks`) as the internet: a cut agent reached the internet through it.
- A cut asked while a server, helper or team member joins the run is set before it runs (it was reported "NOT cut"
  and ran uncut); a cut racing a resume is never left waiting; cuts that hold together (`api+remote`) keep the
  browser closed; the emergency stop is never undone by a sandbox's own cut on its way, and works while a dialog or
  the "Lift every cut?" question is open.
- The model API's exemption from rules for every host holds only for requests whose Host header names the `--llm`
  endpoint.
- An MCP rootfs archive member named `//PATH` stayed absolute (a malicious archive could write outside its folder).
- Approvals: Allow on the Blocked list never opens more than was refused (no `--allow ADDRESS` for a refused packet,
  no host lookup of a name with a canary token); deny or ask again after an allow for the run takes it back in the
  firewall and the proxy; an Allow always from an encoded path no longer matches everything below it; remembered
  decisions can no longer be confused through spaces; a preset cannot copy a login in with `--copy`.
- Reports never print a log's escape sequences raw to the terminal and survive malformed logs.
- `--nested-containers`: each container gets an IPC namespace of its own (crun could not mount mqueue); a workspace
  added during the run is handed back at its end too.
- App: Clone keeps an untrusted board untrusted; file copies keep their permission bits (a 0600 key became 0644);
  Enter in the Questions window allows once, as its button says; Report… asks before replacing a file; Revoke acts on
  the sandbox its rows belong to.

**Local models without endless loops:** a loop guard for starts with `--llm`, in layers that are each switched on
or off (`sandbox-ai defaults set loop_guard ...`, `sandbox-ai llm set NAME --loop-guard ...`, `--llm-param
loop_guard...`, the app's Settings and LLM servers page): OpenCode's step limit, compaction and tool output limits and
instructions against loops (beside your own `AGENTS.md`); the model family's recommended sampling (never greedy for
Qwen3 and DeepSeek-R1); a warning when the agent is told a larger context window than the server loaded; and in the
connection proxy, for that server's requests only: the same tool call with the same result 3 times adds a note to
the model, 6 times pauses tool use for one answer, an answer that repeats one block 10 times ends cleanly with a note
(the next request gets stronger anti-repetition sampling), and an optional watchdog for unattended runs. The model goes
on after each; polling and read-edit-test cycles do not count. Each intervention is a safeguards record (`loop`).
OpenCode's own `doom_loop` question (OpenCode 1.x) is no longer switched off by `--dangerously-skip-permissions`. Why
local models loop, what the agents do themselves and the research behind it: `docs/llm-loops.md`.

**Sampling parameters per model:** `sandbox-ai llm set NAME [--model MODEL] --param temperature=0.7 --param
top_k=40 --force-param repeat_penalty=1.1 --param num_ctx=32768 ...` (and `llm add --param`, `--llm-param` for a
start, the board's LLM node, the LLM servers page), checked per server kind (`sandbox-ai llm params`), set by the
connection proxy in that server's requests for every agent (a default, forced, `max_tokens` a ceiling); `num_ctx`
goes into the agents' configuration (and LM Studio's load), Ollama gets the Modelfile for what its APIs do not take.

**Two sandboxes no longer unload each other's model on LM Studio:** a start loads its model explicitly (Auto-Evict
leaves such models alone) unless `llm set NAME --evict allow`; `llm check` says how Ollama and llama.cpp unload
models. sandbox-ai's own status, model list and check never load a model (now tested).

**Faster:** the connection proxy spends less than half the CPU per request with large rulesets (1000 rules: 1.5 ms ->
0.6 ms) and redacts logged bodies five times faster; reports and `sandbox-ai logs` on large logs take 30-45 % less
time; `mcp catalog` downloads in parallel (0.5 -> 0.2 s); an idle sandbox's supervisor starts one nft process per
second instead of two. The app refreshes the Sandboxes tree ten times faster with many starts, inserts bursts of log
entries at once (2,000 entries: 330 -> 24 ms), reads nothing for a hidden Approvals page, polls nothing
informational while minimised and switches a file to hex ten times faster.
