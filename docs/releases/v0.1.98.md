# sandbox-ai 0.1.98

## State directories

**`sandbox-ai gc --usage` says what sandbox-ai keeps on this computer, and gc compacts the logs.** A host's state
directory had grown to 50 GB (a disk 99 % full): 26 GB of kept HOMEs - mostly what the agents left in them (scratch
clones, test runs, pip caches, transcripts) - and 24 GB of logs, 14 GB of them in one project: one run's file watch
(8.3 GB in four days) and its connection log (5.9 GB), both still growing.

- `sandbox-ai gc --usage [--json]`: every start with its HOME's biggest folders and its download caches, the logs of
  each project by kind, MCP servers, histories, `launcher.log`, the data, cache and configuration folders, Podman
  (`system df`, the images a rebuild left without a name), and what each gc would free. Measured with `os.scandir`
  within a time and entry budget, never through a link or into another file system; what cannot be read is counted.
- `gc --usage` reads as an overview: first a summary table (category | size | share | reclaimable | how), biggest
  first, with the total - Podman's images, volumes and containers counted beside sandbox-ai's folders, and why
  Podman's "reclaimable" is more than `gc --images` frees (it counts every software's images) - then aligned
  tables: the starts (HOME size, caches, state, last used, when they expire, the HOME's biggest folders), the
  log folders, MCP servers, the other folders, Podman, and what gc would free with the exact command per row and
  the total of `gc --caches --images`. Sizes right-aligned, colour on a terminal only (`--color`, `--no-color`,
  `NO_COLOR`); `--json` keeps every field and adds `summary`, `would_free.total` and each start's `expires`.
- **What in a HOME is big, and why:** `sandbox-ai gc --usage --detail` measures every kept HOME by kind -
  download caches (pip, uv, npm, Yarn, pnpm, Cargo registry, Go modules, Bun, Hugging Face, Playwright
  browsers ...), toolchains (rustup, nvm, SDKMAN, pyenv ...), agent state (Claude/Codex transcripts, todos,
  shell snapshots, OpenCode, Goose ...), build output and temp (`node_modules`, Rust `target/`, virtualenvs,
  `tmp/` ... wherever they are) and the agent's own work - one row per start with the total; `--detail NAME`:
  one HOME in depth with its biggest items. Read under each start's lock, never through a link, in one walk
  within the time budget; every byte counted once. `gc --usage --json` gives each HOME's `kinds` too. App:
  each start's HOME by kind in **Disk usage…**, and **HOMEs in depth…** there.
- **What to do with it:** `gc --build-output`, `--toolchains` (never `go/`, the GOPATH with the agent's sources)
  and `--transcripts DAYS` (Claude and Codex transcripts older than DAYS, never the newest of a project or of
  all: the conversation resume continues) remove that of the stopped kept HOMEs; `--home NAME` narrows each and
  `--caches` to one start. Listed first and asked in a terminal, `--yes` otherwise, `--dry-run` only lists; a
  start that runs, is held by another command or is packed is left alone; nothing through a link.
- **`gc --pack [--older-than DAYS] [--home NAME]`** (opt-in, listed and asked or `--yes`) packs a stopped kept HOME
  into one archive beside it (`home.tar.zst` with zstd, else `home.tar.xz`): written, read back whole and compared
  by a digest of every entry before the HOME goes; links stay links. `resume`, `--review-home`, `--restore-home`
  and a start of that name unpack it first under the start's lock (`gc --unpack NAME` by hand); an archive that
  does not read back as packed stays and the start stops - never an empty HOME in its place. An interrupted pack
  or unpack is finished or undone the next time; `gc --usage` marks packed starts and names what
  `--pack --older-than 30` would pack; the app's Disk usage says "packed".
- **Podman: why its "reclaimable" is far more than `gc --images` frees.** Podman counts every image no container
  uses, of every software. `gc --usage` sorts the images by what they are to sandbox-ai - used by kept starts,
  its role images, its images no kept start uses, its unnamed rebuild leftovers, other software's unnamed ones,
  build layers, other software's named images, in use by a container - each with what removing it frees
  (`podman system df -v`). `gc --images[=LEVEL]`: `unnamed` (default, as before), `old` (also sandbox-ai's no kept
  start uses; built again when needed), `prune` (also every software's unnamed images, as `podman image prune`);
  `old` and `prune` list each image and ask (or `--yes`); never forced, never another software's named image.
  The app's Disk usage lists the groups.
- `sandbox-ai gc` compresses the logs of runs that ended (`NAME.gz`) and splits a project's shared log over 96 MiB
  (its newest 32 MiB stay, the older part goes compressed into `NAME.TIME.gz`); never a registered run's logs, nothing
  written within the hour; `--no-compact` leaves them. `--caches` empties the download caches (pip, uv, npm, Go, Yarn,
  Bun, pnpm) of the stopped kept HOMEs; `--images` removes the images of sandbox-ai's a rebuild left without a name.
  Once a day after a start that logs, the same compaction runs in the background (niced, at most ten minutes;
  `SANDBOX_AI_AUTO_COMPACT=0`: off).
- During a run the supervisor rotates what grows: `files.jsonl`, `processes.jsonl`, `dns.jsonl`,
  `egress-denied.jsonl` and the run's connection log over 128 MiB go compressed into older parts (1 GiB of them per
  log); `activity.jsonl` rotates at 256 MiB instead of stopping the timeline; the same file access is logged once per
  30 s (was 2 s). The per-folder limits of the connection and LLM traffic logs count the compressed ones.
- Every reader reads the compressed and rotated logs: `sandbox-ai logs` and the Statistics page, `report`,
  `llm traffic` and the LLM traffic page, the canary check, the Connections page.
- App: **Disk usage…** on the Sandboxes page (also on right-click), then **Clean up…** or **Clean up with the
  caches…**; the clean-up's list names the caches and the logs it compresses.
- The agents' sandbox-ai skill says that what they leave in HOME stays on your disk.
- **Kept starts expire by default.** Without `keep_days` in your defaults, `sandbox-ai gc` and its daily pass remove
  the stopped kept starts unused for 90 days with their HOME - never one that runs, is paused or orphaned, never one
  whose last use is unknown - and only 14 days after this was first said to you (`state/expiry.json`; the daily
  pass alone, which nobody sees, starts no such wait): until then
  `gc`/`gc --dry-run` list them ("will be removed from DATE on"), `gc --usage` and the app's Disk usage name them and
  the date, and a start says it once a day, each with how to keep them: resume them, or
  `sandbox-ai defaults set keep_days 0` (0 is now valid: never). `keep_days N` works as before, also at every start.
  The app's Hosts page shows no `keep_days` as checked with 90 days and writes `keep_days 0` when unchecked.
- `sandbox-ai gc --logs-older-than DAYS` removes the log folders nothing was written into for that long (projects
  that are gone, or not used), with their reports - never one a registered run logs into (checked again right
  before each goes); `--dry-run` names each with its project where a start or history knows it, and whether that
  folder is gone; `gc --usage` says what 30, 90 and 180 days would free.
- The MCP servers' `supervisor.log` and `mcp-calls.jsonl` rotate at 32 MiB while the server runs (256 MiB of
  compressed older parts per log); `gc` and its daily pass do it for a server that does not run, and remove decided
  approvals older than 30 days. `web/audit.jsonl` rotates at 16 MiB. `gc` removes the MCP root file systems
  (`~/.local/share/sandbox-ai/mcp-rootfs/SHA256`) no server definition, team or server state names (older than a
  week; they are unpacked again from their checked archive when needed).
- The run's connection log loses nothing when it is rotated: the proxy writes each record under a lock on the file,
  and the rotation copies the rest and empties the log holding it (before, what the proxy wrote while the copy was
  synced was lost).
- `sandbox-ai activity RUN` finds a run whose records were rotated out of `activity.jsonl`: the older parts
  (`activity.jsonl.TIME`, `.TIME.gz`) are searched and read too, oldest first; `--runs` lists their runs.

## --with for every agent

**Every agent can join a start as a companion (`--with AGENT`) and be a team member, and every agent can lead with
others beside it.** Until now only Claude Code, Codex and OpenCode could be `--with` (the team image held only them),
and OpenHands, nanobot, Letta Code, OpenCode 2 and Pi could not be team members.

- **The team image with layers.** `localhost/team-sandbox:latest` stays Claude Code, Codex and OpenCode;
  Hermes, DeepSeek Harness, Qwen Code, Goose, OpenHands, nanobot, Letta Code, OpenCode 2 and Pi come as layers on
  it: `sandbox-ai build team --with hermes,qwen` (or `--with all`) builds `localhost/team-hermes-qwen-sandbox:latest`.
  Each layer is made from the agent's own Containerfile (`sandbox/team_image.py`): the same reviewed release, the
  same lock file, the same checks and telemetry guard as its own image - never a copy that could drift, and a
  Containerfile whose team change no longer applies stops the build. Layers come in one order, so images that begin
  alike share them on disk, and every one shares the base: `sandbox-ai build team` builds the base again and then
  the team images with layers that are there, on it. The base's uv is pinned to the reviewed agents' release
  (0.13.5: their layers install their CPython with it); `--build-arg <AGENT>_VERSION` takes no other release.
- **The start picks the image.** `sandbox-ai claude --with hermes` takes the team image with exactly its agents;
  when that one is not built, a built one that holds them and more (the smallest, said), else it builds the one it
  needs as for any missing image ("sandbox-ai build team --with hermes"). `gc --images` keeps the team image a kept
  start needs.
- **Under the same rules as in their own images.** A companion gets its login (an agent without a login of its own
  gets nothing of the host's - Goose's `secrets.yaml` holds every key - and the start says it needs `--api-key`), its
  provider's hosts, its managed configuration read-only where its image has it (`/etc/hermes`, `/etc/qwen-code`,
  `/etc/goose`, `/etc/openhands`, `/etc/nanobot`, `/etc/letta`, `/etc/opencode2`, `/etc/pi`, `/etc/dsh`) with the
  run's MCP servers (Qwen Code's in its system settings; Letta Code's laid into its agents by its start script when
  the sandbox starts), the network note and `-D`, its variables, its own `--AGENT-enable` switches, and telemetry
  always off: its command's guard, its opt-out variables and the proxy's rules - for every agent of the team image,
  also those the run did not ask for. Hermes' first-run question is answered before the lead starts. Rules for the
  agents' own tools hold for a companion through the same hooks as for a lead (Qwen Code, Hermes, Pi, OpenCode 2,
  DeepSeek Harness, Letta Code - its start script lays them in before the lead starts, and the sandbox does not
  start when it cannot - and Goose); OpenHands and nanobot cannot enforce them, so a start with tool rules and one of
  them `--with` is refused, as it is for them as the lead.
- **One-shot commands.** The lead gives each a task from the shell in its one-shot mode - `hermes --oneshot=...`,
  `qwen --prompt=...`, `goose run --quiet --text=...`, `openhands task --text=...`, `nanobot agent --no-markdown
  --message=...`, `letta -p --new -- ...`, `opencode2 run -- ...`, `pi -p -- ...`, `echo ... | dsh headless -` (what a
  helper runs for a task) - and every agent's sandbox-ai skill names them all.
- **OpenCode 2 beside OpenCode.** In the team image OpenCode 2 is `opencode2` only (`opencode` stays OpenCode 1: the
  telemetry guard leaves another agent's command alone), and the two never share a sandbox: they read the same
  folders of the HOME and the same variables (refused, with what to do instead).
- **Team members:** OpenHands, nanobot, Letta Code, OpenCode 2 and Pi (the app's and the web page's Teams too).
  OpenHands, nanobot and Letta Code have no first prompt in their own interface: they run the member's prompt as one
  long task that waits for the board's tasks in it.
- The web page refuses `--with` beyond the three, and those team members, on a host older than 0.1.98 (said).
- Not yet: `--with` with `--llm` (as before, for every agent: each companion reaches its own provider).
- Needs a live test with Podman: building the layered images, and each companion's one-shot run in them.
### Logs: less kept, and for 30 days (review 1 of 3)

A hard review of every log sandbox-ai writes per run and per project ([docs/reviews/state-logs-review-1.md](
../reviews/state-logs-review-1.md): who writes what, how fast, who reads it) found that most of the bytes were the
same data again or data no reader shows. Measured on a busy agent's workload:

- **`files.jsonl`: reads are summed per folder.** Reads (a file closed unwritten) were 99 % of the file log - every
  module a test run imports - and no reader showed them one by one. Now one record per folder and 30 seconds
  (`"folder"`, `"reads"`, `"files"`, the first five `"names"`; at most 32 such records per 30 seconds, the deepest
  folders merged into their parents); changes stay one record per file. The file log of a test loop (pytest, git,
  grep) went from 543 MB to 36 MB a day. `sandbox-ai defaults set file_reads files` logs each read as before, `off` none.
- **The connection log writes a repeated body once.** A model request begins with the same system prompt and tools;
  their first 64 KiB, all the log keeps of a request, were the same request after request - and beyond gzip's
  window. A body this part of the log holds already is now a reference (`"same_as"`: connection, time, digest);
  every part of the log still stands alone. A binary answer (a download) is logged by its size, the SHA-256 of its
  first 64 KiB and its first 64 bytes instead of 87 KB of base64 (`connection_bodies all` in your defaults: as
  before); what was sent stays whole. A busy agent's log: 98 MB -> 21 MB, compressed 35 MB -> 3.7 MB.
- **Logs older than 30 days go.** `sandbox-ai gc` and its daily pass remove every log file nothing was written into
  for longer than `log_days` (default 30; `sandbox-ai defaults set log_days 0`: never) - never the log a running
  run writes. Without `log_days` this begins 14 days after the first `gc`, `gc --usage` or daily pass that found
  such logs; `gc` and `gc --usage` say from when, and what goes. The logs hold what the agent sent and received:
  before, they were kept until a size limit, for months.
- **Readers stop at their budget.** `sandbox-ai logs`, the Statistics page and `report` unpacked every compressed
  part of the connection log even after their budget was spent: 12.6 s per refresh with 24 parts, now 2.1 s.
- `activity.jsonl`'s older parts are capped (1 GiB) also in a project a run uses (they grew without end), and
  `tools.jsonl` rotates during the run like `files.jsonl`.
- `--dry-run` shows `proxy.connection_bodies` and `file_log` (watched, reads).

### Logs: nothing lost, nothing unseen (review 2 of 3)

A second, independent review ([docs/reviews/state-logs-review-2.md](../reviews/state-logs-review-2.md)) re-measured
review 1 (with real Claude Code requests: it holds) and looked for what loses or hides records:

- **The LLM traffic log lost most of a conversation to its redaction.** The line was redacted as text: a file the
  agent read with `"--password-store=basic"` in it lost the backslash of an escaped quote, and the line - with every
  later request of the conversation - was no JSON any more, skipped by every reader (320 of 410 requests of a
  measured run). Each text is now redacted on its own; the record's session name is no longer taken for a secret.
- **The LLM traffic log writes a request as what is new in it.** A request that continues an earlier one leaves out
  the messages it begins with and the system part and tools when they are the same (`"delta"`); `sandbox-ai llm
  traffic`, the app's LLM traffic page, reports and the bridge show every request whole as before. Rotated parts are
  compressed while the run goes on. 410 real Claude Code requests: 163 MB -> 22 MB (58.6 -> 6.2 MB compressed).
  `--grep` and the page's search find the requests where the text is new (and the answers), no longer every later
  request that repeats it.
- **A running run's logs are never deleted by the per-folder caps.** A start (or gc) over 1 GiB of connection logs
  deleted the oldest - also those of a run that started earlier and was idle for an hour, even the log its proxy
  still wrote, which then grew unseen and was never rotated again. The same for the LLM traffic logs.
- **The run's taint events are no longer lost when its connection log rotates** (they were written without the
  log's lock: 70 of 300 in a stress test).
- **The 30 days' age limit is said before it removes anything.** The daily pass in the background started its 14
  days' grace without telling anyone; now gc, `gc --usage`, the app and a start (once a day) say it first.
- File statistics count a folder's summed reads by the files read (as before review 1), not every close of a file
  (which made them 120 times larger); reads in more folders than a window tells apart keep their top folder.
- `mcp-calls.jsonl` of a project rotates during a run; a line cut by a killed writer no longer swallows the next
  record; a record written into a shared log just as it was rotated is kept; a start's `supervisor.log` keeps its
  newest 4 MiB once it is over 8 MiB.
- `gc --usage` says what compressing frees, measured on a sample of each kind of log (it said 76.5 MB where 57.7 MB
  were freed; now 59.1 MB).
- The app's Connections page shows a body logged once and then by reference in full, naming the connection it was
  logged with.

### Logs: the readers, redaction, and what happens when something fails (review 3 of 3)

The third review ([docs/reviews/state-logs-review-3.md](../reviews/state-logs-review-3.md)) measured the first two
again and looked at what they left: several runs in one reader, a rotation that fails or is killed, the readers after
a rotation, what the redaction does not know. And it decided the database question with numbers.

- **A request of the LLM traffic log is never put together with another run's.** A request written as a delta names
  the one it continues by its number, and every run counts from 1: `sandbox-ai llm traffic --session NAME --tail N`
  over a session's runs showed an earlier run's requests with the later run's conversation in front of them. A
  request now continues one of its own run only.
- **Deltas also for a conversation that does not only grow.** Only a common beginning was left out: a harness that
  drops its oldest messages (a local model's small context), clears old tool results or changes its first message
  with every request wrote nearly every request whole (x1.0 to x2.1). Messages the earlier request holds anywhere
  are left out now (`"items"` in the delta): x8 to x17, every request still shown whole.
- **Variables assigned a secret are redacted in every log.** `DB_PASSWORD=...`, `AWS_SECRET_ACCESS_KEY=...`,
  `OPENAI_API_KEY=...` of an `.env` file the agent read stayed in the connection log and the LLM traffic log (only
  the timeline redacted them) - and inside a request's JSON even `PASSWORD=...` at the start of a line. MCP
  arguments and a question's body are redacted value by value, no longer as JSON text.
- **A full disk no longer costs a run its older parts.** The connection log's rotation moved every older part up
  before it compressed the log: when that failed it moved them again at the next try, a minute later, and deleted
  them at number 999. They move only once the new part is complete.
- **`sandbox-ai gc` finishes a rotation that was killed.** A connection log whose rotation put the part in place but
  never emptied the log had its records twice (398 requests counted for 199): the duplicate part goes. A part left
  both raw and compressed (a run that ended in the rotation's last 0.2 s) was skipped by gc for good: it is
  completed and the raw one removed.
- **The timeline's older parts are read.** `sandbox-ai activity --since 7d` read the current file only (four days of
  a busy project) and the app's Activity page showed two events just after the timeline rotated: `--since TIME`
  reads the parts written since then, and a tail the current part does not fill just after a rotation goes on into
  the newest older one. A run's records are read in one pass over the parts that name it, which
  `.activity-parts.json` beside them remembers: the last 5000 events of a run three weeks old took 10.3 s in a
  30-day folder, now 2.1 s. Plain `sandbox-ai activity` shows the current part as before and says how many older
  ones there are.
- **The approvals' blocked list keeps what was refused before a log rotated**, and the canary log's requests link to
  their own events in the timeline after the connection log rotated (every part's first request was linked to the
  first part's).
- Two runs of a project that rotate a shared log in the same second never replace each other's part; a part gc
  splits off a shared log keeps its log's time (the age limit kept it up to 30 days longer).
- **No database.** For the same 255 MiB of timeline records SQLite takes 328 MiB (169 MiB with every row
  compressed) where the compressed part takes 62 MiB; what it would speed up - an old run's events, the list of
  runs - is answered in seconds from the parts, and the page a human watches (the newest 5000 events) takes 0.12 s
  either way.

## Model × harness profiles

**A local model gets the settings measured for it in each agent, at every start.** The local-model research of
2026-11-15/16 (LM Studio on an Apple-silicon Mac, nine agents, a smoke test and harder tasks) is now part of
sandbox-ai: [docs/LOCAL_MODELS.md](../LOCAL_MODELS.md) and its [cheat sheet](../LOCAL_MODELS_CHEATSHEET.md), and a
reviewed table of model × harness profiles (`sandbox/model_profiles.json`: Qwen3-Coder-Next, Qwen3-Coder-30B,
Qwen3.6, Qwen3.8-27B, Nemotron-3-Super GGUF and MLX, Laguna-S, VCoder, gpt-oss-120b, GLM-4.7, Gemma-4; each pair with
its status and the evidence). A start with `--llm NAME:MODEL` matches the model against the families and applies the
profile of that model in that agent as the lowest layer, under everything you set yourself (the profile < the
endpoint's `llm set` values < the start's `--llm-param` < `--env`):

- the sampling (the makers' or the measured values; the research's P2 presets for Nemotron, Gemma-4 and GLM-4.7,
  GLM's answers capped at 16384 tokens against thinking loops) as the connection proxy's default for that model's
  requests;
- `num_ctx` as the window the agents are told (never more than the server has the model loaded with or reports, nor
  than the window Ollama serves;
  Qwen3.8-27B gets 49152 so that the agents compact before a prefill outlasts their idle limit) and the window LM
  Studio loads the model with (at most the model's maximum, with parallel 1 as before);
- the loop guard's `steps`: 150 (40 ended a debugging session unsolved);
- an agent's own switch where one helped: Nemotron in Claude Code gets `CLAUDE_CODE_DISABLE_THINKING=1` (the
  debugging task solved in 9.9 minutes with 21 requests instead of unsolved after 25 minutes).

The start says it in one line (`profile qwen3-coder-next × opencode (verified): temperature 0.7, top_p 0.8, top_k 20,
repeat_penalty 1.05, context 131072, loop_guard.steps 150`) and names yours that win; `--dry-run` has it as
`llm.profile` (`id`, `status`, `values`, `applied`, `overridden`, `not_taken`, `warnings`). A model or pair known not
to work (Qwen3.8-27B for big contexts, the Nemotron MLX build in Claude Code, Qwen3-Coder-30B on Responses and
Messages, VCoder) and Laguna with more than one MCP server are WARNINGs with the reason - the start goes on.
`--no-llm-profile` (`-nl`; also a project file's `options`) switches it off; `sandbox-ai llm profiles [MODEL]
[--agent AGENT] [--json]` lists the profiles.

In the app the Board's LLM part shows the profile of its model in the board's agent ("Model profile:
qwen3-coder-next × opencode (verified)"), its properties and the agent's model section show its values with "your
value wins" beside the board's and the server's own, warnings for a pair known not to work, and a switch "Apply the
model profile"; the Start page says it below the model. Help: *Model × harness profiles*.

- **What we know, in short bullets.** Every family and every measured pair of the table now lists what works, what
  does not and what is not known yet (`works`, `fails`, `unknown`: at most 12 lines of 120 characters each; tables
  without them stay valid), filled for all 30 pairs and 11 families from docs/LOCAL_MODELS.md and the research's
  newer round on the real server (e.g. Qwen3-Coder-Next × OpenCode: ✓ MCP-heavy task 7 of 7 hidden tests, ✗ debug
  task 2 of 3 runs unsolved, ? Ollama, llama.cpp and vLLM servers not measured). The app shows them in a box "What
  we know" beside the profile (Board: the LLM part's and the agent's properties; Start page: below the model): the
  pair's status in words, then ✓ works, ✗ does not work, ? not known yet; a pair without an entry says it was not
  tested (with the model's general notes), a model of no family that nothing is known about it. It folds to its
  title line; fold and copy are on its context menu too. `sandbox-ai llm profiles MODEL [--agent AGENT]` lists the
  same bullets (`--json`: `works`, `fails`, `unknown` of each profile).

## Local models: fixes from the research

The local-model research's second phase ran the real harness CLIs against real models on LM Studio and verified each
fix through a relay of its own before it came here. User, live: "a lot of mcp issues, web fetch failures, endless
loops. and some took ages before they finished".

- **A step after the loop guard's note takes a fraction of a second again, not a full read of the conversation.**
  Once a tool call had repeated three times, the guard's note went into the result of the *latest* call of that tool
  in every request to the end of the turn. It moved with every step, so no request began like the one before it, and
  LM Studio (no partial prompt cache reuse with Qwen3-Next, Nemotron or gpt-oss) read the whole conversation again
  each time: 6.7 s per step at 7,000 tokens, 29.5 s at 27,000 - 1,084 of the 1,200 s of one Codex run. Now the k-th
  identical call's result carries the note for k ("3 times", "4 times" ..., the sixth's says to stop calling tools),
  and it stays there in every later request, after your next message too; the watchdog's note keeps its place the
  same way. The same run with the notes in place (the research's relay): 0.34-0.46 s per step. What the guard does
  is unchanged: a note from the third identical call, the stop at the sixth, and sandbox-ai's own answer ends the
  turn when the model calls a tool again. The LLM traffic log lists each note of a request with its message.
- **The turn limit no longer ends real work early: `steps` is 150, not 40.** With 40, OpenCode stopped the
  research's debugging task after 41 requests with nothing fixed and an empty last answer; with a limit of 120 the
  same model solved it in 102. Solved runs took 21 to 38 requests with Nemotron, 23 to 36 with Laguna, 30 with
  Qwen3.6 and 102 with Qwen3-Coder-Next. The value is OpenCode's `agent.build.steps` (`plan` and `explore` 67,
  `general` 100) and the turn limit of the other agents that take one for `--llm`. Loops are stopped by the proxy's
  guard (`warn`, `block`) and the watchdog, not by a low limit; your own value still wins
  (`--llm-param loop_guard.steps=40`, `sandbox-ai llm set NAME --loop-guard steps=40`, your defaults).
- **OpenCode: one tool result no longer costs tens of thousands of tokens.** 0.1.96 raised OpenCode's
  `tool_output.max_bytes` to 128 KiB so that a whole 60,000-character part of the files MCP server's `read_file`
  reached the model. With that limit one `read` of a log took a request from 9,297 to 45,143 tokens - 47 s before the

  characters, which fit, so the limit is 50,000 bytes again (1,000 lines as before).

  of the body, and sends everything again; a 120B model reading a long prompt is silent for longer. A start with

  Checked with the real Pi 1.4.0 against a silent server: it waits as long as set, and no longer.
- **Codex's MCP tools reach a local model.** Codex offers each `--mcp` server as one `namespace` tool of the
  Responses API; LM Studio's `/v1/responses` ignores those, so the model never saw an MCP tool ("I don't have access

  `--llm` server the connection proxy now offers them as plain functions `NAMESPACE__TOOL`

  name and namespace back in the answer (streamed or not), so Codex runs them as its own. The research's smoke run
  with Codex and Qwen3-Coder-Next: 4 MCP calls, all points (before: none). The connection log (`llm_tools`) and the
  LLM traffic log's changes say what was done.
- **Codex no longer refuses a local model's shell commands.** Codex's `exec_command` offers `justification`,
  `prefix_rule` and `sandbox_permissions`, and refuses every call that fills `justification` without

  repeats the refused command until the loop guard ends the turn. The connection proxy no longer offers the three

- **The loop guard's note no longer breaks a Codex run with MCP tools.** Codex sends an MCP tool's result as a list of

- **Every agent says what it assumes when the model's context window is not known.** A start with a model server

- **`sandbox-ai llm models` and the app show the window Ollama really serves a model with.** Ollama's listing has

## Fixes

- **A sandbox never runs on without its supervisor and its kill switch.** A session's supervisor (the launcher on
  the host) ended on a nearly full disk while its pod ran on: `podman pod rm` failed, its cleanup removed the run
  directory anyway - the control socket of approvals, `net allow`, `workspace add` and the kill switch (`net cut`, the
  app's emergency stop) - the safeguard, memory and canary watches were gone, the terminal that started it kept it as
  a zombie, and nobody was told; `sandbox-ai list` said only "orphaned". Now it fails closed and loud:
  - the launcher whose pod Podman cannot remove cuts the sandbox's network through its control socket (the kill
    switch `all`), else kills the pod; one that still runs keeps its run directory and the folders bound into it (the
    HOME of a run without one of its own is no longer removed under the agent), and the reason goes into
    `launcher.log`, the terminal (a session's: `supervisor.log`) and a desktop notification;
  - the sandbox's own supervisor watches its launcher through a lock in the run directory: whatever ends the
    launcher (a crash, `kill -9`, the out-of-memory killer) or removes the directory, the sandbox cuts its own network
    within two seconds (a run without a kill switch is ended) and reports it as a safeguard (Linux with a local
    Podman; with podman machine and `--podman-url` the launcher's own cut above holds);
  - the terminal that started a session reaps its supervisor (no zombie) and, when the sandbox runs on, cuts its
    network (or stops its pod when its run directory is gone) and says so on the terminal and the desktop;
  - `sandbox-ai list` (below the table, and `orphaned_why` in `--json`), `attach`, `shell` and `sandbox-ai doctor`
    (check *Orphaned starts*) say when and why the supervisor ended, whether the network was cut, and what to do:
    save your work, `sandbox-ai stop NAME`, then `sandbox-ai resume NAME`;
  - a log the sandbox's supervisor cannot write (a full disk: `files.jsonl`, `dns.jsonl`, the firewall's refusals)
    loses those records with one warning ("the disk is full", also as a safeguard) instead of ending that monitor
    for the rest of the run, and is written again once there is room.

- **The kill switch reaches an orphaned run, and its commands say why.** With the run directory and control socket
  kept, `sandbox-ai net cut NAME`, the app's kill switch and emergency stop (`net cut --all-runs`) still refused an
  orphaned run ("does not run now (orphaned; see sandbox-ai list)"). Now:
  - `net cut NAME MODE` asks the supervisor in the sandbox through its control socket and says the cut only once it
    confirmed it; when nothing answers (no socket, no run directory, a run without a kill switch) the pod is stopped
    instead (`podman pod stop`), said, and recorded in `launcher.log` and the start's history - never "done" unless
    the cut or the stop is confirmed (else `NOT cut`, with `podman pod rm --force POD`). `net cut --all-runs` reaches
    the orphaned runs too (each one in the `--json` report, `"orphaned": true`, `"stopped"` when its pod was
    stopped); lifting an orphan's cut (`off`) is refused. The app's kill switch button no longer says "It does not
    run." for an orphaned start;
  - what only reads works where the data is there, marked as orphaned: `net show NAME` (what the sandbox's supervisor
    answers, else what its run directory recorded), `approvals list` (its open questions; `orphaned` and
    `orphaned_why` in `--json`) and `usage NAME` / `usage --all`;
  - what widens access - `net allow`, `net untaint`, `workspace add`, `approvals allow`, `git-logins give`,
    `secrets give`, `devices add`, `limits`, `rules reload`, `canaries resume` - is refused with the precise reason
    and the fix: nothing supervises the run, so nothing is opened (`approvals deny` still answers);
  - every other command says the same as `sandbox-ai list`: when and why its supervisor ended, whether its network
    was cut, then save your work, `sandbox-ai stop NAME`, `sandbox-ai resume NAME`.

- **Every option has a help text.** The `--json` options and a few options of `sandbox-ai llm`, `images`,
  `identities`, `hosts` and the other sub-commands (about 110) had none in `--help`; each has a short one now, and a

## Bridges

**A bridge between two sessions that both run on other hosts.** Until 0.1.97 one side had to be a session of this
machine (`bridge add web lab1:docs`); `bridge add lab1:a lab2:b` was refused. Now:

- **Two sessions of one other host** (`bridge add lab1:a lab1:b ...`) are bridged *there*: this machine checks what
  it is given, then runs `sandbox-ai bridge add a b ...` on lab1 over SSH (`--until` is sent as the time it names on
  this machine's clock, never an `HH:MM` read on lab1's). The bridge is lab1's own - one broker there, its questions
  there, no hop through this machine, and it lasts while lab1 runs. It is named `lab1:ID` here.
- **Sessions of two other hosts** (`bridge add lab1:a lab2:b ...`) each get their half on their own host (the
  `bridge-stub` of 0.1.97, which attaches, checks and asks for its own side), and this machine relays the frames
  between the two halves over two SSH connections of its own. The hosts never connect to each other: neither gets a
  key, an address or a route into the other (the design that had lab1 start lab2's half itself was rejected as a
  widening, docs/BRIDGE_DESIGN.md 9.7). The relay has no side: nothing is attached here, no file read, no question
  asked here. It passes on a call only when the calling side was granted that tool, its path lies below a granted
  one and the bridge is active, at most at twice the bridge's rate (anything else is refused on this machine and never
  reaches the other host), and the receiving half checks it again against its own copy of the grant. Answers go back
  cut to what the protocol has; content is framed and tainted by the receiving half; this machine's log has the side,
  tool, outcome and size of each call, never its content. A suspension, a resume, an alert or the end on either host
  reaches the other; `bridge resume ID` and `bridge revoke ID` here act on both. It ends when this machine sleeps,
  shuts down or loses either host. Both hosts need sandbox-ai 0.1.98 or later (a half now describes its session
  before the open, said in its hello; an older one is refused with `sandbox-ai hosts update HOST`); two names of one
  machine are refused (bridge it there).
- **`bridge list --hosts`** lists every host's bridges too (asked at once; a host that does not answer is said),
  each bridge once: the half on another host of a bridge listed here, or by the host that made it, is left out.
  **`bridge show|revoke|resume HOST:ID`** act on a bridge of that host.
- **App:** the Board's Bridge part offers the running sessions of every host, grouped by host and read in the
  background, named as the board's host sees them (`NAME` on that host, `local:NAME` this machine's, `HOST:NAME`
  another's); a board that starts on another host now makes its bridges too (its start is `HOST:NAME`), once that
  host lists both sessions as running, and the part says where the bridge is made. New bridge… takes two sessions of
  other hosts and says whether the bridge is made there or relayed. The Bridges box lists the hosts' bridges beside
  this machine's (`HOST:ID`, asked every 30 s and at once after an action); Show, Revoke… and Resume… act there.
- **Web interface:** a Bridges page - every bridge of the service's machine and its hosts with Show, Resume and
  Revoke (asked first), and New bridge with the running sessions of every host, the launcher's dry run and its
  warnings shown before you confirm.
- Fixes found on the way: a half applied the other's "resumed" and a following "still suspended" in either order
  (the resume ran in a thread of its own), so a bridge could be active on one host while suspended on the other;
  changes of state are now applied in the order they came. Two bridges started at once could read this host's new

## `sandbox-ai uninstall`

Until now only `./install.sh --uninstall` removed an installation, and nothing removed the data.

- **`sandbox-ai uninstall`** removes the installation the command runs from (a user's own; a system one as root,
  which says so otherwise) exactly as `install.sh --uninstall` does: install.sh lists what that is
  (`--uninstall --dry-run`, a new option: KIND, a tab and PATH per line) and removes it, so the two can never differ.
  `install.sh --uninstall` now also removes the app's login entry when it starts that installation.
- **A table first** - what goes, where, how much space (gc --usage's sizing and table) - then a typed `y`; `--yes`
  for scripts, refused without a terminal otherwise; `--dry-run` shows the table only. What stays is listed below it.
- **`--purge`**: also the kept starts and their HOMEs, logs and state, kits, plugins and the other data, settings,
  caches, run directories, the web interface's files, the app's login entry, and sandbox-ai's own Podman images,
  volumes, networks and stopped containers and pods (a label `sandbox-ai.*`, Cairn's relay volumes; never another
  program's; never forced). macOS: `~/Library/Caches/sandbox-ai`, the LaunchAgent `org.sandbox-ai.app`, the Keychain.
- **`--secrets`** (only with `--purge`, named apart in the question: cannot be recovered): sandbox-ai's keyring or
  Keychain entries and its file store, the Git and registry logins, the agents' logins, VPN profiles and keys, the
  app's login browser.
- **Running starts** are listed and refuse the uninstall; `--stop-running` stops them through the normal stop path
  (and the MCP servers through `mcp stop`) first, and nothing is removed while one still runs.
- **Never touched**: workspaces, mounted folders (a folder of sandbox-ai's that holds a mount point is left and named),
  links out of its folders (removed as links), a folder of sandbox-ai's that is itself a link elsewhere, other users'
  data, other hosts (named: each is uninstalled there). A checkout, pip, pipx and the packages say what to do
  instead (`pip uninstall sandbox-ai-app`, `pipx uninstall sandbox-ai-app`, delete the AppImage or `.pyz`, move the
  macOS app to the Trash) and remove nothing.

## Several items in one allow option

`--allow`, `--allow-host`, `--allow-domain`, `--allow-tcp`, `--allow-host-port`, `--nameserver`, `--no-inspect` and
`--vpn-bypass-tcp` take one or more items in one value, separated by commas and/or whitespace:
`--allow-host "pypi.org, files.pythonhosted.org *.example.com"`, `--allow-tcp 10.0.0.5:22,[2001:db8::5]:443`,
`--allow "10.0.0.0/8 192.168.1.0/24"`, `--allow-host-port 8080,11434`.

- **Exactly the option once per item**: each item is checked as it is alone; one bad item refuses the whole option
  and names the item (`--allow-host "pypi.org,*.co.uk"`: `--allow-host *.co.uk: refused ...`); an item given twice
  counts once; empty items (`a,,b`) are left out; a value without any item (`--allow-host ","`) is refused.
- **Everywhere these options are read**: the start (the parser's `ListOption`), and everything that reads option lists
  by name through `canonical_options`, which now writes one option per item (`spread_lists`): a project file, a
  preset's options, an MCP server's options, `resume`, the security modes and the trust question.
  `sandbox-ai net allow` and `revoke` (their `--keep` writes one option per item), the CLI wizard, the app (Board
  fields, the setup wizard and the guide: one or more per line; the network dialog) and the web interface's network
  card (its API splits each string too) take them alike. The app and the web interface pass each item as an option of
  its own, so an older sandbox-ai on another host takes them as well.
- **Not split**: values with a comma or a space by meaning - `--api-key HOST=NAME[=SECRET]`, `--allow-http 'HOST
  METHODS PATH'` (`GET,HEAD`), paths and mounts (`--mount`, `--copy`, `--rules`), `NAME=VALUE` pairs - and `--profile`
  (a choice; repeat it).
- **One word per option**: `--allow-host a.example b.example` does not make `b.example` a second item. In
  `sandbox-ai net allow -A a.example RUN` the word after the value is the run, and every reader of saved option lists
  (project files, presets, MCP definitions, kept starts, the app, older hosts) takes one word per value; the start
  keeps refusing the extra word. Quote the list instead.
- Help texts, the option tables of the READMEs and bash completion's notes say "one or more, separated by commas or
  spaces".

## Root sees every user's starts

- **Why root's `sandbox-ai list` showed none of a user's sessions:** every start lives in the state directory
  (`~/.local/state/sandbox-ai`), the runtime directory (`/run/user/UID`) and the rootless Podman of the user who
  started it; root's list reads only root's own. README: *How sessions are identified* (run id, start id and name,
  state directory, the Podman pod `agent-RUN` with its labels `sandbox-ai.run` and `sandbox-ai.session`, Podman per
  user), in English and German.
- **`sandbox-ai list --all-users`** (root only; anybody else is refused with the reason): every user's starts, a USER
  column first (`"user"` and `"uid"` in `--json`), with the filters of plain `list` (what runs by default,
  `--stopped`, `--mcp`, `-a`, `--json`, `--no-trunc`); `--user USER` for one user's. The users are those of the user
  database with a `~/.local/state/sandbox-ai`. A user who is not logged in (no `/run/user/UID`, no lingering) is not
  asked: their kept starts are *stopped* when their end was recorded, else *unknown (not logged in)*.
- **`stop`, `logs`, `report` and `list --history` take `USER:NAME`** (or `--user USER`) for root: the command runs as
  that user - root's own sandbox-ai copy with root's Python, after `runuser -u USER` (else `setpriv`, `su`; macOS
  `sudo -u`), `env -i`, in their HOME, in a session of its own without root's terminal (no input: a question needs
  `--yes`; its output relayed with control characters escaped, so it cannot type into or steer root's terminal).
  Completion offers the other users' starts as `USER:NAME` to root.
- **Safe for root:** a user's state is read as data only - each directory opened below the one above it with
  `O_NOFOLLOW`, owned by that user, each file a regular file of that user of at most 1 MiB, checked again on the open
  descriptor; a link the user planted toward a root file (`session.json` -> `/etc/shadow`), a hard link to another
  owner's file, a FIFO or a device is never read. Podman is asked as the user with root's own `podman`; nothing in
  the user's HOME and never the user's installed sandbox-ai is executed; root's copy must be root's, writable by
  nobody else and reachable by the user (else refused with the fix). The app and the web interface run as their user
  and are unchanged. Tests: `tests/test_allusers.py` (fake users in a fake passwd, temporary HOMEs and
  `/run/user`, fake `runuser` and `podman`; the symlink attack, the refusal for non-root, and that the user's own copy
  never runs, through `./sandbox-ai`).

## Copy MCP servers from another host

Reported live on coding-101 (Sessions › Add MCP server… to a running session): that host had no MCP servers yet, and
"it would be practical to copy MCP servers from other hosts to an active session".

- **`sandbox-ai mcp copy NAME... --from HOST --to HOST`** (`local`: this machine) takes servers of yours from one host
  to another through the existing `sandbox-ai hosts` SSH paths: `mcp export NAME --json` there, `mcp import - --dry-run
  --json` on the target (every problem of every server said; nothing is written while there is one), then the import
  there; `--attach RUN` attaches them to that running start (`mcp attach --live` there); `--dry-run` and `--json`.
- **A catalog server is never copied raw:** the target adds it from its own read of the catalog (the same entry, the
  same pinned digest, its signature checked there; the image pulled there by digest, a rootfs fetched and checked
  there) with the source's folders, variables, network, VPN and limits as `mcp add` options. A catalog there that pins
  another image is refused (`--current-pin` takes its pin); one taken unsigned needs `--unsigned` again; one added from
  a catalog file needs `--catalog FILE_OR_URL` as the target reads it. A server of your own goes through mcp.json's
  validation there (`validated`, `validated_image`), never as it came; one whose command line holds what looks like a
  credential is not exported at all.
- **What the target cannot take as it is is shown and must be resolved:** a name it has (`--as NEWNAME`, `--replace`
  asked first), a secret it lacks (names only, never a value; `secrets set NAME` there or `--secrets-later`), a host
  folder of the source (never mounted there unasked: `--path OLD=NEW`, `OLD=OLD` keeps it, `--drop-path OLD`; the
  folders given are checked and warned about as `mcp add --mount`), an image it lacks (`--pull-image` by digest, or
  `--copy-image`: `podman save | podman load` through this machine with its size said, used only when Podman there has
  it under its pinned digest - else refused with the pull to do), a VPN profile it lacks (`--no-vpn`). Network grants
  and a command server's egress options are copied as defined and shown.
- **An older sandbox-ai there** is named with the update: "needs 0.1.98 or later (this machine has …); update it from
  here: sandbox-ai hosts update HOST --from-here".
- **App:** Add MCP server… of a running session and the MCP servers page have *From another host…*: the other hosts'
  servers read in the background; Check shows what is copied, changed and to be resolved, with a folder field of the
  target for each folder of the source (… chooses there) or *leave out*, a button to keep a missing secret there (typed
  in the app, sent to that host only), the image pulled or sent; Copy only after a clean check of the same choices,
  asked first (`mcp-copy`, and `mcp-replace` where one is replaced); attached to the running session at once, with the
  agent's restart offered where it needs one.
- **App, Add… of another host's catalog entry:** it showed one raw line ("TARGET=HOST_FOLDER[:ro|rw], one per line")
  and refused anything else ("Ein Ordner ist ZIEL=HOST_ORDNER ..."). The entry now comes whole from `mcp catalog
  --json` there (which also says each entry's description and recommended limits): the same fields as this machine's -
  each folder with its container path, a folder field with the remote chooser of that host and *writable*, the
  variables, the limits. Only a host older than 0.1.95 gives the line alone; then the dialog says so plainly, names the
  folders this machine's catalog knows for the entry, and takes a folder alone for the entry's one folder.
- **Web:** a running start's resources card has *From another host* (`POST /api/hosts/HOST/mcp-copy`, run by the
  service's machine: a check, then the copy asked first, `mcp-copy`).
- Tests first: `tests/test_mcp_copy.py` (in-process with a signed test catalog; end to end through `./sandbox-ai` with
  a fake ssh to the other host's real sandbox-ai and the fake Podman's pull, save and load; the regressions: a catalog

## Secrets: a primary password for the private files

Where no system keyring answers (a server, a container, `SANDBOX_AI_SECRETS=file`), `sandbox-ai secrets` keeps
secrets in private files. Until now they were plain text (`0600`). They are now encrypted with a primary password,
as a browser's password manager has one. Design and threat model: `docs/SECRETS_DESIGN.md`.

- `sandbox-ai secrets password set|change|remove`: typed twice at the terminal, never shown; for scripts
  `--password-stdin` or `--password-fd N`, never an argument or a variable. `set` encrypts every plain file in
  place (atomically; the old file's blocks are written over) and unlocks for 8 hours.
- The first secret kept in the files asks to set the password. Without a terminal `secrets set` stops and names
  the command; plain files are your choice: `secrets set NAME --plain`, or `SANDBOX_AI_SECRETS_PLAIN=1`.
- **Existing plain stores keep working.** A secret read from a plain file says once that it is not encrypted and
  that `sandbox-ai secrets password set` fixes it. Nothing is refused.
- `sandbox-ai secrets unlock [--for DURATION] [--idle DURATION]` asks once per session: a small process of your
  user keeps the key in memory (a `0600` socket in a `0700` folder, the peer's user checked by the kernel, no core
  file), until its time is over or `sandbox-ai secrets lock`. A start that needs a secret while locked asks on its
  terminal; without one it says `sandbox-ai secrets unlock`.
- `sandbox-ai secrets backend` now says what protects the secrets after the word (`file (encrypted with the primary
  password; locked: sandbox-ai secrets unlock)`, `keyring (encrypted by the system's keyring)`); `secrets status
  [--json]` has the numbers; `sandbox-ai doctor` has a check "Secrets" (a warning for plain files).
- Desktop app, Credentials, Secrets: the line above the list says what protects that host's secrets; one button
  does the step that is due (Set password…, Unlock…, Lock). Adding a secret to a locked store asks for the password
  first.
- Web interface, page Secrets: the same, for a logged-in session over the service's HTTPS; wrong passwords are
  slowed down per host and every attempt is in the audit log, the password never.
- Other hosts: `sandbox-ai hosts run HOST -- secrets unlock`, or from the app and the web interface: the password
  goes over the existing SSH connection on the remote command's standard input.
- Construction: scrypt (n = 2^17, r = 8, p = 1, a salt per store) derives the key that seals the store's random
  data key; each secret is sealed with encrypt-then-MAC from HMAC-SHA-512 (the standard library has no AES), bound
  to its name, its length padded. A wrong password, a changed file and a file moved to another name are detected.
- Not encrypted, and why (the full table is in the design document): the web interface's TOTP secrets and TLS key
  (the service must start and check logins unattended), agents' logins (the agent rewrites them while it runs).
  OpenVPN profiles and the wizard's typed push tokens are encrypted too (see "Secrets: OpenVPN profiles and push
  tokens under the primary password" below).
- An older desktop app that asks a 0.1.98 host for `secrets backend` shows the whole new line as "not known"; the
  app of this release reads both forms.

## MCP servers with network reach the internet, not your network

The MCP server review (group B, 2026-11-17): servers that run with network "full" - playwright, chrome-devtools,
gowitness, whatweb, web-fetch, and the "allowlist" entries (duckduckgo, brave-search, context7, youtube, ...) that
needed `--network full` because sandbox-ai could not hold them to their hosts - reached private and LAN addresses,
link-local, this host and the cloud metadata address 169.254.169.254 (navigating there was attempted in the review).
A network now means the internet, not your local network, held at the firewall in the server's own network namespace,
not by the server's code.

- **`full`: the internet, no LAN.** Every catalog server with network gets an nftables table in its namespace before
  it runs there (`vpn_runtime.egress_rules`): refused are RFC 1918, carrier-grade NAT (100.64/10), loopback, link-local
  (169.254/16 with the metadata services), the documentation, benchmark and reserved networks, multicast and broadcast,
  IPv6 unique-local (fc00::/7), link-local (fe80::/10), site-local, the IPv4-mapped and translation prefixes, and this
  host's own addresses - over IPv4 and IPv6, whatever a DNS answer said (rebinding meets the same refusal). DNS reaches
  the namespace's own resolver on port 53 only (pasta's 169.254.1.1, your router, slirp4netns's 10.0.2.3).
- **`allowlist`: only its hosts** (new; the default of an allowlist entry, so `mcp add duckduckgo` needs no `--network
  full` any more). The hosts its catalog entry declares (`NAME:PORT`) are looked up when each connection begins -
  public answers only, a private one dropped and said - and pinned in the rules and in its `/etc/hosts`; nothing else,
  DNS included (no lookups of its own, no channel out through DNS).
- **`lan`: internet + LAN** (new, opt-in): your network and this host too, never the metadata service; said with a
  warning, asked first in the app and the web interface (`mcp-lan`). **`--allow-private CIDR`** and **`--allow-tcp
  IP:PORT`** (`mcp add` and `mcp set`, repeatable; `set --no-allow` takes them away) open a part of your network to a
  `full` or `allowlist` server - a SearXNG on your LAN, a scanner's targets - with a warning.
- **Where it is enforced:** Podman - each connection's container is created, initialised (its namespace and pasta are
  there, nothing of the server runs), given the rules with `podman unshare nsenter --net=... nft -f -`, listed back and
  checked, and only then started; anything else removes it unstarted (`sandbox/mcp_egress.py`). Bubblewrap - bwrap waits
  on `--block-fd` until slirp4netns is attached and the rules are loaded into the sandbox's namespaces (nft with
  CAP_NET_ADMIN there, which the server never has). Behind a VPN or Tor - the VPN container loads the table before its
  own redirects (the tunnel's resolver, Tor's TransPort), so the original destination is judged: no tailnet address
  (100.64/10), no provider network behind the tunnel; an allowlist server's hosts are resolved and pinned through the
  tunnel; each connection checks the table again (`vpn.mcp_guard`); the VPN paths are otherwise unchanged.
- **Existing definitions keep working:** `full` now without your network; `sandbox-ai mcp list` and `sandbox-ai
  doctor` (new check *MCP network*) tell a `full` server whose catalog entry needs only its hosts to switch: `sandbox-ai
  mcp set NAME --network allowlist`. A server with network needs `nft` on this host (and `nsenter` for Podman): without
  it, it does not start, and doctor says so. `mcp copy` carries the choices and says where a server reaches the
  target's network. The administrator's policy (`mcp_network none`, `require_vpn`) holds for every kind with network.
  macOS: catalog servers do not run there yet (as before); a server defined with a command keeps its sandbox's own
  firewall.
- **App and web:** the network choice of a server (Add…, Properties…, the web page's add form) says *internet (no LAN)*,
  *only its hosts*, *internet + LAN (warning)* and *none*; the server lists have a Network column with what to change
  beneath. The Board no longer asks to give an allowlist server the whole outside network: it is added with its hosts.
- Tests first: `tests/test_mcp_egress.py` (an oracle that interprets the rules' nft lines: the metadata address,
  RFC 1918, carrier-grade NAT, IPv6 private and this host refused, a DNS answer that points into your network never
  pinned, an allowlist host reached and another refused, the LAN opt-in reaching the LAN but not the metadata service;
  the Podman guard with a fake Podman, Bubblewrap's gate, the VPN container's table), `tests/test_mcp_egress_e2e.py`
  (`./sandbox-ai mcp start` and a real bridge connection with a fake Podman: the rules loaded before the start, an
  allowlist host with a private answer refused before anything is made, no nft no start), the app's
  `tests/test_mcp_limits_ui.py` and `tests/test_hotfix_round_2.py`. The kernel's part (Podman's init, nsenter, nft in a
  real namespace, Bubblewrap's gate) needs a run with real Podman.

## Secrets: OpenVPN profiles and push tokens under the primary password

The two credentials that still lay in plain files beside the secret store are now under it too. Design:
`docs/SECRETS_DESIGN.md`, "Sealed files".

- **OpenVPN profiles are encrypted as files.** `~/.config/sandbox-ai/vpn/NAME.ovpn` holds the client's key and
  certificates (multi-line, up to 1 MiB: more than a secret's one line). The secret store seals files now, with the
  same construction and the same data key, the file's name bound in (`sandbox-ai-sealed-file-v1`; a profile copied
  to another name or changed is refused). It is opened only in the launcher's memory when a VPN starts (`vpn check`,
  a start, an MCP server's or a team member's VPN) and reaches the VPN container on its standard input, which keeps
  it in a tmpfs: never a plain file on the host's disk. While unlocked, the agent seals and opens files too; the key
  stays there.
- **The keyring and the Keychain** have no primary password: a profile is sealed there with a random key kept in the
  keyring as `SANDBOX_AI_FILE_KEY` (made once; `secrets delete` refuses it while a profile needs it). A login without
  the keyring (SSH without the desktop's session) cannot open the profiles and says so.
- **Push tokens typed in the wizard are secrets** (`GIT_TOKEN_HOST`, e.g. `GIT_TOKEN_GITHUB_COM`) and the project file
  names `--git-token-secret URL=NAME` - in `sandbox-ai wizard` and in the app's wizard (locked or without a password
  yet, the app asks for it in a hidden field first). No token file is written any more.
- **Migration, no plain leftovers:** existing plain profiles and the wizard's token files in
  `~/.config/sandbox-ai/tokens/` are moved when the primary password is set, at every unlock (said: `moved under the
  primary password: vpn/work.ovpn (encrypted), tokens/github.com (now the secret GIT_TOKEN_GITHUB_COM)`), and at their
  first use when that needs nobody to type anything (the keyring, or unlocked). Each is replaced atomically and the
  old file's blocks are written over (copy-on-write file systems, snapshots, SSDs and backups may still keep the old
  text: replace a key or token that lay plain on a disk you do not trust). Locked, a plain profile or token is read
  as it is, with a warning, and moved later. `secrets status` (`plain_files`) and the doctor's check "Secrets" list
  what is still plain; `secrets password remove` makes the profiles plain again with the secrets.
- **Old project files keep working:** a moved token file names its secret, so `--git-token-file URL=FILE` for it
  reads the secret (locked: `sandbox-ai secrets unlock`), and the first start says once which `--git-token-secret` to
  write instead; `sandbox-ai wizard edit` and the app's wizard offer the secret in its place. A token file of your own
  elsewhere is read as before, never moved, with a warning.
- **New OpenVPN profiles** (`vpn add --openvpn`, the app's and the web interface's VPN pages) are sealed as a new
  secret is kept: without a primary password a terminal sets one first; without a terminal the command stops and
  names `sandbox-ai secrets password set` (`SANDBOX_AI_SECRETS_PLAIN=1`: plain, your choice). `vpn remove` writes the
  file over before removing it.
- Tests first: `tests/test_secrets_sealed_files.py` (the construction and its associated data, files up to 1 MiB
  through the agent, the keyring's key, migration with a canary grepped across the whole temporary HOME and the old
  inodes written over, locked stores refused with the unlock hint, old project files, the wizard; `./sandbox-ai` end
  to end with a temporary HOME: `secrets password set`, `vpn check` with a fake Podman that gets the key whole, a
  start's dry run unlocked and locked), `tests/test_wizard.py`, the app's `tests/test_wizard_token_secret.py`.

## Approvals: no answer is no refusal, one table, no second window

**A question nobody answered in time stays open, and every answer can be changed.** Until now an unanswered question
was refused after 60 s, the same request was then refused at once for 2 minutes without a question, and that could
not be taken back; the app and the web showed the questions in one table and what was refused in another below; a
click on Allow or Block opened another window to confirm it; and an answer sandbox-ai refused (a name without any
address, say) came in a box with OK.

- **Timed out is not refused.** After the wait, the request fails ("not answered yet - the human may still allow it;
  retry later") and its question stays open, listed as timed out. A later answer counts at once for the request's
  next try: for the run, the destination is opened now (a name pinned for the run); once, it is kept for the next
  try and used up by it. The next try of the same request waits for that same question again instead of asking a
  new one, and nothing is refused at once for being unanswered any more. The supervisor marks the question
  (`ID.state`: open again, or timed out) and watches the questions that timed out for their answers; questions that
  timed out do not count as open (twenty of them leave room for the next question). MCP servers of their own do the
  same. What rules deny stays denied, a canary's pause is unchanged, the administrator's and the security mode's
  caps on the scope still hold.
- **`--ask-timeout SECONDS`** (5-3600, short `-at`): how long a request waits for its answer - at a start, in a
  project file's options, in a preset, as `ask_timeout` in `~/.config/sandbox-ai/defaults.json` (`sandbox-ai
  defaults set ask_timeout 120`, the web interface's defaults, the app's Settings > Polling). Default still 60 s.
  The proxy waits as long, and the run's MCP servers ask with the same time.
- **Every answer can be changed.** `sandbox-ai approvals list --state open|timeout|allowed|refused|all [--json]`
  lists the questions in every state, each with what may be done about it; `approvals allow|deny|ask-again ID` take
  any of them - an open one, one that timed out (answered as a question) or one answered already (the run's
  decision changed: `allow ID` means for the run there; the list then says what the run decides now). `ask-again`
  on a question still open says so.
- **One table with tabs.** The app's Approvals page and the web interface's have one table with the tabs Open,
  Allowed, Refused, Timed out and All, with their counts, across every host as before; the app's Blocked and History
  sections are gone (what the sandboxes refused without a question is under Refused). Rows can be selected and
  answered together.
- **No second window.** Allow, Deny, Block always and Ask again act at once, "always" too; a note offers *Undo* for
  a few seconds (the run forgets the answer, a changed answer is changed back). The confirmations
  `approval-allow-always` and `approval-deny-always` are gone from both confirmation tables (the app's and the web
  service's, which stay equal); the notifications' *Allow always* and *Block always* answer at once too.
- **Errors in passing.** An answer sandbox-ai refuses is a short notice in the error colour that goes by itself (at
  least 1.5 s, longer for a longer text) and stays in the page's note line - in the app (`short_notice(...,
  error=True)`) and the web interface (its toast closes by itself for these).
- The agents' skills, the refusal texts, the help (EN, DE), the READMEs and the tour say it so.

## System monitor

"The app should have system monitoring too - CPU, memory, IO usage by project as well, so you see what is heavy and
what could do with less. With statistics, warnings ..." Until now `sandbox-ai usage` showed one look at a run, and the
memory watch only ran for runs with a limit and kept a sample a minute. Now every run is recorded and summed up:

- **The collector** is a thread of each run's launcher (`monitor.py`): every 10 seconds (`monitor_interval` in your
  defaults, 1-3600; 0: off) it reads the run's own cgroup - the pod's with Podman (the agent, the agents `--with` it,
  its services), the scope with Bubblewrap, a Bubblewrap run without a scope by its process tree in `/proc` - and the
  counters of its network namespace: CPUs (and their share of `--cpus` or of the host, throttled periods), memory
  (current, peak, limit, `/tmp` files, `memory.high` events, OOM kills), disk IO (`io.stat`), network bytes,
  processes and threads, PSI pressure on CPU, memory and IO, and with `--gpu nvidia` the GPU (`nvidia-smi` every
  minute). Where this host cannot read the cgroup (macOS: podman machine's VM; `--podman-url`; a host without cgroup
  v2) one `podman stats` call every 30 seconds stands in (CPU, memory, block IO, network, processes; no pressure).
  MCP servers' sandboxes are recorded alike. Cost: about 1 ms of CPU per sample with the host's totals (0.01 % of one
  CPU at 10 s, measured; each minute's rollup records the collector's own CPU, and `stats usage` says it).
- **Kept** per run in the project's log folder: `monitor-TIME-RUN.jsonl` (each sample, 24 h), `monitor-1m-...` (minute
  averages and peaks, 7 days), `monitor-1h-...` (hours, 30 days), each trimmed by its writer while the run runs; once
  it ended `gc` and its daily pass compress them like the run's other logs and `log_days` removes them (`gc --usage`
  counts them as their own kinds). Runs without a log folder: `state/monitor/runs/` (30 days, 256 MiB at most). The
  host's totals (CPU busy, load, free memory, swap and swapping, disk IO, pressure) are written by one launcher at a
  time (`monitor/host.lock`); each run's last look is in `monitor/live/RUN.json`, which `top` and the app read without
  measuring anything.
- **Warnings** (once per stretch; one that comes back within an hour is recorded, not said again): memory at 90 % of the limit, an OOM kill, the CPU
  limit holding a run back in half the periods for 2 minutes, IO pressure (40 % "some" or 20 % "full" for a minute),
  idle (under 0.02 CPUs for 30 minutes while holding 1 GiB or more), processes and threads at 90 % of `--pids` (4000
  without a limit), the host under 10 % free memory or swapping in. Each has a suggestion and its command ("raise
  --memory to 12g: peak 7.8 of 8 GiB with 3 throttling events", "raise --cpus to 4: held back in 74 % of the periods
  for 6 min", "stop idle run web: 3.2 GiB for 2.0 h") and goes to the run's safeguard records (new kind `resources`:
  the app's and the web's popups, a grouped desktop notification - those the memory watch tells itself are not told
  twice), to its activity (new kind `resources`) and to its series.
- **`sandbox-ai top [--host HOST] [--project DIR] [--sort cpu|mem|io|net|pids] [--json] [--watch [S]]
  [--no-measure]`**: what runs now, the heaviest first, with project (MCP servers and helpers under the start they
  serve), CPU, memory of the limit, IO, network, processes, warnings and suggestions, and the host's line.
- **`sandbox-ai stats usage [--since 7d] [--by project|run|agent] [--project DIR] [--host HOST] [--json]
  [--series]`**: per group and run the CPU-hours, CPUs on average and at most, memory on average and at most, bytes
  read, written, received and sent, OOM kills, warnings; the top consumers, the idle runs that held memory, the host's
  window and the collector's cost. It reads samples up to 6 h, minutes up to 7 days, hours beyond (and the finer tier
  for the part the coarser has not yet).
- **App**: a **System monitor** page under Monitoring (beside Statistics; it follows the Sandboxes page's host): the
  host's line, the runs grouped by project with a trend (CPU line, memory area) of the last 15 minutes, sort by CPU,
  memory, disk IO, network or processes, a history chart of the run, the project or the host for 1 hour, 24 hours, 7
  or 30 days (QPainter: the app ships without Qt Charts), the warnings in German or English with Do what it suggests
  (raise the limit with `limits-raise` asked first, stop the run with `start-stop`) and Stop run…, also on the
  right-click menu. One `top` read every 10 s and one history read a minute while the page is shown, none while it is
  hidden. Help EN+DE (page and concept), tour, tips.
- **Web**: a **System monitor** page with the same (`GET .../monitor`, `GET .../monitor/usage/24h`; SVG trends and
  history; Raise and Stop asked in place, sent with the confirmation), read again every 10 s while shown.
- **macOS**: recorded through `podman stats` of podman machine's VM every 30 s; the host's line is the Mac's (load,
  memory from `vm_stat`, swap); no PSI and no per-run GPU there. Not tested on a Mac in this round.

### Security review

[docs/reviews/final-review-1-security.md](../reviews/final-review-1-security.md): the new features read as an attacker
would use them - an agent in a sandbox, a hostile MCP server, another host that is not what it seems, another user of
this machine, a web page, a project file. Five bugs, each with a failing test first:

- **`mcp import` believed the export's own lists of folders and secrets.** The target resolved the folders and
  secrets the export *listed*, and took the definition beside them as it came: a source host (or an export file) that
  listed none had a command server written with its `--mount /etc:...:rw` and its workspace unasked, and its
  `--secret-env` took a secret of the target without a word. The target now reads both from the definition itself
  (its options as `mcp.json` reads them: a short form is its long option), takes the kind from it too, and refuses a
  definition whose parts cannot be read. The plan of a command server shows its command and every option as they
  are written (`--git-logins`, a device, a published port came without a line).
- **`mcp copy --copy-image` let the source rename this host's images.** `podman load` names every image of an archive
  as the archive says: a source that sent one naming `localhost/sandbox-ai-claude:latest` replaced that image for
  every later start. `mcp image-load` now keeps the archive in a private file first, reads its index (an OCI archive's
  `index.json`, a Docker archive's `manifest.json` and `repositories`) and loads it only when every name in it
  belongs to the server's own repository; anything that is not such an archive is refused, nothing reaches Podman.
- **A tool call could show the rules one path and run another.** The rules see every agent's arguments under Claude
  Code's names (Pi's `path` is `file_path`). A call that carried `file_path` as well, with a harmless value the
  agent's tool does not read, had that value checked: `write {path: /etc/x, file_path: /work/ok}` passed a rule that
  keeps writes in `/work` (Pi, OpenCode, OpenCode 2, Hermes, Goose; Letta Code's `cmd` beside `command`). Such a call
  is refused; the same value twice is one argument.
- **Wrong primary passwords sent at once were all checked.** The count of wrong attempts was read before the key
  derivation and written after it: six `secrets unlock` at once (a web session's parallel requests) were six checks
  against a count of zero, counted as one. One attempt at a time now (`.attempts.lock`): three are checked, the rest
  wait, as six in a row.
- **What the target of `mcp copy` answers is data.** Its plan's texts went to this terminal as they came (escape
  sequences), and a plan without its keys ended the command with a traceback: every text is made printable and the
  plan's shape checked; the image reference of an export is checked before it is passed on.

Also: an image server of your own that reaches the local network on the source (`--network lan`, `--allow-private`,
`--allow-tcp`) is now a warning of the import's plan (it reaches the target's network).

Read and found sound, with what was tried: the primary password's construction and its key agent, the egress rules of
MCP servers, the relay of bridges across hosts, root's reading of other users' state, `uninstall --purge`, remote
folders, `--no-totp`, the log redaction's long-text path (1.4 million random texts against the plain one: no
difference). What needs a real Podman, nft or another machine is listed in the review.

## Local models: the research's first round on the real server

The first of five rounds ran the fixes above with sandbox-ai's own connection proxy and MCP relay (not a relay of the
research) on all nine harnesses and four models (Qwen3-Coder-Next, Laguna-S-2.1, Qwen3.6-35B-A3B, Nemotron-3-Super),
each harness's real CLI configured by sandbox-ai's own start code. It confirmed them on the server - a step after the
loop guard's note takes about a second at 90,000 tokens, Codex's MCP tools and shell commands work, no request was
refused - and found six more causes of "a lot of mcp issues ... endless loops ... took ages":

- **An MCP server's empty capabilities no longer reach the agent.** Every server made with the MCP SDK's FastMCP
  advertises `resources` and `prompts`, whether it publishes any (sandbox-ai's catalog servers publish none). OpenCode,
  Claude Code and Pi then offer the model tools for MCP resources (`list_mcp_resources`, `read_mcp_resource`), Hermes
  four more tools per server. Asked for "the MCP tool read_file of the server named files", a local model took those:
  Laguna-S in Hermes called `mcp__files__read_resource` again and again and then searched Hermes' own logs for how
  the "resource" is addressed - ten minutes without one call of the tool asked for; in OpenCode it gave the server up
  ("isn't exposing any resources"). The relay in front of every MCP server now asks a server that advertises
  resources or prompts once, at the handshake, what it lists, and answers the agent's `initialize` without the
  capabilities that list nothing (`mcp-calls.jsonl`: a `capabilities` record). OpenCode then offers 35 tools instead
  of 38 with `--mcp files,exec`, Claude Code 46 instead of 49, Hermes 44 instead of 52, Pi 29 instead of 32; the same
  runs then took 57 s (OpenCode) and 80 s (Hermes) and passed. A capability stays when the server lists something,
  says its list may change, or does not answer within 5 seconds.
- **The agents' tools for MCP resources say what they are not.** Codex, DSH and Goose offer theirs whatever a server
  advertises, and the descriptions read like the way to an MCP server ("Read a specific resource from an MCP server
  given the server name and resource URI"): Laguna-S in Codex called `read_mcp_resource` 115 times with guessed URIs
  until the time limit - never the same call twice, so the loop guard had nothing to count. The connection proxy adds
  a sentence to each such tool's description: that it does not call a server's tools, and how the request's own MCP
  functions are named ("tool T of the MCP server files is the function mcp__files__T, of exec mcp__exec__T - for
  example mcp__files__read_file"; the start's `--mcp` servers are in `proxy.json` for that). With it: 2 such calls
  instead of 33 in Codex, none instead of 6 in DSH.
- **Claude Code no longer compacts at half the window with LM Studio.** LM Studio's Messages API reports
  `input_tokens` as the whole prompt and `cache_read_input_tokens` beside it for the cached part; in Anthropic's API
  `input_tokens` exclude the cached tokens. Claude Code added both and compacted at 50,589 of 131,072 tokens - a
  summary request of over a minute, the conversation again from 22,000 tokens, what the model had found out gone, twice
  in one 20-minute run. For an LM Studio endpoint the proxy takes the cached tokens out of `input_tokens` on the
  answer's way to the agent (`llm_usage` in the connection log). With Claude Code's CLI and a scripted server that
  counts as LM Studio does: compaction at 52,000 tokens before, at 95,000 after. On the real server the same task
  with the same model was then solved in 13 minutes, in one conversation of up to 60,040 tokens.
- **The proxy keeps a streamed answer alive while the server reads a long prompt.** Seven of the nine harnesses wait
  for a silent server with the settings a `--llm` start gives them (checked: 420 s of silence after the headers, one
  request, answered). Claude Code and DSH have no setting: both gave the request up after 300 s and sent it again, for
  ever - and the proxy did not notice the agent's leaving until the server's first token, so the server went on
  reading the abandoned prompt and the second try waited behind it. For a model server of your own the proxy now
  sends a line that readers of server-sent events skip (`: keep-alive`; Anthropic's `ping` event on the Messages API)
  after 20 s without a byte, between two events only; with it Claude Code waits and finishes, and an agent that went
  away is noticed at the next such line. DSH gives up after 300 s whatever the stream carries (no remedy found).
- **Qwen Code no longer takes a thinking model's reasoning for a loop.** With `--llm` its heuristic loop detection
  ended the debugging task a minute in - "Loop detection halted the run (repetitive_thoughts ...)" - with Laguna-S
  twice of two runs and with Qwen3.6-35B (its detector compares the start of the last three "thoughts", and a local
  server streams one thought in many pieces). A `--llm` start now sets `model.skipLoopDetection`; Qwen Code's
  protection against a repeated tool call stays with the loop guard on (`model.loopProtection: stop`), and the loop
  guard holds on the wire as for every agent. The same task was then solved with Qwen3.6-35B in 4 and 14 minutes (two
  runs) and with Laguna-S in 18.
- **Qwen Code no longer offers a local model its tool for MCP resources.** It lists `read_mcp_resource` among its
  deferred tools whatever a server advertises, so neither the relay's dropped capabilities nor the proxy's sentence
  reach it: Laguna-S, asked for an MCP server's `read_file`, found it with `tool_search` and called it six times with
  guessed URIs until Qwen Code stopped the run, `mcp__files__read_file` offered all along. A `--llm` start leaves the
  tool out (`tools.exclude`; checked with the real CLI: no longer in its list of deferred tools); Laguna-S then passed
  the smoke test twice of two.
- **The loop guard sees a repeat whose description changes.** Claude Code's `Bash`, DSH's `bash` and Qwen Code's
  `run_shell_command` take a free-text `description` beside the command, and Qwen3-Coder-Next, asked to run
  `python3 -m pytest -q` five times, described the calls as "Run pytest first time" ... "fifth time": five different
  calls for the guard, no note in those three harnesses. A call is now compared without such text: the harnesses'

  `thought(s)`, `comment` or `title` that the request's own tool schema does not require - never an argument the
  call has no other one beside. Calls that are exactly the same count as before.
- **The loop guard sees Hermes' repeats.** Hermes appends a note of its own to the result of the third identical call
  ("[hermes note: this is the 3rd consecutive identical call ...]", then "4th" ...), so every result from the third on

- **Guessed calls of one tool that all fail get a note too.** Laguna-S in Codex called `read_mcp_resource` 110 times

  read the errors, check what the tool expects or take another tool; again at every as many failures after it. A
  failed call is one the API marks (`is_error` on the Messages API) or whose result starts as the harnesses write an
  error ("Error: ...", "resources/read failed: ...", "Failed to read MCP resource", `<tool_use_error>`, a JSON
  `{"error": ...}`, a command's non-zero exit); a call of the tool that worked, or of another tool, ends the streak.
  A note only - the model goes on - at its fixed place like the others, so the server's prompt cache holds. Only for
  the `--llm` server, as the whole guard.
- **The model x harness profiles say what round 1 measured.** Every pair of the four models and nine harnesses has

## Remote folders (sshfs)

**A folder of another machine as a workspace or a mount, at the start and while the sandbox runs.** sandbox-ai mounts
it on the host with sshfs and gives the sandbox that folder exactly as a local one; the agent never gets `/dev/fuse`,
an SSH key or the connection.

- `--workspace sshfs://[USER@]HOST[:PORT]/PATH` (`/~/DIR`: a folder in the remote HOME), `--mount
  sshfs://...:DEST:ro|rw` and `sandbox-ai workspace add [RUN] sshfs://... [--ro] [--name NAME]` (`workspace remove RUN
  sshfs://...` takes it out and unmounts it). HOST: your `~/.ssh/config` and ssh-agent, or a host of `sandbox-ai
  hosts` (its user, port, identity and known_hosts).
- Mounted in sandbox-ai's own state folder (`remote/RUN/N/NAME`, 0700), then every check of a workspace or mount
  applies; read-only with `:ro`, `--ro`, `--workspace-ro` or the mode. Writable, the start warns that the agent
  changes and deletes files on that machine, and that the traffic goes over SSH from the host, not through the proxy.
- The host key is always checked (never `StrictHostKeyChecking=no`). Without a terminal: keys only (BatchMode), with
  what to do when the login fails; a session started in a terminal opens the connection there first (a password or a
  passphrase is asked there), its supervisor's sshfs uses it.
- Unmounted after the pod at the end of the run (with what `workspace add` mounted); a sandbox that outlives its
  launcher keeps it until the run has ended (`sandbox-ai stop`, `list`); `sandbox-ai gc` unmounts what ended runs left.
  Only empty folders are removed there, never recursively. A kept start keeps the source and mounts it again on
  `resume` (also `workspace add NAME sshfs://...` for a stopped kept start, and `resume NAME --workspace sshfs://...`).
- Without sshfs: the start and `sandbox-ai doctor` ("Remote folders (sshfs)") say how to install it.
- App: **Other machine…** in Add workspace (with what it means under the field), **sshfs…** beside the Board's project
  folder and extra folder (the Board checks the source and counts it as a folder of another machine); the list of
  added workspaces shows the source. Web interface: the workspace field of a start, Add workspace, Remove and the
  resume options take `sshfs://...`.
- macOS: the Mac's sshfs (macFUSE or FUSE-T) mounts it in your HOME, which podman machine shares with its VM - not
  tested on a Mac yet.
- **NFS and SMB** in the same places: `nfs://SERVER[:PORT]/EXPORT[/PATH]` (fuse-nfs without root when installed or
  `?mount=fuse`, else the kernel's client through `sudo mount -t nfs`; `?vers=`) and
  `smb://[[DOMAIN;]USER@]SERVER[:PORT]/SHARE[/PATH][?secret=NAME]` (the kernel's client through `sudo mount -t cifs`,
  files owned by you; the password from a sandbox-ai secret, in a 0600 file removed right after the mount; else as
  guest). Always `nosuid,nodev`; unmounted the same way. sudo asks in the terminal of a foreground start; a session
  and the app use `sudo -n` (a sudoers rule for mount and umount, else the start says what to do). Doctor names what
  mounts NFS and SMB. The app's and the web's folder fields take them too. Linux only so far.

## Mounts: you decide

**A host path you choose is given - with a warning that names the risk - wherever it is.** "If the human wants to
mount something in, no matter what it is, it is done, with a warning that it is a risk": sandbox-ai refused some of
your choices until now. Every path you choose - `--workspace`, `--mount`, `--state-dir`, `--copy`, `--log-dir`,
`--gui-vnc`, `--browser-profile`, `sandbox-ai workspace add`, an MCP server's folder (`mcp add|set --mount`,
`--mcp-mount`), the trusted project file, a preset of your own, the app's and the web page's folder choices - is now
given, and the warning says on standard error and in `launcher.log` what the agent can do there and that read-only
(`--ro`, a `--mount` with `:ro`) is the safer choice:

- **sandbox-ai's own folders** (its configuration and trust store, `~/.local/state/sandbox-ai`, the approvals,
  logins, caches; also those a start recorded for a later `workspace add`): "the agent can change sandbox-ai itself -
  its approvals, network rules and policy, the trust store, its own run's records; read-only lowers this to reading
  them (request logs with their bodies, approvals, logins)". A `--copy` from the secret store, too.
- **HOME and `/`**: "the agent can change your shell start files, credentials and sandbox-ai's trust store:
  everything you can do on this host" (read-only, it still reads all of it). The temporary directory and
  `XDG_RUNTIME_DIR` say what is there (other programs' files, your session's sockets).
- **The launcher's tree** (a checkout, a venv, the package or its copy), writable: "the agent can change the code
  that runs on your host as you". Read-only says nothing, as before.
- **A folder of your sockets, a tree with a live socket in it, a socket file itself** (`/var/run/docker.sock`): "the
  agent can connect to it and get what runs behind it ... even through a read-only mount".
- **`/proc`, `/sys`, `/dev` and the kernel's own file systems** (also `--copy /proc/self/environ`): what the agent
  gets with them. If Podman or Bubblewrap cannot bind such a tree, the start fails with the engine's own message and
  sandbox-ai names the tree it gave (the one refusal left: it cannot be done). A device node itself is refused for
  `--mount`, because the engines mount with `nodev` and it could not be used - `--device` gives it.
- **A file the launcher reads or writes inside a tree the agent can write** (the trust store, your rules, the
  defaults file, `--privacy-rules`, a kit, the login store, the project memory, the plugin store, a token or
  credentials file, an extra preset directory, an MCP server's folder, the run's own folders: the log directory, the
  tmux, MCP and approvals sockets): what the agent can change, and that a link it puts there could make the launcher
  act on another file of yours.

What stays refused is what you did not choose: a symlink on the way that a sandbox could have planted (sandbox-ai
never follows one in a tree an earlier run exposed - now also on the way to a file the launcher reads), and a preset
passed on to you (a team's directory, an imported file) that names a private location itself. Remembered approvals
("always" for the project) in a tree the agent can write are read too, like the trust store, the defaults file and the
kit hook approvals beside them, with a warning that the agent could have approved its own wishes there for its next
start (your choice: read all, warn). An MCP server's connection is still refused when its folder was swapped. Structural refusals stay: overlapping workspaces, a workspace in the run's own HOME, commas,
the administrator's policy, the mode paranoid's.

The app shows it where you choose: the Board's verdict says "The launcher accepts these options, with a warning" with
the launcher's words, a folder the app creates is made with the warning (it said "Not created" before), the wizard's
new project folder asks with the warning in the question, and a workspace added to a running sandbox shows the
warning in a box that stays - in English and German. The web page's workspace add and resume show the warnings in a
toast that stays.

## Fixes from the audit of 2026-11-16

- **A damaged `approved.json` is kept, not written over.** The remembered "always" approvals were read as empty when
  the file was not valid JSON, and the next "always" (or `approvals forget`) wrote back only its own entry: every
  earlier answer was gone. Now the damaged file is kept beside it as `approved.json.damaged-TIME` (with every answer
  in it), the warning says so (standard error and `launcher.log`) and a new one is begun; a file that cannot be read
  at all (permissions) is left as it is and nothing is remembered ("not remembered for the project: ..."), the answer
  holds for the run.
- **A start or resume whose agent ends at once says so.** It said "Session failed to start (status 0)" - a failure
  with a status that says none. Now: "Session ended at once, before its terminal was ready: the agent exited with
  status N after S s (or: the agent ended at once), and its sandbox with it (status 0)", the path of its
  `supervisor.log` and its last output.
- **Two `sandbox-ai web serve` at once each keep their port from the sandboxes.** Both wrote `web/listen.json`, the
  second over the first's port: while both ran, `--allow-host-port` (at the start, and `net allow` during a run)
  accepted the first one's port - a sandbox reached a web interface that controls every sandbox. Each server keeps a
  record of its own (`web/listen-PID.json`, removed at its end); every running one's port is refused, an older
  server's `listen.json` still counts.
- **`net allow --allow-host-port` never takes a port the sandbox listens on itself.** DSH's web UI (3080, or the
  next free port) was kept from the host's relayed ports only at the start: a later `sandbox-ai net allow RUN
  --allow-host-port 3080` was accepted, and the relay took the sandbox's `127.0.0.1:3080` - the session browser and
  the agent reached the host's port instead of DSH. The start now records the web UI's port (`dsh_web_port` in
  run.json), and `net allow` refuses it, and a `--service`'s ports, naming what listens there.
- **`--mcp-env` with a variable that changes what code runs is set with a warning, never from someone else's
  preset.** `LD_PRELOAD`, `LD_*`, `NODE_OPTIONS`, `PYTHONSTARTUP`, `PYTHONPATH`, `BASH_ENV`, `PATH`,
  `JAVA_TOOL_OPTIONS` and the like make an MCP server's sandbox run other code - with a folder the agent can write
  mounted there, the agent's. Your own (the command line, the app, the web page, your defaults, the project file you
  trusted, a preset of yours) is set and the warning names the risk (standard error and `launcher.log`; a session's
  start says it once); a preset passed on (built-in, an extra directory's) may not set one - "give it yourself if you
  mean it" - unless the whole value is one you give (`--preset-value`).
- **The sandbox's browser has a `/dev/shm` of its own.** The pod's `/dev/shm` (its IPC namespace's) is the agent's
  too. Chromium keeps its shared memory in `/tmp` (`--disable-dev-shm-usage`); Firefox has no such switch, so what it
  puts there (POSIX shared memory where it cannot use memfd, named semaphores) - pages, what you type - the agent
  could read and change. The browser's container now mounts a tmpfs of its own there (512 MiB, nothing executable),
  for Firefox and Chromium alike.

## PyPI: one package, `sandbox-ai-app`

**The PyPI package is `sandbox-ai-app`** (the name `sandbox-ai` on PyPI is not this project: never install
that one). One package with everything; the command stays `sandbox-ai`:

```bash
pipx install sandbox-ai-app                    # the command line and the web interface (sandbox-ai web)
pipx install 'sandbox-ai-app[gui]'             # with the desktop app: sandbox-ai-app
python3 -m pip install 'sandbox-ai-app[gui]'   # the same with pip, in a virtual environment
```

- The wheel `sandbox_ai_app-X.Y.Z-py3-none-any.whl` holds the command line with its web interface (`sandbox_ai`,
  standard library only, Python 3.9+) and the desktop app (`sandbox_ai_app`). The extra `[gui]` adds the app's
  PySide6, pinned exactly: 6.12.0 on Python 3.12+ (the release the AppImage and the macOS app carry), 6.11.3 on
  3.10-3.11 and 6.10.3 on 3.9 (6.12.0 crashes below 3.12); each pin at least 14 days old.
- `sandbox-ai-app` without `[gui]` says how to add it (`pip install 'sandbox-ai-app[gui]'`, with pipx
  `pipx install --force 'sandbox-ai-app[gui]'`) instead of a traceback.
- The app finds the `sandbox-ai` of its own installation (the `sandbox_ai` beside it), whatever other `sandbox-ai`
  comes first on `PATH`; no `SANDBOX_AI_HOME` needed. `SANDBOX_AI_HOME` still wins when set.
- `sandbox-ai version --verbose`, `update`, `doctor` and `hosts` name the pip installation's update as
  `pip install -U sandbox-ai-app`; so do the app (System, update) and the help.
- Release: `make_dist.py` builds exactly `sandbox_ai_app-X.Y.Z-py3-none-any.whl` and `sandbox_ai_app-X.Y.Z.tar.gz`
  (it stops on any other name) and `release.yml` uploads those two to PyPI by trusted publishing (project
  `sandbox-ai-app`, repository `c0decave/sandbox-ai`, workflow `release.yml`, environment `pypi`); every other
  release file is unchanged.

## Local models: the research's second round

The second round looked at why Claude Code on Qwen3.6-35B-A3B "took ages" in round 1, and at what the server does
with an agent's thinking request:

- **A harness's note between two tool steps no longer costs a full prefill.** Qwen3's chat template keeps the model's
  earlier reasoning only up to the last user message that is not a tool result, and LM Studio moves a system message
  from the middle of a conversation into the system prompt at the top. Claude Code sends its "changed on disk" note
  (a file it edited was changed by a command) as such a system message after the tool result, and its reminders as
  text beside it: each one changed the prompt right after the tools, and the server read everything again (round 1:
  16,384 of 86,413 tokens from the cache, 93 s). The connection proxy now puts such a note of the harness's into the
  tool result it follows (the human's own messages stay as they are); measured with the server's own counts: 9,472
  of 9,777 tokens from the cache instead of none.
- **OpenCode 2's code mode gets the sentence about MCP resources.** Its tools for MCP resources are listed in the
  system prompt's "Code Mode" catalog, not as tools, and no setting of OpenCode 2 removes them; the proxy now puts the
  sentence it gives the other harnesses' resource tools under each such entry.
- **Measured, not changed:** LM Studio applies neither Claude Code's thinking request nor its effort, nor the chat
  API's `reasoning_effort` or `enable_thinking`, to Qwen3.6 (MLX): its log says "Reasoning setting 'high' cannot be
  converted", and the prompt it renders ends in `<think>` in every case. `CLAUDE_CODE_DISABLE_THINKING` only hides
  the reasoning: the model still thinks, the answer comes after a silence, and the reasoning is lost from the history.
